# CloudDisk 第五期：引入注册中心设计文档

本文档基于第四期 `CloudDisk` 微服务版本和《Web网盘项目.pdf》第 29-31 页的第五期内容，说明如何在当前项目中引入 Consul 注册中心。

第五期的目标不是继续拆业务服务，也不是修改前端 HTTP API，而是解决第四期遗留的服务地址硬编码问题：

1. 后端 srpc 服务启动后，主动把自己的服务名、实例 ID、IP、端口和健康检查信息注册到 Consul。
2. API Gateway 不再固定连接 `127.0.0.1:9001/9002/9003`，而是从 Consul 查询健康实例。
3. 支持同一个服务启动多个实例，为后续横向扩容和故障转移打基础。

---

## 一、第四期当前状态

第四期已经把单体后端拆成多个进程：

```text
Browser
  |
  | HTTP
  v
API Gateway :8888
  |
  | srpc
  +--> AuthService     :9001 -> tbl_user
  |
  | srpc
  +--> UserService     :9002 -> tbl_user
  |
  | srpc
  +--> FileMetaService :9003 -> tbl_file
  |
  | RabbitMQ publish
  v
RabbitMQ -> OssUploadWorker -> Aliyun OSS
```

当前可执行程序：

```text
bin/server             API Gateway
bin/auth_service       认证微服务
bin/user_service       用户资料微服务
bin/filemeta_service   文件元数据微服务
bin/oss_upload_worker  OSS 上传后台 worker
```

第四期的主要问题在 API Gateway 和微服务之间：
网关会根据固定 host/port 创建三个 srpc 客户端。

`CloudDiskServer` 构造函数中会直接创建固定地址的 srpc 客户端：

```cpp
CloudDiskServer::CloudDiskServer()
    : oss_uploader_()
    , auth_client_(AuthServiceHost.c_str(), AuthServicePort)
    , user_client_(UserServiceHost.c_str(), UserServicePort)
    , filemeta_client_(FileMetaServiceHost.c_str(), FileMetaServicePort)
{}
```

这意味着：

```text
1. 服务端口变更时，网关必须同步修改配置。
2. 某个服务实例宕机时，网关无法自动切换到其它实例。
3. 同一个服务即使启动多个实例，网关也只能使用配置中的那个实例。
4. 网关和后端服务仍然没有彻底解耦。
```

## 二、第五期目标架构

引入 Consul 后，架构调整为：

```text
               Consul :8500
             service registry
            /       |        \
           /        |         \
          v         v          v
AuthService     UserService FileMetaService
register + TTL  register    register
  :9001          :9002       :9003
  :9011          :9012       :9013

Browser
  |
  | HTTP
  v
API Gateway :8888
  |
  | 1. discover healthy instance from Consul
  | 2. create srpc client by discovered host/port
  v
AuthService / UserService / FileMetaService

API Gateway
  |
  | publish upload task
  v
RabbitMQ -> OssUploadWorker -> Aliyun OSS
```

请求链路变成：

```text
1. AuthService/UserService/FileMetaService 启动。
2. 服务启动成功后向 Consul 注册实例。
3. 服务周期性向 Consul 上报 TTL 心跳。
4. API Gateway 收到 HTTP 请求。
5. API Gateway 按服务名从 Consul 查询 passing 状态实例。
6. API Gateway 选择一个实例，创建 srpc client，发送 RPC 请求。
7. 如果 Consul 不可用或没有健康实例，网关直接返回内部服务器错误。
```

前端 HTTP 接口不变：

```text
POST /api/v1/auth/register
POST /api/v1/auth/login
GET  /api/v1/user/me
GET  /api/v1/files
POST /api/v1/files
GET  /api/v1/file/{id}
```

Protobuf 业务接口不变：

```text
AuthService.Register
AuthService.Login
AuthService.VerifyToken
UserService.GetUserProfile
FileMetaService.ListFiles
FileMetaService.CreateFile
FileMetaService.GetFileForDownload
```

## 三、服务注册设计

### 1. 注册哪些进程

第五期只注册可被 API Gateway 通过 srpc 调用的后端服务：

```text
AuthService
UserService
FileMetaService
```

暂不注册：

```text
API Gateway
OssUploadWorker
```

原因：

```text
1. API Gateway 当前直接面向浏览器，暂时没有被其它后端服务发现和调用。
2. OssUploadWorker 不监听端口，不提供 RPC 能力，只是 RabbitMQ 消费者。
3. 第五期目标是解决网关调用后端 srpc 服务的硬编码地址问题。
```

后续如果要做网关集群、反向代理、worker 可观测性，再考虑把它们纳入注册中心。

### 2. 服务命名

Consul 中服务名建议和 Protobuf 服务名保持一致：

```text
AuthService
UserService
FileMetaService
```

这样 API Gateway 调用时可以直接按业务服务名发现实例：

```cpp
discovery_.select("AuthService");
discovery_.select("UserService");
discovery_.select("FileMetaService");
```

### 3. 实例 ID

实例 ID 必须唯一。建议格式：

```text
{service_name}-{host}-{port}
```

示例：

```text
AuthService-127.0.0.1-9001
AuthService-127.0.0.1-9011
UserService-127.0.0.1-9002
FileMetaService-127.0.0.1-9003
```

同一个服务启动多个实例时，只要端口不同，就能注册成多个不同实例。

### 4. 注册元数据

每个服务实例向 Consul 注册：

```text
id       实例唯一 ID
name     服务名
address  服务对外可访问地址
port     srpc 监听端口
tags     srpc, cloud-disk
check    TTL 健康检查
```

ppconsul 调用示意：

```cpp
agent.registerService(
    ppconsul::agent::kw::id = service_id,
    ppconsul::agent::kw::name = service_name,
    ppconsul::agent::kw::address = host,
    ppconsul::agent::kw::port = port,
    ppconsul::agent::kw::tags = ppconsul::Tags { "srpc", "cloud-disk" },
    ppconsul::agent::kw::check = ppconsul::agent::TtlCheck { chrono::seconds(ttl_seconds) });
```

### 5. TTL 健康检查

参考 PDF 中的 Consul 示例，使用 TTL 心跳：

```text
TTL:       10 秒
heartbeat: 5 秒
```

服务注册后，每隔 5 秒调用：

```cpp
agent.servicePass(service_id);
```

如果服务进程退出、卡死或网络异常，Consul 在 TTL 超时后会把该实例标记为非健康。API Gateway 查询 passing 实例时，就不会选到它。

### 6. 注销服务

服务正常退出时执行：

```cpp
agent.deregisterService(service_id);
```

这样可以避免 Consul UI 中长期残留已经退出的实例。

如果进程异常崩溃，无法执行注销，Consul 仍会因为 TTL 心跳停止而把实例标记为不健康。

## 四、服务发现设计

### 1. 发现方式

API Gateway 使用 Consul Health API 查询健康实例：

```cpp
ppconsul::health::Health health(consul);
auto instances = health.service(service_name, ppconsul::health::kw::passing = true);
```

不建议使用 Catalog API 直接查服务列表，因为 Catalog 返回的是注册实例，不一定都是健康实例。第五期需要的是“可调用实例”，所以应按健康状态过滤。

### 2. 实例选择策略

第一版建议使用简单轮询：

```text
1. 查询某个服务的健康实例列表。
2. 如果有多个实例，按 round-robin 选择一个。
3. 如果只有一个实例，直接使用。
4. 如果没有实例，返回 500。
```

这样可以验证多实例负载分摊：

```text
AuthService :9001
AuthService :9011
AuthService :9021
```

连续登录或 token 校验请求会轮流打到不同实例。

### 3. 本地缓存

直接每次 HTTP 请求都同步访问 Consul，代码简单但会增加 Consul 压力，也会让 Consul 短暂不可用影响所有请求。

建议 `ServiceDiscovery` 内部增加短 TTL 缓存：

```text
cache ttl: 3 秒
```

流程：

```text
1. select(service_name) 时先看缓存。
2. 缓存存在且未过期，直接从缓存实例列表中轮询。
3. 缓存不存在或过期，重新访问 Consul。
4. Consul 查询成功则刷新缓存。
5. Consul 查询失败或没有可用实例时返回错误。
```

课程项目也可以先实现无缓存版本，确认流程跑通后再加缓存。但设计上建议保留缓存抽象。

## 五、公共组件设计

### 1. 新增文件

建议新增：

```text
src/common/ServiceRegistry.h
src/common/ServiceRegistry.cc
```

该文件同时提供服务注册和服务发现能力，避免 Consul 代码散落在每个 main 和网关业务路由里。

### 2. 基础结构

```cpp
struct ServiceEndpoint {
    std::string host;
    unsigned short port;
};
```

### 3. ServiceRegistrar

给三个 srpc 服务使用。

职责：

```text
1. 读取 Consul 配置。
2. 生成 service_id。
3. 调用 registerService 注册服务。
4. 启动 TTL 心跳。
5. 停止心跳。
6. 正常退出时注销服务。
```

接口建议：

```cpp
class ServiceRegistrar {
public:
    ServiceRegistrar(const std::string& service_name,
                     const std::string& host,
                     unsigned short port);
    ~ServiceRegistrar();

    bool start();
    void stop();

private:
    void heartbeat_loop();
};
```

服务启动中使用：

```cpp
if (server.start(port) == 0) {
    ServiceRegistrar registrar("AuthService", service_host, port);
    registrar.start();

    wait_group.wait();

    registrar.stop();
    server.stop();
}
```

### 4. ServiceDiscovery

给 API Gateway 使用。

职责：

```text
1. 按服务名查询健康实例。
2. 在多个实例中选择一个。
3. 维护短时间缓存。
```

接口建议：

```cpp
class ServiceDiscovery {
public:
    ServiceDiscovery();

    bool select(const std::string& service_name,
                ServiceEndpoint& endpoint);

private:
    bool query_consul(const std::string& service_name,
                      std::vector<ServiceEndpoint>& endpoints);
};
```

网关中使用：

```cpp
ServiceEndpoint endpoint;
if (!discovery_.select("AuthService", endpoint)) {
    response_error(resp, HttpStatusInternalServerError, "内部服务器错误");
    return;
}

cloud::disk::AuthService::SRPCClient client(endpoint.host.c_str(), endpoint.port);
srpc::SRPCClientTask* task = client.create_Login_task(callback);
```

注意：如果 `SRPCClient` 是局部变量，必须确认 srpc task 创建后是否还依赖 client 对象生命周期。更稳妥的实现方式是让创建 task 的辅助函数内部持有 client，或让 `CloudDiskServer` 保留按服务名更新的 client 对象。

推荐的稳妥做法：

```text
1. 封装 create_auth_task/create_user_task/create_filemeta_task。
2. 在封装内部先 discover endpoint。
3. 用 discovered endpoint 构造临时 client 并创建 task。
4. 如确认 srpc task 创建后已经复制连接参数，则可直接返回 task。
5. 如果发现 task 依赖 client 生命周期，则将 client 放入 shared_ptr，并在回调 lambda 捕获 shared_ptr 延长生命周期。
```

第五期实现前应通过一次小测试确认 srpc client 生命周期行为。

## 六、API Gateway 改造点

### 1. 删除固定客户端成员

当前 `CloudDiskServer.h` 中有：

```cpp
cloud::disk::AuthService::SRPCClient auth_client_;
cloud::disk::UserService::SRPCClient user_client_;
cloud::disk::FileMetaService::SRPCClient filemeta_client_;
```

第五期建议改成：

```cpp
ServiceDiscovery discovery_;
```

### 2. 删除构造函数中的固定地址初始化

当前：

```cpp
, auth_client_(AuthServiceHost.c_str(), AuthServicePort)
, user_client_(UserServiceHost.c_str(), UserServicePort)
, filemeta_client_(FileMetaServiceHost.c_str(), FileMetaServicePort)
```

第五期不再初始化固定地址的客户端，也不再保存固定服务地址。
网关会在每次创建 RPC task 前按服务名查询 Consul。

### 3. 替换 RPC task 创建方式

当前：

```cpp
srpc::SRPCClientTask* task = auth_client_.create_Login_task(callback);
```

第五期：

```cpp
ServiceEndpoint endpoint;
if (!discovery_.select("AuthService", endpoint)) {
    response_error(resp, HttpStatusInternalServerError, "内部服务器错误");
    return;
}

auto client = std::make_shared<pb::AuthService::SRPCClient>(
    endpoint.host.c_str(),
    endpoint.port);

srpc::SRPCClientTask* task = client->create_Login_task(
    [client, resp](pb::LoginResponse* rpc_resp, srpc::RPCContext* ctx) {
        // 原有回调逻辑
    });
```

捕获 `client` 是为了确保 task 回调完成前，客户端对象不会提前析构。

### 4. verify_request_async 改造

当前 `verify_request_async` 接收固定的 `AuthService::SRPCClient&`：

```cpp
static void verify_request_async(const HttpReq* req,
                                 HttpResp* resp,
                                 pb::AuthService::SRPCClient& auth_client,
                                 const function<void(pb::UserIdentity)>& next)
```

第五期建议改为接收 `ServiceDiscovery`：

```cpp
static void verify_request_async(const HttpReq* req,
                                 HttpResp* resp,
                                 ServiceDiscovery& discovery,
                                 const function<void(pb::UserIdentity)>& next)
```

内部先发现 `AuthService`，再创建 `VerifyToken` RPC task。

### 5. 业务路由不变

以下路由的请求解析、响应封装、业务 JSON 结构都不变：

```text
register_auth_module()
register_user_module()
register_file_module()
```

只替换“创建 srpc task 前如何获得 client”这一层。

## 十、run.sh 改造

当前 `run.sh` 只检查 RabbitMQ。第五期建议增加 Consul 检查。

### 1. 本地单节点 Consul

课程项目优先支持单节点：

```bash
docker run --name consul1 -d \
  -p 8500:8500 \
  -p 8301:8301 \
  -p 8302:8302 \
  -p 8600:8600 \
  hashicorp/consul agent \
  -server \
  -bootstrap-expect 1 \
  -ui \
  -bind=0.0.0.0 \
  -client=0.0.0.0
```

访问 UI：

```text
http://127.0.0.1:8500/ui
```

### 2. PDF 中三节点 Consul

PDF 第 30 页给出的是三节点方式：

```bash
docker run --name consul1 -d -p 8500:8500 -p 8301:8301 -p 8302:8302 -p 8600:8600 \
hashicorp/consul agent -server -bootstrap-expect 2 -ui -bind=0.0.0.0 -client=0.0.0.0

docker inspect consul1

docker run --name consul2 -d -p 8501:8500 hashicorp/consul agent -server -ui \
-bind=0.0.0.0 -client=0.0.0.0 -join <consul1-container-ip>

docker run --name consul3 -d -p 8502:8500 hashicorp/consul agent -server -ui \
-bind=0.0.0.0 -client=0.0.0.0 -join <consul1-container-ip>
```

课程本地开发不强制三节点。三节点更接近集群演示，单节点更方便调试第五期功能。

### 3. 启动顺序

建议顺序：

```text
1. 加载 .env
2. 检查或启动 RabbitMQ
3. 检查或启动 Consul
4. 启动 auth_service
5. 启动 user_service
6. 启动 filemeta_service
7. 启动 oss_upload_worker
8. 等待 1-2 秒，让服务注册和首次心跳完成
9. 前台启动 API Gateway
```

Consul 是第五期必需依赖。
如果 Consul 未 ready，`run.sh` 直接退出，不启动后端服务。

## 十一、异常场景处理

### 1. Consul 启动失败

```text
1. run.sh 在启动业务进程前检查 Consul。
2. 如果 Consul 未 ready，run.sh 直接退出。
3. 如果服务运行期间 Consul 不可用，服务发现失败时网关返回 500。
4. 如果微服务启动时注册 Consul 失败，该微服务启动失败。
```

### 2. 服务实例宕机

```text
1. 实例停止发送 TTL 心跳。
2. Consul 在 TTL 超时后将实例标记为 critical。
3. 网关查询 passing 实例时不再选中它。
4. 如果有其它健康实例，请求继续成功。
5. 如果没有健康实例，网关返回 500。
```

### 3. 服务正常退出

```text
1. 收到 Ctrl+C。
2. wait_group.wait() 返回。
3. registrar.stop() 停止心跳。
4. deregisterService(service_id) 注销实例。
5. server.stop() 停止 srpc 服务。
```

### 4. 网关缓存过期前实例已经宕机

短缓存可能导致网关在几秒内仍调用旧实例。

处理策略：

```text
1. 缓存 TTL 设置短一点，例如 3 秒。
2. RPC 失败时可以清理对应服务缓存。
3. 下一次请求重新从 Consul 拉取健康实例。
```

第一版可以只做短缓存，不做 RPC 失败主动摘除；后续再增强。

## 十二、验证方案

### 1. 基础启动验证

启动 Consul：

```bash
docker start consul1
```

启动项目：

```bash
./build.sh
./run.sh
```

查看 Consul UI：

```text
http://127.0.0.1:8500/ui
```

应看到：

```text
AuthService      passing
UserService      passing
FileMetaService  passing
```

### 2. 注册和登录验证

```bash
curl -X POST http://127.0.0.1:8888/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"u1","password":"123","confirm":"123"}'

curl -X POST http://127.0.0.1:8888/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"u1","password":"123"}'
```

预期：

```text
1. 网关从 Consul 发现 AuthService。
2. 登录注册响应和第四期一致。
```

### 3. 多实例验证

手动启动多个 AuthService：

```bash
AUTH_SERVICE_PORT=9001 ./bin/auth_service
AUTH_SERVICE_PORT=9011 ./bin/auth_service
```

Consul UI 中应看到两个 `AuthService` 实例。

连续请求登录接口，服务端日志应能看到请求分布到不同实例。

### 4. 故障转移验证

```text
1. 启动两个 AuthService 实例。
2. 停掉其中一个实例。
3. 等待超过 CONSUL_TTL_SECONDS。
4. Consul UI 中该实例变为 critical 或消失。
5. 再次登录，网关应选择仍然 passing 的实例。
```

### 5. Consul 必需依赖验证

设置：

```env
CONSUL_HTTP_ADDR=http://127.0.0.1:18500
```

即 Consul 地址故意写错。

预期：

```text
1. run.sh 检查 Consul 失败。
2. 项目不继续启动业务服务。
3. 终端打印 Consul service is not ready 相关错误。
```

## 十三、实施步骤

建议按以下顺序实现，便于逐步验证：

```text
1. 新增 ServiceRegistry.h/.cc，先实现读取 Consul 配置和 ServiceEndpoint。
2. 实现 ServiceRegistrar，接入 AuthServiceMain.cc。
3. 启动 AuthService，确认 Consul UI 能看到 AuthService passing。
4. 把 ServiceRegistrar 接入 UserServiceMain.cc 和 FileMetaServiceMain.cc。
5. 实现 ServiceDiscovery，先不加缓存，只查 passing 实例。
6. 改造 API Gateway 的 AuthService 调用，验证注册、登录、VerifyToken。
7. 改造 UserService 和 FileMetaService 调用，验证用户信息、文件列表、上传、下载。
8. 增加短 TTL 缓存和 round-robin。
9. 修改 CMakeLists.txt 链接 ppconsul。
10. 修改 .env 和 run.sh。
11. 编写第五期 README 或补充本文档中的运行说明。
```

## 十四、边界和后续扩展

```text

```

## 十五、结论

第五期引入 Consul 后，CloudDisk 的微服务调用关系从“网关固定知道后端地址”变成“服务主动注册、网关按服务名发现健康实例”。

这次改造的核心收益：

```text
1. 去掉 API Gateway 对后端服务地址的硬编码依赖。
2. 支持同一服务多实例部署。
3. 服务宕机后可以通过健康检查自动摘除。
4. 为后续配置中心、网关集群、服务治理继续铺路。
```

推荐落地策略是：

```text
Consul 强制依赖；
TTL 心跳检查；
passing 实例发现；
公共组件封装；
业务代码少改。
```
