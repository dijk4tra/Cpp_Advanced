# CloudDisk 第四期：微服务架构设计文档&改造方案

本文档基于第三期 `CloudDisk` 当前代码和《Web网盘项目.pdf》第 21-29 页的第四期内容，说明如何把现有单体 Web 网盘改造成基于 srpc + Protobuf 的微服务架构。

第四期目标不是把所有代码都拆成服务，而是按职责边界拆分：

1. API Gateway 继续负责 HTTP、静态资源、请求解析、响应封装、文件上传下载字节流。
2. 注册、登录、用户信息、文件元数据改造成独立 srpc 微服务。
3. RabbitMQ + OSS 上传消费者从网关进程中移出，作为独立后台 worker。
4. 网关通过 srpc 异步任务与 Workflow 集成，不在 HTTP 请求线程中做同步阻塞调用。

---

## 一、当前第三期代码职责分析

第三期代码集中在 `CloudDiskServer.cc` 中，虽然已经把 OSS 和 RabbitMQ 封装成了 `OssStorage`、`RabbitMqOssUploader`，但整体仍然是一个单体应用。

当前主要职责如下：

```text
CloudDiskServer
  - 静态资源服务
  - HTTP 路由注册
  - JSON / multipart/form-data / path 参数解析
  - Bearer Token 解析和 JWT 校验
  - 注册、登录业务
  - 用户信息接口
  - 文件列表、上传元数据、下载元数据查询
  - RabbitMQ 上传任务发布
  - RabbitMQ 后台消费线程
  - OSS 上传、下载编排
  - HTTP JSON 响应和文件下载响应
```

当前 HTTP 接口：

```text
GET  /
GET  /static/*

POST /api/v1/auth/register
POST /api/v1/auth/login
GET  /api/v1/user/me
GET  /api/v1/files
POST /api/v1/files
GET  /api/v1/file/{id}
```

第四期改造后，浏览器仍然只访问 API Gateway，前端接口地址不需要变化。

## 二、微服务拆分边界

### 1. API Gateway

API Gateway 不改造成 srpc 服务。它仍然是对浏览器暴露的 HTTP 服务，监听 `8888`。

保留职责：

```text
1. 静态资源服务
   - /
   - /static/*

2. HTTP 路由
   - /api/v1/auth/register
   - /api/v1/auth/login
   - /api/v1/user/me
   - /api/v1/files
   - /api/v1/file/{id}

3. HTTP 请求解析
   - JSON body
   - multipart/form-data
   - Authorization: Bearer ...
   - path 参数

4. HTTP 响应封装
   - 统一 JSON 响应
   - 下载文件时设置 Content-Type
   - 下载文件时设置 Content-Disposition

5. 文件字节流处理
   - 上传时接收 multipart 文件内容
   - 计算文件 hashcode
   - 保存临时文件
   - 下载时从 OSS 读取内容并写入 HTTP 响应

6. 任务投递
   - 文件元数据创建成功后发布 RabbitMQ 上传任务
```

不放入 API Gateway 的职责：

```text
1. tbl_user 的注册、登录 SQL
2. 密码 salt/hash 业务
3. JWT 生成和校验的核心逻辑
4. tbl_file 的增删查改 SQL
5. RabbitMQ 后台消费线程
6. OSS 异步上传 worker
```

### 2. AuthService

独立 srpc 服务，建议监听 `9001`。

职责：

```text
1. 注册用户
2. 登录用户
3. 生成 JWT
4. 校验 JWT
5. 管理密码 salt/hash 逻辑
6. 访问 tbl_user
```

对应当前代码：

```text
POST /api/v1/auth/register
POST /api/v1/auth/login
check_login() 中的 JWT 校验逻辑
CryptoUtil::generate_salt()
CryptoUtil::hash_password()
CryptoUtil::generate_token()
CryptoUtil::verify_token()
```

说明：

```text
API Gateway 仍然负责从 HTTP Header 中取出 Bearer Token。
但 Token 是否有效、Token 对应哪个用户，由 AuthService.VerifyToken 判断。
```

### 3. UserService

独立 srpc 服务，建议监听 `9002`。

职责：

```text
1. 查询当前用户资料
2. 后续扩展用户资料修改、头像、空间容量等用户相关能力
3. 访问 tbl_user
```

对应当前接口：

```text
GET /api/v1/user/me
```

第三期中 `/user/me` 直接从 JWT claims 还原用户信息，不查数据库。第四期改造成独立 `UserService` 后，建议按 `uid` 查询 `tbl_user`，这样可以确认用户未被逻辑删除，并返回数据库中的最新信息。

### 4. FileMetaService

独立 srpc 服务，建议监听 `9003`。

职责：

```text
1. 查询当前用户文件列表
2. 创建文件元数据
3. 查询下载所需元数据
4. 访问 tbl_file
```

对应当前代码：

```text
GET  /api/v1/files
POST /api/v1/files 中 INSERT tbl_file 部分
GET  /api/v1/file/{id} 中 SELECT filename, hashcode 部分
```

不负责：

```text
1. 不解析 multipart/form-data
2. 不保存临时文件
3. 不发布 RabbitMQ 消息
4. 不调用 OSS
5. 不返回文件字节流
```

### 5. OssUploadWorker

独立后台进程，不是 srpc 服务，建议无监听端口。

职责：

```text
1. 连接 RabbitMQ
2. 消费 oss.queue
3. 读取消息中的 uid/hashcode/tempPath
4. 从 tempPath 读取临时文件
5. 调用 OssStorage::upload_object()
6. 上传成功后 ack 消息并删除临时文件
7. 上传失败时 reject 并重新入队
```

对应当前代码：

```text
RabbitMqOssUploader::worker_loop()
OssStorage::upload_object()
```

注意：

```text
第四期如果仍然使用 tempPath，API Gateway 和 OssUploadWorker 必须运行在同一台机器上，或者共享同一个临时目录挂载。

如果后续部署到多台机器，RabbitMQ 消息不能只传本地 tempPath，应改为：
1. 网关先把文件放到共享存储；
2. 或网关先上传到 OSS 临时对象；
3. 或浏览器使用预签名 URL 直传 OSS；
4. 消息中传递共享对象 key，而不是本地文件路径。
```

## 三、第四期整体架构

```text
Browser
  |
  | HTTP
  v
API Gateway :8888
  |
  | srpc
  +--> AuthService     :9001  -> tbl_user
  |
  | srpc
  +--> UserService     :9002  -> tbl_user
  |
  | srpc
  +--> FileMetaService :9003  -> tbl_file
  |
  | publish task
  v
RabbitMQ
  |
  | consume task
  v
OssUploadWorker
  |
  | PutObject
  v
Aliyun OSS

API Gateway
  |
  | GetObject
  v
Aliyun OSS
```

为什么下载仍然由网关同步读 OSS：

```text
下载接口必须在本次 HTTP 响应中返回文件字节。
如果下载也改成 RabbitMQ 异步任务，浏览器无法立即拿到文件内容。
所以 FileMetaService 只返回 filename/hashcode，真正的 OSS GetObject 和 HTTP 文件响应仍然由 API Gateway 完成。
```

## 四、Protobuf / srpc 接口设计

建议把 `.proto` 放在：

```text
CloudDisk/proto/common.proto
CloudDisk/proto/auth.proto
CloudDisk/proto/user.proto
CloudDisk/proto/filemeta.proto
```

也可以先放在同一个 `cloud_disk.proto` 中，降低第四期实现复杂度。下面按多个 proto 文件展示。

### 1. common.proto

```proto
syntax = "proto3";

package cloud.disk;

message CommonResult {
  int32 code = 1;
  string message = 2;
}

message UserIdentity {
  int32 user_id = 1;
  string username = 2;
  string created_at = 3;
}
```

`CommonResult.code` 建议约定：

```text
0    OK
400  请求参数错误
401  未登录或 token 无效
404  资源不存在
409  资源冲突，例如用户名已存在
500  服务内部错误
```

这样网关可以直接把业务 code 映射成 HTTP status。

### 2. auth.proto

```proto
syntax = "proto3";

package cloud.disk;

import "common.proto";

message RegisterRequest {
  string username = 1;
  string password = 2;
}

message RegisterResponse {
  CommonResult result = 1;
  int32 user_id = 2;
  string username = 3;
}

message LoginRequest {
  string username = 1;
  string password = 2;
}

message LoginResponse {
  CommonResult result = 1;
  string access_token = 2;
  string token_type = 3;
  UserIdentity user = 4;
}

message VerifyTokenRequest {
  string access_token = 1;
}

message VerifyTokenResponse {
  CommonResult result = 1;
  UserIdentity user = 2;
}

service AuthService {
  rpc Register(RegisterRequest) returns (RegisterResponse);
  rpc Login(LoginRequest) returns (LoginResponse);
  rpc VerifyToken(VerifyTokenRequest) returns (VerifyTokenResponse);
}
```

说明：

```text
RegisterRequest 不包含 confirm。
confirm 是 HTTP 表单层字段，只用于网关判断两次输入是否一致。
真正发给 AuthService 的请求只需要 username/password。
```

### 3. user.proto

```proto
syntax = "proto3";

package cloud.disk;

import "common.proto";

message GetUserProfileRequest {
  int32 user_id = 1;
}

message GetUserProfileResponse {
  CommonResult result = 1;
  UserIdentity user = 2;
}

service UserService {
  rpc GetUserProfile(GetUserProfileRequest) returns (GetUserProfileResponse);
}
```

说明：

```text
UserService 不接收 access_token。
认证由网关通过 AuthService.VerifyToken 完成。
网关拿到 user_id 后，再调用 UserService.GetUserProfile。
```

### 4. filemeta.proto

```proto
syntax = "proto3";

package cloud.disk;

import "common.proto";

message FileInfo {
  int32 file_id = 1;
  string filename = 2;
  int64 size = 3;
  string created_at = 4;
  string updated_at = 5;
}

message ListFilesRequest {
  int32 user_id = 1;
}

message ListFilesResponse {
  CommonResult result = 1;
  repeated FileInfo files = 2;
}

message CreateFileRequest {
  int32 user_id = 1;
  string filename = 2;
  string hashcode = 3;
  int64 size = 4;
}

message CreateFileResponse {
  CommonResult result = 1;
  int32 file_id = 2;
  string filename = 3;
}

message GetFileForDownloadRequest {
  int32 user_id = 1;
  int32 file_id = 2;
}

message GetFileForDownloadResponse {
  CommonResult result = 1;
  string filename = 2;
  string hashcode = 3;
}

service FileMetaService {
  rpc ListFiles(ListFilesRequest) returns (ListFilesResponse);
  rpc CreateFile(CreateFileRequest) returns (CreateFileResponse);
  rpc GetFileForDownload(GetFileForDownloadRequest) returns (GetFileForDownloadResponse);
}
```

## 五、srpc 代码生成方式

以 `auth.proto` 为例：

```bash
protoc --cpp_out=./generated proto/common.proto proto/auth.proto
srpc_generator protobuf proto/auth.proto ./generated
```

会生成类似文件：

```text
generated/common.pb.h
generated/common.pb.cc
generated/auth.pb.h
generated/auth.pb.cc
generated/auth.srpc.h
generated/client.pb_skeleton.cc
generated/server.pb_skeleton.cc
```

实际项目中建议每个服务放到独立目录，避免多个 `client.pb_skeleton.cc`、`server.pb_skeleton.cc` 文件互相覆盖：

```text
CloudDisk/
  proto/
    common.proto
    auth.proto
    user.proto
    filemeta.proto

  gateway/
    main.cc
    ApiGatewayServer.h
    ApiGatewayServer.cc

  services/
    auth/
      AuthServiceImpl.h
      AuthServiceImpl.cc
      main.cc
    user/
      UserServiceImpl.h
      UserServiceImpl.cc
      main.cc
    filemeta/
      FileMetaServiceImpl.h
      FileMetaServiceImpl.cc
      main.cc

  worker/
    OssUploadWorker.cc

  common/
    CryptoUtil.h
    CryptoUtil.cc
    OssStorage.h
    OssStorage.cc
    RabbitMqTaskPublisher.h
    RabbitMqTaskPublisher.cc
```

## 六、API Gateway 如何调用 srpc

srpc 生成的客户端通常提供三种调用方式：

```cpp
client.Method(&req, callback);                 // 异步回调
client.Method(&req, &resp, &sync_ctx);          // 同步阻塞
client.create_Method_task(callback);            // Workflow task
```

在 API Gateway 中推荐使用第三种：`create_Method_task()`。

原因：

```text
1. wfrest 本身基于 Workflow。
2. 当前 MySQL 调用已经是异步回调风格。
3. 同步阻塞会占用 HTTP 服务线程，降低并发能力。
4. Workflow task 可以和其它 task 串联或并联，适合“先验 token，再调业务服务”的链路。
```

### 1. 注册接口调用方式

HTTP：

```text
POST /api/v1/auth/register
```

网关流程：

```text
1. 检查 Content-Type 是否为 application/json
2. 解析 username/password/confirm
3. 检查字段为空、两次密码是否一致
4. 构造 RegisterRequest
5. 创建 AuthService.Register srpc task
6. 在回调中把 RegisterResponse 转成 HTTP JSON
```

伪代码：

```cpp
server_.POST("/api/v1/auth/register", [this](const HttpReq *req, HttpResp *resp) {
    // 1. HTTP 层参数检查
    // 2. 构造 RegisterRequest

    auto *task = auth_client_.create_Register_task(
        [resp](RegisterResponse *rpc_resp, srpc::RPCContext *ctx) {
            if (!ctx->success()) {
                response_error(resp, 500, "内部服务器错误");
                return;
            }

            int code = rpc_resp->result().code();
            if (code != 0) {
                response_error(resp, code, rpc_resp->result().message());
                return;
            }

            json data;
            data["userId"] = rpc_resp->user_id();
            data["username"] = rpc_resp->username();
            response_success(resp, 201, "注册成功", data);
        });

    RegisterRequest rpc_req;
    rpc_req.set_username(username);
    rpc_req.set_password(password);
    task->serialize_input(&rpc_req);
    task->start();
});
```

### 2. 登录接口调用方式

HTTP：

```text
POST /api/v1/auth/login
```

网关流程：

```text
1. 解析 JSON
2. 构造 LoginRequest
3. 调用 AuthService.Login
4. 把 access_token/token_type/user 转成当前前端需要的 JSON
```

### 3. 认证过滤流程

受保护接口包括：

```text
GET  /api/v1/user/me
GET  /api/v1/files
POST /api/v1/files
GET  /api/v1/file/{id}
```

这些接口都需要先调用 `AuthService.VerifyToken`。

通用流程：

```text
1. 网关从 Authorization Header 解析 Bearer Token
2. 构造 VerifyTokenRequest
3. 调用 AuthService.VerifyToken
4. 成功后得到 user_id/username/created_at
5. 再继续调用 UserService 或 FileMetaService
```

### 4. Workflow 串联调用

以 `/api/v1/user/me` 为例，需要两个 RPC：

```text
AuthService.VerifyToken
  -> UserService.GetUserProfile
  -> HTTP JSON response
```

可以用 Workflow 的串行任务思路：

```text
SeriesWork
  task1: VerifyToken
  task2: GetUserProfile
```

简单实现时，也可以在 `VerifyToken` 回调中创建并启动 `GetUserProfile` task。

伪代码：

```cpp
auto *verify_task = auth_client_.create_VerifyToken_task(
    [this, resp](VerifyTokenResponse *verify_resp, srpc::RPCContext *ctx) {
        if (!ctx->success() || verify_resp->result().code() != 0) {
            response_error(resp, 401, "无效的访问令牌");
            return;
        }

        int user_id = verify_resp->user().user_id();

        auto *profile_task = user_client_.create_GetUserProfile_task(
            [resp](GetUserProfileResponse *profile_resp, srpc::RPCContext *ctx) {
                if (!ctx->success()) {
                    response_error(resp, 500, "内部服务器错误");
                    return;
                }

                if (profile_resp->result().code() != 0) {
                    response_error(resp,
                                   profile_resp->result().code(),
                                   profile_resp->result().message());
                    return;
                }

                json data;
                data["userId"] = profile_resp->user().user_id();
                data["username"] = profile_resp->user().username();
                data["createdAt"] = profile_resp->user().created_at();
                response_success(resp, 200, "获取个人信息成功", data);
            });

        GetUserProfileRequest profile_req;
        profile_req.set_user_id(user_id);
        profile_task->serialize_input(&profile_req);
        profile_task->start();
    });
```

### 5. 文件上传流程

HTTP：

```text
POST /api/v1/files
```

网关流程：

```text
1. VerifyToken
2. 解析 multipart/form-data
3. 获取 filename/content
4. 计算 hashcode
5. 保存临时文件 tempPath
6. 调用 FileMetaService.CreateFile
7. CreateFile 成功后发布 RabbitMQ 任务
8. 返回上传成功
```

为什么 RabbitMQ 发布仍留在网关：

```text
当前消息体包含 tempPath，而 tempPath 是网关本地生成的临时文件路径。
如果让 FileMetaService 发布 RabbitMQ，它可能无法访问网关机器上的 tempPath。
所以第四期先由网关在 CreateFile 成功后发布任务。
```

### 6. 文件下载流程

HTTP：

```text
GET /api/v1/file/{id}
```

网关流程：

```text
1. VerifyToken
2. 获取 path 参数 file_id
3. 调用 FileMetaService.GetFileForDownload
4. 得到 filename/hashcode
5. 网关调用 OssStorage::download_object(user_id, hashcode, content)
6. 设置 Content-Disposition
7. 返回文件字节
```

## 七、各服务内部实现方案

### 1. AuthServiceImpl

继承 srpc 生成的服务基类：

```cpp
class AuthServiceImpl : public cloud::disk::AuthService::Service {
public:
    void Register(RegisterRequest *request,
                  RegisterResponse *response,
                  srpc::RPCContext *ctx) override;

    void Login(LoginRequest *request,
               LoginResponse *response,
               srpc::RPCContext *ctx) override;

    void VerifyToken(VerifyTokenRequest *request,
                     VerifyTokenResponse *response,
                     srpc::RPCContext *ctx) override;
};
```

`Register` 内部逻辑：

```text
1. 校验 username/password
2. generate_salt()
3. hash_password()
4. INSERT tbl_user
5. 成功返回 user_id/username
6. 用户名重复返回 code=409
```

`Login` 内部逻辑：

```text
1. SELECT tbl_user
2. 校验 password hash
3. generate_token()
4. 返回 access_token/token_type/user
5. 用户名或密码错误返回 code=401
```

`VerifyToken` 内部逻辑：

```text
1. verify_token()
2. token 无效或过期返回 code=401
3. token 有效返回 UserIdentity
```

### 2. UserServiceImpl

```cpp
class UserServiceImpl : public cloud::disk::UserService::Service {
public:
    void GetUserProfile(GetUserProfileRequest *request,
                        GetUserProfileResponse *response,
                        srpc::RPCContext *ctx) override;
};
```

内部逻辑：

```text
1. 根据 user_id 查询 tbl_user
2. 条件包含 tomb=0
3. 返回 user_id/username/created_at
4. 查不到返回 code=404
```

### 3. FileMetaServiceImpl

```cpp
class FileMetaServiceImpl : public cloud::disk::FileMetaService::Service {
public:
    void ListFiles(ListFilesRequest *request,
                   ListFilesResponse *response,
                   srpc::RPCContext *ctx) override;

    void CreateFile(CreateFileRequest *request,
                    CreateFileResponse *response,
                    srpc::RPCContext *ctx) override;

    void GetFileForDownload(GetFileForDownloadRequest *request,
                            GetFileForDownloadResponse *response,
                            srpc::RPCContext *ctx) override;
};
```

`ListFiles`：

```text
SELECT id, filename, size, created_at, last_update
FROM tbl_file
WHERE uid = ?
ORDER BY last_update DESC, id DESC;
```

`CreateFile`：

```text
INSERT INTO tbl_file (uid, filename, hashcode, size)
VALUES (?, ?, ?, ?);
```

`GetFileForDownload`：

```text
SELECT filename, hashcode
FROM tbl_file
WHERE id = ? AND uid = ?
LIMIT 1;
```

## 八、数据库归属

第四期可以先继续共用一个 MySQL 数据库：

```text
CloudDisk
  tbl_user
  tbl_file
```

服务访问表：

```text
AuthService     -> tbl_user
UserService     -> tbl_user
FileMetaService -> tbl_file
```

这不是最严格的微服务数据库隔离，但适合第四期课程改造。

后续更严格的方向：

```text
AuthService 拥有 auth_user 表
UserService 拥有 user_profile 表
FileMetaService 拥有 file_meta 表
服务之间不直接访问彼此的数据表
```

第四期重点是进程拆分、RPC 通信和网关编排，不建议一开始就引入复杂的数据拆库。

## 九、错误处理和 HTTP 映射

服务内部统一返回：

```text
CommonResult {
  code
  message
}
```

网关映射规则：

```text
RPC 网络失败 / ctx->success() == false
  -> HTTP 500
  -> {"status":"error","message":"内部服务器错误"}

CommonResult.code == 0
  -> HTTP 成功状态
  -> {"status":"success","message":"...","data":...}

CommonResult.code != 0
  -> HTTP 使用 code 对应状态
  -> {"status":"error","message": CommonResult.message}
```

建议错误消息保持与第三期一致，避免前端行为变化：

```text
请求格式有误
用户名和密码不能为空
两次输入的密码不一致
用户名已存在
用户名或密码错误
无效的访问令牌
获取个人信息成功
获取文件列表成功
上传成功
文件不存在
内部服务器错误
```

### 1. 注册

```text
Browser
  -> POST /api/v1/auth/register
  -> API Gateway 解析 JSON / 检查 confirm
  -> AuthService.Register
  -> tbl_user
  -> API Gateway 返回 JSON
```

### 2. 登录

```text
Browser
  -> POST /api/v1/auth/login
  -> API Gateway 解析 JSON
  -> AuthService.Login
  -> tbl_user
  -> AuthService 生成 JWT
  -> API Gateway 返回 accessToken
```

### 3. 当前用户

```text
Browser
  -> GET /api/v1/user/me
  -> API Gateway 解析 Bearer Token
  -> AuthService.VerifyToken
  -> UserService.GetUserProfile
  -> API Gateway 返回用户信息
```

### 4. 文件列表

```text
Browser
  -> GET /api/v1/files
  -> API Gateway 解析 Bearer Token
  -> AuthService.VerifyToken
  -> FileMetaService.ListFiles
  -> API Gateway 返回文件列表
```

### 5. 上传

```text
Browser
  -> POST /api/v1/files
  -> API Gateway 解析 Bearer Token
```

## 十三、风险和注意事项

### 1. 不要在网关里用同步 RPC

同步调用写法简单，但会阻塞 HTTP 处理线程。

```cpp
client.Login(&req, &resp, &sync_ctx);
```

第四期应使用：

```cpp
auto *task = client.create_Login_task(callback);
task->serialize_input(&req);
task->start();
```

### 2. 注意 HttpResp 生命周期

网关在 srpc 回调中写 `HttpResp`，要保证当前框架允许异步回调完成响应。当前第三期已经通过 `resp->MySQL(...)` 在 MySQL 异步回调里写响应，说明项目本身就是按异步响应方式组织的。srpc task 应沿用这个模式。

### 3. tempPath 的部署约束

只要 RabbitMQ 消息仍然传 `tempPath`，就要求：

```text
API Gateway 写入的临时文件，OssUploadWorker 必须能读到。
```

本地课程项目中可以用同机同目录解决。生产架构中需要换成共享对象 key。

### 4. 上传成功不等于 OSS 已完成

第三期已经存在这个行为：

```text
文件元数据创建成功 + RabbitMQ 投递成功 -> HTTP 返回上传成功
```

但此时 OSS 对象可能仍在后台上传。

更完整的生产方案应给 `tbl_file` 增加：

```text
status: pending / ready / failed
```

第四期为了聚焦微服务，不强制修改表结构。

### 5. 服务地址先硬编码，注册中心放到第五期

第四期先用配置项：

```text
127.0.0.1:9001
127.0.0.1:9002
127.0.0.1:9003
```

第五期再接 Consul，解决服务发现和多实例问题。

## 十四、最终拆分结果

第四期完成后，代码职责应变成：

```text
API Gateway
  - HTTP
  - 静态资源
  - 参数解析
  - 响应封装
  - 文件上传下载字节流
  - 调用 srpc
  - 发布 RabbitMQ 上传任务

AuthService
  - 注册
  - 登录
  - JWT 生成
  - JWT 校验
  - tbl_user 认证相关访问

UserService
  - 当前用户资料
  - 用户信息扩展能力
  - tbl_user 用户资料相关访问

FileMetaService
  - 文件列表
  - 文件元数据创建
  - 下载元数据查询
  - tbl_file 访问

OssUploadWorker
  - RabbitMQ 消费
  - OSS 异步上传
  - 临时文件清理

OssStorage
  - OSS SDK 生命周期
  - PutObject
  - GetObject
```

这个拆分既符合第四期微服务主题，也保留了 Web 网盘项目的关键现实边界：HTTP 网关处理浏览器协议和文件字节流，后端微服务处理业务数据和业务规则。
