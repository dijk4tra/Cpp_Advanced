#### 2. 新增分片 LRU + TTL 本地缓存

新增文件：

```text
include/cache/ShardedLruCache.h
src/cache/ShardedLruCache.cc
```

实现能力：

- 总容量限制。
- 分片缓存。
- 分片数量会限制为不超过总容量，避免实际可缓存条目数超过配置容量。
- 每个分片独立 `std::mutex`。
- 每个分片独立 `std::list` + `std::unordered_map`。
- `get()` 命中后移动到 LRU 链表头部。
- `put()` 超容量后淘汰最久未访问节点。
- 支持 TTL。
- 支持 `ttlSeconds <= 0` 表示不过期。
- `erase()` 支持删除指定 key。

分片选择逻辑：

```text
shard_index = hash(key) % shard_count
```

该实现为后续多 muduo 工作线程并发访问缓存做准备，避免所有请求争抢同一把全局锁。

#### 3. 新增 CachedSearchService

新增文件：

```text

src/cache/CachedSearchService.cc
```

提供接口：

```cpp
std::string suggest(const std::string& query,
                    const std::string& lang,
                    int topK);

std::string search(const std::string& query,
                   int topK);
```

内部流程：

```text
构造缓存 key
  -> 查询缓存
      -> 命中：直接返回 JSON
      -> 未命中：调用 KeywordRecommender 或 WebSearcher
          -> 写入缓存
          -> 返回 JSON
```

当前缓存对象：

- 关键词推荐最终 JSON。
- 网页搜索最终 JSON。

当前 key 设计：

```text
v:{cache_version}:suggest:{lang}:{topK}:{query_length}:{query}
v:{cache_version}:search:{topK}:{abstract_length}:{query_length}:{query}
```

当前还实现了：

- query 首尾空白裁剪。
- query 内连续 ASCII 空白压缩为一个空格。
- 关键词推荐 lang 自动归一为 `cn` 或 `en`。
- `topK <= 0` 时按原业务默认值处理：关键词推荐 10，网页搜索 33。
- 空 `results` 的 JSON 使用较短 TTL。

## 2026-06-26-23:00：补充网页库按需读取与细粒度缓存

### 背景

用户指出 `项目第三期缓存改造流程.md` 遗漏了“把网页库改为按需从文件读取，并为文档展示信息和动态摘要片段添加缓存机制”。该判断成立。

原第二期实现中，`PageLibrary::load()` 会根据 `offsets.dat` 遍历 `pages.dat`，把所有 `<doc>` 解析成 `documents_` 哈希表。这样在线进程会常驻保存全部网页正文；当网页库规模增长时，内存占用会线性扩大。第三期既然引入缓存，更合理的方式是：

```text
offsets_ 常驻内存
pages.dat 按需读取
热点 Document / Abstract 进入缓存
```

### PageLibrary 改造

修改文件：

```text
include/online/PageLibrary.h
src/online/PageLibrary.cc
```

改造前：

```text
load()
  -> 读取 offsets.dat
  -> 遍历 pages.dat
  -> 解析所有 <doc>
  -> 存入 documents_

find(docId)
  -> 从 documents_ 哈希表返回 Document*
```

改造后：

```text
load()
  -> 验证 pages.dat 可读
  -> 保存 pagesFile_
  -> 只加载 offsets.dat

find(docId, Document& doc)
  -> 查 offsets_
  -> 打开 pages.dat
  -> seek 到 offset
  -> 读取 length 字节
  -> parse_document()
  -> 输出 Document
```

关键变化：

- 删除 `documents_` 全量文档内存表。
- `size()` 改为返回 `offsets_.size()`。
- `find()` 改为 `bool find(int docId, Document& doc) const`，避免返回按需读取产生的临时对象指针。
- `offsets_` 和 `pagesFile_` 在加载完成后只读，按需读取时每次使用独立 `std::ifstream`，多线程之间不会共享文件流状态。

### Redis L2 实现

新增文件：

```text
include/cache/RedisCache.h
src/cache/RedisCache.cc
include/cache/TwoLevelCache.h
src/cache/TwoLevelCache.cc
```

`RedisCache` 实现：

- 不依赖 hiredis 等第三方 Redis 客户端。
- 使用最小 RESP 协议实现本项目需要的命令：
  - `GET`
  - `SET`
  - `SETEX`
  - `DEL`
  - `SELECT`
- 每次命令使用短连接，避免多线程共享 Redis 连接的复杂状态。
- 支持连接超时和命令读写超时。
- Redis 失败、超时、协议解析异常都会被视为缓存未命中或写入失败，不向搜索主流程抛出。

`TwoLevelCache` 实现：

```text
get(key)
  -> 查 L1
  -> L1 未命中查 L2 Redis
  -> L2 命中后回填 L1

put(key, value, ttl)
  -> 写 L1
  -> 写 L2 Redis

erase(key)
  -> 删除 L1
  -> 删除 L2 Redis
```

## 2026-06-27-13:48：第九阶段简化 W-TinyLFU

### 阶段结论

第九阶段选择实现简化 W-TinyLFU，而不是只实现 SLRU。原因是该结构已经包含下一阶段完整 W-TinyLFU 所需的 Window、Main SLRU 和 Admission Policy；下一阶段只需重点替换频率估计器，不需要再次调整 L1 的主体数据结构。

### 核心实现

- 按 key 哈希分片，每个分片独立持有互斥锁，保持原 L1 的并发模型。
- 每个分片包含 Window LRU、Main Probation 和 Main Protected 三条链表。
- 新 key 先进入 Window，Window 尾部候选再尝试进入 Main。
- Main 未满时直接接纳候选；Main 已满时，将候选与 Probation 尾部 victim 比较访问频率。
- 候选频率必须严格高于 victim 才准入；频率相同保留旧数据，以抵抗一次性扫描。
- Probation 命中后晋升 Protected，Protected 超限时将 LRU 尾部降级回 Probation。
- 保留 TTL 惰性清理、显式删除和总容量约束。
- 当前使用精确频率哈希表，每达到“分片容量 × 采样倍数”次访问后计数减半，并删除衰减为 0 的冷 key。
- 增加命中、未命中、准入、拒绝、淘汰和过期统计快照，便于后续基准测试。

### 配置和兼容性

## 2026-06-27-14:06：第十阶段完整 W-TinyLFU

### 阶段目标

在第九阶段已有 Window LRU、Main SLRU 和 Admission Policy 基础上，将按 key 增长的精确频率哈希表替换为固定空间概率型估计器，完成改造流程要求的 Count-Min Sketch、Doorkeeper 和 Frequency Aging。

### 新增文件

```text
include/cache/TinyLfuFrequencySketch.h
src/cache/TinyLfuFrequencySketch.cc
tests/cache_policy_benchmark.cc
```

### Count-Min Sketch

- 固定使用 4 行计数器，每行使用不同种子扰动 key 哈希值。
- 查询频率时取 4 个计数器的最小值，降低哈希碰撞导致的高估。
- 每个计数器为 4 bit，两个计数器打包在一个字节中。
- 计数器最大值为 15，达到上限后饱和，不发生整数回绕。
- 每行宽度约为分片容量的两倍并向上取 2 的幂，可使用位与代替取模。

### Doorkeeper

- 使用固定大小 Bloom Filter，每个 key 设置两个哈希 bit。
- 采样周期内第一次访问只写 Doorkeeper，不写 Count-Min Sketch。
- 从第二次访问开始才增加 Sketch，避免大量一次性 query 污染频率统计。
- `estimate()` 返回 Sketch 最小计数加 Doorkeeper 的首次访问证据，范围为 0 到 16。

### Frequency Aging

- 每累计“分片容量 × `l1_wtinylfu_frequency_sample_multiplier`”次访问触发老化。
- 所有 4-bit 计数器同时除以 2。
- 清空 Doorkeeper，重新识别下一个采样周期内的首次访问。
- 老热点若不再被访问，其历史优势会持续衰减。

### 空间边界

频率估计器全部内存在构造时分配，运行中不会因为不同 query 数量增加而扩容。默认配置为总容量 4096、32 个分片，每个分片容量 128：

```text
Count-Min Sketch: 512 bytes/shard
Doorkeeper:       128 bytes/shard
合计:             640 bytes/shard
32 分片合计:      20480 bytes
```

该空间不包含实际缓存 Entry、链表和 key 索引，仅表示频率估计器额外开销。

### 缓存主体调整

- `ShardedWTinyLfuCache::Shard` 改为持有 `TinyLfuFrequencySketch`。
- `get()` 对命中和未命中都记录访问，保证新热点有机会通过准入。
- `put()` 不重复记录频率，避免一次 `get miss -> put` 被计算成两次访问。
- `erase()` 只删除缓存值；共享 Sketch 无法按单个 key 清零，残留频率由 Aging 衰减。
- 统计新增 `frequencyAges`，并提供频率估计器固定内存字节数。

### 测试与基准

组件及策略测试覆盖：

- 第一次访问只进入 Doorkeeper。
- 第二次访问进入 Count-Min Sketch。
- 4-bit 计数器饱和值。
- Frequency Aging 触发。
- 估计器内存大小保持不变。
