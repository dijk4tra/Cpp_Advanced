# 搜索引擎项目第三期缓存改造流程

本文用于记录第三期缓存功能的具体改造路线。整体目标是为“关键词推荐最终结果”“网页搜索最终结果”“文档展示信息”和“动态摘要片段”添加缓存机制，同时把网页库从启动时全量加载改为按需从 `pages.dat` 读取。工程上先落地本地 L1 缓存，再预留并接入 Redis L2 缓存，最后逐步升级缓存淘汰算法。

## 1. 当前方案评估

当前选择是合理的：

1. 优先缓存关键词推荐最终结果和网页搜索最终结果。
2. 将网页库改为按需从 `pages.dat` 读取，避免启动时把正文全量加载到内存。
3. 在按需读取基础上，为文档展示信息和动态摘要片段添加细粒度缓存。
4. 缓存架构采用二级缓存：本地缓存 + Redis 分布式缓存。
5. 工程落地采用“先实现 L1，预留 L2 接口，再接入 Redis”的方式。
6. 淘汰算法分阶段从分片 LRU + TTL 演进到 SLRU / 简化 W-TinyLFU，再演进到完整 W-TinyLFU。

这个路线是对原计划的补充修正。第二期项目已经把词典、倒排索引和网页库加载到内存，`KeywordRecommender::recommend_json()` 和 `WebSearcher::search_json()` 都返回最终 JSON 字符串。因此，最容易落地、收益也最直接的缓存对象就是：

```text
normalized query + 参数 -> JSON response
```

但如果继续保留 `PageLibrary` 启动时全量解析正文，文档级缓存价值会被削弱，也会让在线进程常驻内存随网页库规模线性增长。因此第三期应补入一个明确阶段：`PageLibrary` 启动时只加载 `offsets.dat`，查询时按 docId 从 `pages.dat` 读取单篇 XML 片段；热点文档和热点摘要再由缓存层保存。

## 2. 关于 W-TinyLFU / Caffeine 是否需要第三方库

不建议在当前 C++ 课程项目中直接安装或依赖 Caffeine。

Caffeine 是 Java 生态的高性能本地缓存库，它的 W-TinyLFU 思想非常值得借鉴，但不能直接作为 C++ 库嵌入当前项目。当前项目是 C++，如果要用第三方 C++ 缓存库，需要额外评估库质量、依赖链、CMake 集成、线程安全和学习成本。

更推荐的路线是：

1. 第一阶段自己实现分片 LRU + TTL。
2. 第二阶段在已有 LRU 基础上升级为 SLRU 或简化 W-TinyLFU。
3. 第三阶段再实现 Count-Min Sketch、频率衰减和 admission 策略。

也就是说，不需要一开始安装第三方库。先用项目内自研实现更稳，因为：

- 代码可控，便于写入课程项目文档和答辩说明。
- 不引入额外依赖，降低编译和部署问题。
- 分片 LRU 是完整 W-TinyLFU 的基础设施之一，不会浪费。
- 后续可以渐进式演进，不需要推翻第一版。

## 3. 总体架构

推荐新增一层 `CachedSearchService`，让 TLV 和 HTTP 服务都调用它。

改造前：

```text
SearchServer / WebHttpServer
  -> KeywordRecommender
  -> WebSearcher
```

改造后：

```text
SearchServer / WebHttpServer
  -> CachedSearchService
      -> TwoLevelCache
          -> L1 ShardedWTinyLfuCache（可配置回退 ShardedLruCache）
          -> L2 RedisCache
      -> KeywordRecommender
      -> WebSearcher
```

这样网络层仍然只负责协议解析和响应发送，缓存逻辑集中在服务层，不会散落到 `SearchServer` 和 `WebHttpServer` 两套入口里。

## 4. 缓存 Key 设计

关键词推荐缓存 key：

```text
v:{cache_version}:suggest:{lang}:{normalized_query}:{topK}
```

网页搜索缓存 key：

```text
v:{cache_version}:search:{normalized_query}:{topK}:{abstract_length}
```

文档展示信息缓存 key：

```text
v:{cache_version}:doc:{docId}
```

动态摘要片段缓存 key：

```text
v:{cache_version}:abstract:{docId}:{abstract_length}:{keywords_signature}
```

说明：

- `cache_version` 用于隔离离线重建后的旧缓存。
- `normalized_query` 应去掉首尾空白，并对连续空白做规整。
- 关键词推荐需要包含 `lang`，因为中文和英文会走不同词典。
- 网页搜索需要包含 `abstract_length`，因为摘要长度不同会影响返回 JSON。
- 文档缓存需要包含 `docId` 和 `cache_version`，离线重建后通过版本隔离旧文档。
- 动态摘要依赖文档、摘要长度和查询关键词，因此 key 需要包含 `docId`、`abstract_length` 和稳定的关键词签名。
- 如果未来 HTTP 和 TLV 的响应格式出现差异，需要把协议类型也加入 key。

## 5. 第一阶段：新增缓存接口和分片 LRU

目标：

- 实现可用的本地 L1 缓存。
- 支持容量限制。
- 支持 TTL。
- 支持分片，降低多线程锁竞争。

建议新增文件：

```text
include/cache/Cache.h
include/cache/ShardedLruCache.h
src/cache/ShardedLruCache.cc
```

缓存接口：

```cpp
class Cache {
public:
    virtual ~Cache() = default;
    virtual bool get(const std::string& key, std::string& value) = 0;
    virtual void put(const std::string& key, const std::string& value, int ttlSeconds) = 0;
    virtual void erase(const std::string& key) = 0;
};
```

分片 LRU 结构：

```text
ShardedLruCache
  -> shard[0]
      -> mutex
      -> unordered_map
      -> list
  -> shard[1]
  -> ...
```

分片选择：

```text
shard_index = hash(key) % shard_count
```

每个 shard 内部使用：

```text
unordered_map<string, list iterator>
list<Node>
mutex
```

`Node` 至少包含：

```text
key
value
expireTime
```

第一阶段验收标准：

- 相同 key 第二次请求能命中缓存。
- 超过容量后会淘汰最久未访问数据。
- 超过 TTL 后会重新计算并覆盖缓存。
- 多线程压测不崩溃、不出现数据竞争。

## 6. 第二阶段：新增 CachedSearchService

目标：

- 统一封装缓存读写。
- 避免 `SearchServer` 和 `WebHttpServer` 重复写缓存逻辑。
- 保留原始 `KeywordRecommender` 和 `WebSearcher` 的算法实现。

建议新增文件：

```text
include/online/CachedSearchService.h
src/online/CachedSearchService.cc
```

对外接口：

```cpp
class CachedSearchService {
public:
    std::string suggest(const std::string& query,
                        const std::string& lang,
                        int topK);

    std::string search(const std::string& query,
                       int topK);
};
```

内部依赖：

```text
KeywordRecommender&
WebSearcher&
Cache&
cache_version
ttl config
```

关键词推荐流程：

```text
build suggest key
if cache hit:
    return cached json
result = recommender.recommend_json(...)
cache.put(key, result, ttl)
return result
```

网页搜索流程：

```text
build search key
if cache hit:
    return cached json
result = searcher.search_json(...)
cache.put(key, result, ttl)
return result
```

第二阶段验收标准：

- TLV 和 HTTP 两个入口都通过 `CachedSearchService` 调用业务能力。
- 原始推荐和搜索结果保持不变。
- 缓存开启时能命中。
- 缓存关闭时仍走原始流程。

## 7. 第三阶段：让 SearchServer 和 WebHttpServer 依赖 CachedSearchService

目标：

- 网络层不再直接依赖 `KeywordRecommender` 和 `WebSearcher`。
- 缓存逻辑集中在 `CachedSearchService`。

改造点：

```text
SearchServer
  KeywordRecommender& recommender_  -> CachedSearchService& service_
  WebSearcher& searcher_            -> 删除

WebHttpServer
  KeywordRecommender& recommender_  -> CachedSearchService& service_
  WebSearcher& searcher_            -> 删除
```

`SearchServer::handle_request()` 中：

```text
keyword request -> service_.suggest(query, lang, topK)
web request     -> service_.search(query, topK)
```

`WebHttpServer::handle_api()` 中：

```text
/api/suggest -> service_.suggest(query, "", keywordTopK_)
/api/search  -> service_.search(query, webTopK_)
```

第三阶段验收标准：

- `SearchServer` 和 `WebHttpServer` 不再直接调用 `recommend_json()` / `search_json()`。
- 两个入口返回格式与改造前一致。
- 缓存命中逻辑只存在于 `CachedSearchService`。

## 8. 第四阶段：配置化启用 L1 缓存

建议新增配置：

```text
cache_enabled=1
cache_version=search_engine_v3_001

l1_cache_enabled=1
l1_cache_shards=32
l1_cache_capacity=4096
l1_cache_ttl_seconds=600
l1_empty_ttl_seconds=60
```

说明：

- `cache_enabled=0` 时整体关闭缓存。
- `l1_cache_enabled=0` 时不使用本地缓存。
- `l1_cache_shards` 建议先取 32。
- `l1_cache_capacity` 是总容量，再平均分配给每个 shard。
- 空结果也可以缓存，但 TTL 应更短。

第四阶段验收标准：

- 修改配置即可开启或关闭 L1。
- 配置缺失时使用安全默认值。
- 缓存关闭后功能仍正常。

## 9. 第五阶段：增加缓存命中率统计日志

目标：

- 能观察缓存是否真的生效。
- 为后续调整容量、TTL、淘汰策略提供依据。

建议统计：

```text
l1_hit
l1_miss
l2_hit
l2_miss
backend_compute
cache_put
cache_expired
cache_evict
```

第一版可以先只记录：

```text
l1_hit
l1_miss
cache_put
cache_evict
```

日志示例：

```text
[Cache] L1 hit=1024 miss=256 hit_rate=80.00% evict=35
```

第五阶段验收标准：

- 能定期看到命中率。
- 能区分 suggest 和 search 两类请求。
- 能看到淘汰次数和缓存写入次数。

## 10. 第六阶段：网页库按需读取与文档/摘要缓存

目标：

- 把 `PageLibrary` 从“启动时全量加载所有 Document”改为“启动时只加载 offsets，查询时按需读取 pages.dat”。
- 为热点文档展示信息添加缓存，减少重复从 `pages.dat` 读取和 XML 解析。
- 为热点动态摘要片段添加缓存，减少重复清洗正文、窗口打分和高亮生成。

`PageLibrary` 改造：

```text
load(pages, offsets)
  -> 保存 pages.dat 路径
  -> 加载 offsets.dat 到内存
  -> 不再解析全部 <doc>

find(docId, Document& doc)
  -> 查 offsets_
  -> 打开 pages.dat
  -> seek 到 offset
  -> 读取 length 字节
  -> parse_document()
```

注意：

- `offsets_` 仍需要常驻内存，因为它是 docId 到文件位置的轻量索引。
- 不再维护 `documents_` 全量正文哈希表。
- `find()` 不再返回 `Document*`，因为按需读取出的文档是临时对象，应改为输出参数或返回值。

`WebSearcher` 改造：

```text
search_json()
  -> 完成倒排索引召回和打分
  -> 组装 topK 时：
      -> get_document(docId)
          -> doc cache hit: 返回缓存文档
          -> doc cache miss: PageLibrary 按需读取，写入 doc cache
      -> get_abstract(doc, keywords)
          -> abstract cache hit: 返回缓存摘要
          -> abstract cache miss: DynamicAbstract::generate()，写入 abstract cache
```

建议新增配置：

```text
document_cache_ttl_seconds=600
abstract_cache_ttl_seconds=600
```

第六阶段验收标准：

- `PageLibrary` 启动时不再把所有网页正文加载进 `documents_`。
- 网页搜索仍能返回 `id/title/link/abstract/score`。
- 热点 docId 能命中文档缓存。
- 同一 docId、同一关键词集合和同一摘要长度能命中动态摘要缓存。
- 编译通过，并能解释按需读取相比全量加载的内存收益。

## 11. 第七阶段：接入 Redis，实现 L2

目标：

- 在 L1 未命中时查询 Redis。
- Redis 命中后写回 L1。
- 原始计算完成后同时写入 Redis 和 L1。
- Redis 不可用时自动降级，不影响搜索服务。

建议新增文件：

```text
include/cache/RedisCache.h
include/cache/TwoLevelCache.h
src/cache/RedisCache.cc
src/cache/TwoLevelCache.cc
```

二级缓存流程：

```text
get(key):
  if L1 hit:
      return value
  if L2 enabled and Redis hit:
      put L1
      return value
  return miss

put(key, value):
  put L1
  if L2 enabled:
      put Redis
```

建议新增配置：

```text
redis_cache_enabled=0
redis_host=127.0.0.1
redis_port=6379
redis_db=0
redis_connect_timeout_ms=20
redis_command_timeout_ms=20
redis_ttl_seconds=1800
redis_l1_backfill_ttl_seconds=600
```

注意：

- Redis 服务虽然在本机，但仍然是进程外服务，必须处理连接失败和超时。
- Redis 失败应当视为缓存未命中，不能影响主流程。
- 第一版可以默认关闭 Redis，待 L1 稳定后再打开。
- 如果不引入 hiredis 等第三方依赖，可以先实现最小 RESP 客户端，只支持 GET、SET/SETEX、DEL。

第七阶段验收标准：

- Redis 开启时，重启搜索服务后仍能从 Redis 命中旧缓存。
- Redis 关闭或异常时，服务仍能正常搜索。
- L2 命中后会回填 L1。

## 12. 第八阶段：singleflight、空结果缓存、TTL 抖动

### 12.1 singleflight

目标：

避免同一个热点 key 过期时，多个线程同时回源计算。

流程：

```text
cache miss
try become owner for key
  owner: compute backend result, write cache, wake waiters
  waiters: wait owner result, return same value
```

第一版可以只对 `CachedSearchService` 中的回源计算加 singleflight。

### 12.2 空结果缓存

目标：

避免不存在的 query 每次都走完整搜索流程。

策略：

- 空 `results` 的 JSON 也缓存。
- 空结果 TTL 比正常结果短。

建议：

```text
normal ttl = 600s
empty ttl  = 60s
```

### 12.3 TTL 抖动

目标：

避免大量 key 同时过期导致缓存雪崩。

策略：

```text
real_ttl = base_ttl + random(0, jitter_seconds)
```

建议新增配置：

```text
cache_ttl_jitter_seconds=30
```

第八阶段验收标准：

- 热点 key 过期瞬间不会触发大量重复计算。
- 空结果不会频繁回源。
- 大批缓存不会在同一秒集中失效。

## 13. 第九阶段：升级为 SLRU 或简化 W-TinyLFU

目标：

提升命中率，减少一次性冷查询污染缓存。

推荐先实现 SLRU：

```text
probation segment
protected segment
```

规则：

- 新数据进入 probation。
- probation 中的数据再次命中后晋升 protected。
- protected 满了之后降级一部分数据回 probation。
- probation 满了淘汰尾部数据。

SLRU 比纯 LRU 更能保护真正重复访问的热点，复杂度也明显低于完整 W-TinyLFU。

简化 W-TinyLFU 可以增加：

```text
Window LRU
Main SLRU
Frequency Estimator
Admission Policy
```

核心思想：

- 新 key 先进入 Window LRU。
- Window 淘汰候选进入 Main 前，与 Main 的淘汰候选比较频率。
- 只有新候选频率更高，才允许进入 Main。

第九阶段验收标准：

- 大量一次性 query 不会明显冲掉稳定热点。
- 命中率比纯 LRU 更稳定。
- 代码仍保持可理解、可调试。

当前实现状态（2026-06-27）：已完成。

- 新增分片 `ShardedWTinyLfuCache`，采用 Window LRU + Main SLRU。
- Main 已满时比较 Window candidate 与 Probation victim 的访问频率，严格更高才准入。
- 当前频率估计使用精确哈希表，并按采样窗口周期减半、清理冷 key。
- 保留 `ShardedLruCache`，可通过 `l1_cache_policy=lru` 回退或进行对照测试。
- 已增加扫描抗污染、TTL、删除和并发访问测试。
- 下一阶段仅需替换频率估计组件并扩展准入统计，无需重写分段主体。

## 14. 第十阶段：完整 W-TinyLFU

目标：

实现更接近 Caffeine 思想的本地缓存。

完整组件：

```text
Window LRU
Main Probation
Main Protected
Count-Min Sketch
Doorkeeper
Frequency Aging
Admission Policy
```

其中：

- `Count-Min Sketch` 用较小空间估算访问频率。
- `Doorkeeper` 可用 Bloom Filter 思想过滤首次访问。
- `Frequency Aging` 周期性衰减频率，避免旧热点长期占据缓存。
- `Admission Policy` 决定新淘汰候选是否有资格替换旧缓存项。

建议只有在前九个阶段稳定后再实现完整 W-TinyLFU。否则复杂度会过早压到项目主流程上。

第十阶段验收标准：

- 有可重复的命中率测试。
- 对扫描型 query 有明显抗污染能力。
- 高频热点在混合流量中能稳定保留。
- 代码注释和文档能解释每个结构的职责。

## 15. 推荐最终开发顺序

1. 新增缓存接口和分片 LRU。
2. 新增 `CachedSearchService`，封装 `suggest(query, lang, topK)` 和 `search(query, topK)`。
3. 让 `SearchServer` 和 `WebHttpServer` 依赖 `CachedSearchService`，不直接依赖 `KeywordRecommender` / `WebSearcher`。
4. 配置化启用 L1 缓存。
5. 增加缓存命中率统计日志。
6. 将网页库改为按需从 `pages.dat` 读取，并为文档展示信息和动态摘要片段添加缓存。
7. 再接入 Redis，实现 L2。
8. 增加 singleflight、空结果缓存、TTL 抖动。
9. 将 LRU 升级为 SLRU 或简化 W-TinyLFU。
10. 升级为完整 W-TinyLFU。

## 16. 当前阶段的推荐结论

当前不要急于安装第三方缓存库，也不要一开始实现完整 W-TinyLFU。

最稳妥的第三期路径是：

```text
先完成 L1 分片 LRU + TTL
再通过 CachedSearchService 统一接入
补上网页库按需读取和文档/摘要细粒度缓存
再接 Redis L2
最后逐步升级淘汰算法
```

这样既能快速让第三期缓存功能可运行，也保留了向二级缓存和高级淘汰算法演进的空间。
