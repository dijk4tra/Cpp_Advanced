# 搜索引擎第三期 HTTP 压测报告

## 1. 测试目标

本次测试直接启动真实 `search_server`，通过 HTTP 接口验证：

1. 关键词推荐和网页搜索在不同并发度下的 QPS 与 P50/P95/P99。
2. LRU 与 W-TinyLFU 在稳定热点场景中的端到端差异。
3. Redis L2 开启时，两种 L1 策略在扫描流量下的整体表现。
4. 关闭 Redis 后，单独观察 L1 淘汰算法对命中、回源和延迟的影响。
5. 同一个冷 key 并发到达时，singleflight 是否只执行一次回源。

本文中的 HTTP 指标包含客户端建连、服务端 HTTP 解析、缓存访问、Redis、必要时的搜索回源、响应发送和连接关闭。

## 3. 公平性控制

正式配置文件没有被修改。测试在 `/tmp/searchengine_v3_http_bench/` 中建立临时运行目录，并复用正式二进制与数据文件。

LRU 和 W-TinyLFU 使用：

- 相同二进制。
- 相同数据文件。
- 相同请求顺序、请求数与并发度。
- 相同 HTTP 线程数和 Redis 配置。
- 不同 `cache_version`，避免 Redis 缓存结果互相污染。
- 相同文件日志输出，避免一组写 PTY、另一组写文件造成偏差。

测试顺序固定为 LRU 后 W-TinyLFU。每个条件只执行一次，因此结果适合发现数量级和结构性问题，不应当解释为严格统计置信区间。

## 4. 服务配置

### 4.1 二级缓存测试

```text
L1 capacity：100
L1 shards：32
L1 policy：分别为 lru / wtinylfu
Redis L2：开启，127.0.0.1:6379
HTTP 工作线程：2
普通 TTL：600 秒
空结果 TTL：60 秒
TTL 抖动：0~30 秒
HTTP 连接：服务端 Connection: close
```

容量 100、分片 32 表示每个分片只有约 3~4 个条目。这不是推荐生产配置，而是为了在有限请求中触发淘汰。正式默认配置 `4096 / 32 = 128` 条/分片，更适合 W-TinyLFU 发挥作用。

### 4.2 L1 隔离测试

```text
L1 capacity：100
L1 shards：1
Redis L2：关闭
其他参数不变
```

单分片与关闭 Redis 用于排除分片容量碎片和 L2 回填影响，直接比较 LRU/W-TinyLFU。

## 7. 稳定热点结果

### 7.1 网页搜索 `/api/search`

| 策略 | 并发 | QPS | P50 ms | P95 ms | P99 ms | Max ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| LRU | 1 | 913.19 | 1.006 | 1.396 | 1.540 | 4.669 |
| W-TinyLFU | 1 | 914.48 | 1.010 | 1.403 | 1.626 | 2.849 |
| LRU | 8 | 516.81 | 14.589 | 27.238 | 34.816 | 46.170 |
| W-TinyLFU | 8 | 500.63 | 15.036 | 29.483 | 35.728 | 43.571 |
| LRU | 32 | 666.59 | 44.788 | 87.909 | 111.000 | 156.452 |
| W-TinyLFU | 32 | 665.80 | 45.021 | 87.028 | 106.892 | 137.533 |

结论：稳定热点已经全部进入 L1，两种策略的命中结果相同。并发 1 和 32 时 QPS 几乎相等；并发 8 时本轮 W-TinyLFU 低约 3.1%，但单次运行不足以证明稳定差异。

### 7.2 关键词推荐 `/api/suggest`

| 策略 | 并发 | QPS | P50 ms | P95 ms | P99 ms | Max ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| LRU | 1 | 953.01 | 0.970 | 1.367 | 1.515 | 1.661 |
| W-TinyLFU | 1 | 903.53 | 1.020 | 1.405 | 1.582 | 3.603 |
| LRU | 8 | 560.13 | 13.661 | 25.345 | 31.492 | 45.313 |
| W-TinyLFU | 8 | 549.02 | 13.751 | 26.422 | 33.201 | 47.850 |
| LRU | 32 | 735.01 | 40.052 | 80.161 | 105.649 | 149.769 |
| W-TinyLFU | 32 | 692.06 | 42.863 | 83.743 | 104.006 | 138.082 |

本轮 W-TinyLFU QPS 低约 2%~6%。这符合算法级测试中观察到的额外维护成本，但由于测试未做多轮交叉顺序与 CPU 绑定，不能把差值直接认定为稳定开销。

### 7.3 并发度现象

并发从 1 提升到 8 后，延迟明显上升、QPS反而下降；并发 32 时 QPS有所回升但尾延迟达到约 80~111ms。

主要原因不是缓存锁：

1. HTTP 服务只有 2 个工作线程。
2. 每个请求新建并关闭 TCP 连接。
3. 服务端为每次连接和断开打印 INFO 日志。
4. Python 压测端也使用线程和短连接。

因此当前服务的最佳并发度不能只通过增加客户端线程获得。

## 8. Redis L2 开启的扫描结果

配置：容量 100、32 分片、Redis 开启、并发 32。

| 策略 | QPS | P50 ms | P95 ms | P99 ms | Max ms | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| LRU | 768.92 | 38.673 | 79.890 | 103.534 | 177.665 | 0 |
| W-TinyLFU | 762.06 | 38.811 | 81.354 | 107.112 | 152.177 | 0 |

差异：

```text
W-TinyLFU QPS：-0.89%
P50：+0.36%
P95：+1.83%
P99：+3.46%
```

两者几乎相同。原因是 `TwoLevelCache` 在 L1 未命中后继续查询 Redis，L1 被淘汰的数据仍可能在 L2 命中并回填。`CachedSearchService` 当前统计的是组合缓存命中，无法区分 L1 与 L2，因此服务日志中的累计命中率和回源次数也基本一致。

最后一个完整的 15000 请求检查点：

```text
LRU：        hit_rate=76.45%，backend_compute=3533
W-TinyLFU：  hit_rate=76.45%，backend_compute=3532
```

此结果说明二级缓存提高了整体稳定性，但也掩盖了 L1 淘汰策略差异。

## 9. L1-only 扫描结果

配置：容量 100、单分片、Redis 关闭、并发 32。

### 9.1 HTTP 指标

| 策略 | QPS | P50 ms | P95 ms | P99 ms | Max ms | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| LRU | 718.28 | 41.213 | 84.294 | 105.728 | 188.381 | 0 |
| W-TinyLFU | 726.40 | 41.085 | 83.629 | 105.558 | 180.121 | 0 |

W-TinyLFU：

```text
QPS：+1.13%
P50：-0.31%
P95：-0.79%
P99：-0.16%
```

### 9.2 6000 请求服务端检查点

| 策略 | 命中率 | hit | miss / backend_compute |
| --- | ---: | ---: | ---: |
| LRU | 28.33% | 1700 | 4300 |
| W-TinyLFU | 34.67% | 2080 | 3920 |

W-TinyLFU 多命中 380 次，回源减少 380 次，结果与算法级扫描测试方向一致。

端到端 QPS只提升约 1.13%，远低于命中率变化，说明当前扫描 query 主要返回空结果，回源计算成本很低；HTTP 短连接、日志和线程排队占据了大部分请求时间。

## 10. singleflight 与空结果缓存

300 个同 key 冷请求、并发 32：

```text
completed=300
errors=0
QPS=648.11
P50=41.254ms
P95=102.135ms
P99=159.973ms
```

服务端最终统计：

```text
search_hit=298
search_miss=2
backend_compute=1
cache_put=1
empty_put=1
singleflight_wait=1
```

解释：两个 HTTP 工作线程同时看到冷 key 未命中，其中一个成为 owner，另一个等待；只执行一次回源并写入一次空结果，之后 298 次请求命中缓存。singleflight 与空结果缓存均按设计生效。

由于 HTTP 服务只有两个工作线程，即使客户端并发 32，同一时刻最多只有少量请求进入业务层，因此 `singleflight_wait=1` 是合理结果。

## 11. 主要结论

### 11.1 功能正确性

- 43100 个计量请求全部成功，无 HTTP 错误。
- Redis L2 正常提供降级命中与 L1 回填。
- singleflight 将两个并发冷 miss 合并为一次回源。
- 空结果只写入一次，并被后续请求复用。

### 11.2 淘汰策略

- W-TinyLFU 在 L1-only 扫描场景显著提高命中率并减少回源。
- Redis 开启后，L2 会掩盖大部分 L1 差异，端到端结果几乎相同。
- 稳定小热点场景中，两种策略都能完整容纳工作集，W-TinyLFU没有命中率优势。
- W-TinyLFU 的结构维护存在成本；是否值得取决于真实流量中的长尾比例和回源成本。

### 11.3 当前主要瓶颈

当前端到端性能首先受以下因素影响：

1. HTTP 线程只有 2 个。
2. 每次请求使用短连接。
3. 每次连接/断开都打印 INFO 日志，单轮产生约 8MiB 日志。
4. Redis 每条命令创建 hiredis 短连接。

缓存淘汰算法不是当前 P95/P99 的唯一或首要决定因素。

## 12. 改进建议

### P0：补齐可观测性

1. 分别统计 L1 hit、L2 hit、L2 backfill 和 backend miss。
2. 将 W-TinyLFU admission/rejection/Aging 接入周期日志。
3. 记录回源耗时、Redis 耗时和 HTTP 排队耗时。

没有分层指标时，二级缓存命中会掩盖 L1 策略差异。

### P1：降低 HTTP 与日志开销

1. 将逐连接 INFO 日志降为 DEBUG 或采样记录。
2. 根据 CPU 核数和压测结果调整 `http_threads`。
3. 评估 HTTP keep-alive，减少短连接成本。

### P2：优化 Redis

1. 使用每线程连接或连接池替代每命令短连接。
2. 分别测试 Redis 开启/关闭时的 P95/P99。
3. 监控 Redis 超时和连接失败次数。

### P3：进行统计上更严格的复测

1. 每个条件至少运行 5 次，报告中位数与离散程度。
2. 交叉测试顺序：LRU/W-TinyLFU 轮换先后。
3. 固定 CPU 频率和进程亲和性，减少调度噪声。
4. 使用脱敏真实查询日志，而不是主要依赖合成空结果 query。
5. 使用正式容量 4096，并测试容量/分片比对 W-TinyLFU 的影响。
6. 同时采集 CPU、RSS、上下文切换和 Redis 指标。

## 13. 复现命令

稳定热点示例：

```bash
python3 tests/http_load/http_load_test.py \
  --mode search \
  --query-file tests/http_load/sample_queries.txt \
  --requests 1500 \
  --concurrency 32 \
  --warmup 100
```

扫描序列需要按 `tests/cache_policy/cache_policy_benchmark.cc` 中的 `scan_resistance` 顺序生成 6200 行 query，再执行：

```bash
python3 tests/http_load/http_load_test.py \
  --mode search \
  --query-file scan_queries.txt \
  --requests 6200 \
  --concurrency 32 \
  --warmup 0
```

复测时必须保证两种策略使用不同 `cache_version`，并保持日志输出方式、请求顺序和 Redis 状态一致。
