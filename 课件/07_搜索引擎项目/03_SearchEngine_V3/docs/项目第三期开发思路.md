# 搜索引擎项目第三期开发思路：缓存设计

本文基于当前 `03_SearchEngine_V3` 已完成的第二期代码，以及《搜索引擎项目.pdf》第 15-16 页第三期“缓存设计”要求，分析现有数据存储方式，并给出第三期引入缓存的设计建议。

第三期 PDF 的核心要求可以概括为三点：

1. 使用缓存加快查询结果返回。
2. 缓存适合保存读多写少、计算耗时、热点、可短暂不一致的数据。
3. 多工作线程同时访问同一份缓存会造成锁竞争，应考虑分片缓存，使绝大多数访问只竞争局部锁。

结合当前项目，缓存设计不应替代第二期已经加载到内存的词典、倒排索引和网页库，而应叠加在“重复查询结果”或“热点文档展示信息”之上。

## 1. 当前数据存储机制分析

### 1.1 离线阶段：数据先落到磁盘文件

当前项目的数据不是直接写入数据库，也不是运行时从远程服务读取，而是离线建库生成一批本地文件，再由在线服务加载。

入口在 `src/offline/offline_main.cc`：

- `main()` 读取 `conf/config.conf`。
- 创建 `data/dict`、`data/index`、`bin` 目录。
- 调用 `KeywordProcessor::process()` 生成关键词推荐相关文件。
- 调用 `PageProcessor::process()` 生成网页搜索相关文件。

关键词推荐离线数据由 `KeywordProcessor` 生成：

- `include/offline/KeywordProcessor.h` 定义 `KeywordProcessor`。
- `src/offline/KeywordProcessor.cc` 中：
  - `create_en_dict()` 统计英文词频，输出 `data/dict/dict_en.dat`。
  - `build_en_index()` 读取英文词典，输出 `data/index/index_en.dat`。
  - `create_cn_dict()` 使用 cppjieba 切中文语料，输出 `data/dict/dict_cn.dat`。
  - `build_cn_index()` 读取中文词典，输出 `data/index/index_cn.dat`。

网页搜索离线数据由 `PageProcessor` 生成：

- `include/offline/PageProcessor.h` 定义 `PageProcessor`。
- `src/offline/PageProcessor.cc` 中：
  - `extract_documents()` 从 XML 语料中提取文档。
  - `deduplicate_documents()` 用 SimHash 去重。
  - `build_pages_and_offsets()` 输出 `data/index/pages.dat` 和 `data/index/offsets.dat`。
  - `build_inverted_index()` 输出 `data/index/invert_index.dat`。

这些文件路径由 `conf/config.conf` 配置：

- `en_dict=data/dict/dict_en.dat`
- `cn_dict=data/dict/dict_cn.dat`
- `en_dict_index=data/index/index_en.dat`
- `cn_dict_index=data/index/index_cn.dat`
- `pages=data/index/pages.dat`
- `offsets=data/index/offsets.dat`
- `invert_index=data/index/invert_index.dat`

因此，项目的持久化存储机制是“离线文件存储”。第二期在线服务启动时读取这些文件。

### 1.2 在线阶段：启动时加载到内存，查询阶段多线程只读共享

你的猜测基本正确：第二期在线服务运行时，核心检索数据会被加载进内存，并由 TLV 服务线程和 HTTP 服务线程共享读取。但需要补充一点：这些数据最初来自磁盘文件，不是只存在内存；内存只是在线查询阶段的常驻索引副本。

入口在 `src/online/online_main.cc`：

- `KeywordRecommender recommender;`
- `recommender.load(...)`
- `WebSearcher searcher;`
- `searcher.load(...)`
- 构造 `SearchServer` 和 `WebHttpServer` 时，把同一个 `recommender`、`searcher` 以引用方式传入。

具体共享关系：

- `SearchServer` 中保存 `KeywordRecommender& recommender_` 和 `WebSearcher& searcher_`。
- `WebHttpServer` 中也保存 `KeywordRecommender& recommender_` 和 `WebSearcher& searcher_`。
- 两个 server 运行在同一个进程内，分别监听 TLV 端口和 HTTP 端口，共享同一份业务对象。

### 1.3 关键词推荐数据如何存储

核心类：`KeywordRecommender`

定义位置：`include/online/KeywordRecommender.h`

关键成员：

```cpp
std::vector<DictEntry> cnDict_;
std::vector<DictEntry> enDict_;
CharIndex cnIndex_;
CharIndex enIndex_;
```

其中：

```cpp
using CharIndex = std::unordered_map<std::string, std::vector<int>>;
```

含义：

- `cnDict_` / `enDict_`：词典数组，保存 `word` 和 `frequency`。
- `cnIndex_` / `enIndex_`：字符到词典行号的索引。

加载位置：`src/online/KeywordRecommender.cc`

- `KeywordRecommender::load()` 调用：
  - `load_dict(cnDict, cnDict_)`
  - `load_index(cnIndex, cnIndex_)`
  - `load_dict(enDict, enDict_)`
  - `load_index(enIndex, enIndex_)`

查询位置：

- `KeywordRecommender::recommend_json()`

查询时会：

1. 判断语言。
2. 把查询词拆成字符。
3. 从 `cnIndex_` 或 `enIndex_` 找候选词典行号。
4. 去重候选行号。
5. 对每个候选词计算编辑距离。
6. 按编辑距离、词频、字典序排序。
7. 组装 JSON 返回。

该函数是 `const` 成员函数，查询阶段不修改 `cnDict_`、`enDict_`、`cnIndex_`、`enIndex_`。因此多个 muduo 工作线程可以并发读取它们。

### 1.4 网页搜索数据如何存储

核心类：`WebSearcher`

定义位置：`include/online/WebSearcher.h`

关键成员：

```cpp
cppjieba::Jieba tokenizer_;
std::set<std::string> stopWords_;
PageLibrary pageLibrary_;
std::unordered_map<std::string, PostingMap> invertedIndex_;
int abstractLength_ = 150;
```

其中：

```cpp
using PostingMap = std::unordered_map<int, double>;
```

含义：

- `tokenizer_`：cppjieba 分词器。
- `stopWords_`：中文停用词集合。
- `pageLibrary_`：内存中的网页库。
- `invertedIndex_`：倒排索引，结构为 `word -> docId -> normalized TF-IDF weight`。
- `abstractLength_`：动态摘要长度。

加载位置：`src/online/WebSearcher.cc`

- `WebSearcher::load()` 调用：
  - `TextUtils::load_stop_words(stopWords)`
  - `pageLibrary_.load(pages, offsets)`
  - `load_inverted_index(invertIndex)`

查询位置：

- `WebSearcher::search_json()`

查询时会：

1. 使用 cppjieba 分词。
2. 过滤停用词和无意义 token。
3. 根据倒排索引构造查询 TF-IDF 向量。
4. 求多个查询词 posting list 的交集。
5. 计算余弦相似度。
6. 排序取 topK。
7. 通过 `PageLibrary::find(docId)` 取文档。
8. 调用 `DynamicAbstract::generate()` 针对本次查询生成动态摘要。
9. 组装 JSON 返回。

### 1.5 网页库如何存储

核心类：`PageLibrary`

定义位置：`include/online/PageLibrary.h`

关键成员：

```cpp
std::unordered_map<int, PageOffset> offsets_;
std::unordered_map<int, Document> documents_;
```

加载位置：`src/online/PageLibrary.cc`

- `PageLibrary::load()` 先调用 `load_offsets()` 读 `offsets.dat`。
- 再打开 `pages.dat`。
- 根据每篇文档的 offset 和 length 从 `pages.dat` 中读取 XML 片段。
- 调用 `parse_document()` 解析为 `Document`。
- 存入 `documents_`。

查询位置：

- `PageLibrary::find(int docId) const`

它只做 `documents_.find(docId)`，返回哈希表中 `Document` 的指针，不修改内部状态。

这说明第二期已经把网页库完整加载到内存，查询时不再频繁读磁盘。因此 PDF 中提到的“缓存热门文档信息，避免频繁读取网页库”在当前代码里收益会弱一些，因为当前不是按需读文件，而是内存哈希表查找。

### 1.6 网络线程与共享对象

网络层使用 muduo。

`SearchServer`：

- 定义位置：`include/online/SearchServer.h`
- 实现位置：`src/online/SearchServer.cc`
- `server_.setThreadNum(ioThreads)` 设置 TLV 服务线程数。
- `handle_request()` 根据 TLV type 调用：
  - `recommender_.recommend_json(query, lang, topK)`
  - `searcher_.search_json(query, topK)`

`WebHttpServer`：

- 定义位置：`include/online/WebHttpServer.h`
- 实现位置：`src/online/WebHttpServer.cc`
- `server_.setThreadNum(httpThreads)` 设置 HTTP 服务线程数。
- `/api/suggest` 调用 `recommender_.recommend_json(...)`。
- `/api/search` 调用 `searcher_.search_json(...)`。

结论：

- 第二期在线服务中的核心业务数据是“进程内共享内存数据”。
- 数据在启动阶段从磁盘加载。
- 查询阶段基本只读。
- 因为只读，所以当前不需要业务数据锁。
- 第三期引入缓存后，缓存会有读写、淘汰、更新命中顺序等操作，这会带来新的并发控制问题。

## 2. 缓存概念与价值对齐

### 2.1 什么是缓存

缓存是一层更靠近访问方、更小、更快、通常可淘汰的数据副本。它的目标不是保存全部真实数据，而是保存近期或高频访问的数据，让后续相同或相似请求绕过昂贵计算、磁盘 IO、网络 IO 或复杂对象构造。

缓存通常具备几个特征：

- 容量有限。
- 数据可丢失，丢失后能从原始数据或计算流程重建。
- 关注热点访问。
- 需要淘汰策略。
- 可能允许短时间不一致。
- 需要命中率、容量、过期时间、并发访问等设计。

### 2.2 缓存与当前“内存数据存储”的本质区别

当前第二期的内存数据不是严格意义上的缓存，而是在线检索必须依赖的主索引副本。

区别如下：

| 对比项 | 当前内存数据 | 第三期缓存 |
| --- | --- | --- |
| 数据来源 | 离线生成的完整文件 | 查询结果或热点数据的副本 |
| 数据范围 | 词典、字符索引、网页库、倒排索引基本全量加载 | 只保存热点 query 或热点 doc |
| 是否可淘汰 | 不应淘汰，淘汰会导致查询功能不完整 | 可以淘汰，未命中时重新计算 |
| 是否有写入 | 启动阶段写入，查询阶段只读 | 查询阶段会读写、更新访问状态 |
| 目标 | 支撑检索功能 | 减少重复计算，提高热点请求速度 |
| 一致性 | 与当前离线数据版本一致 | 可通过 TTL 或版本号控制一致性 |
| 并发问题 | 只读共享，基本无锁 | 有读写和淘汰，需要并发设计 |

例如：

- `invertedIndex_` 是完整倒排索引，不能只保存热门词，否则冷门词无法检索。
- `documents_` 是完整网页库内存副本，不能按缓存方式随意淘汰，除非重构为按需加载。
- `query -> response JSON` 才是典型缓存：热门查询命中后可以直接返回，不再分词、求交集、打分、生成摘要。

### 2.3 本项目中最值得缓存的数据

结合当前代码，推荐缓存优先级如下。

第一优先级：关键词推荐最终结果

键：

```text
suggest:{lang}:{normalized_query}:{topK}:{dict_version}
```

值：

```text
KeywordRecommender::recommend_json() 返回的 JSON 字符串
```

原因：

- 同一输入前缀可能被多个用户频繁请求。
- 前端输入框有联想场景，热点前缀重复率高。
- 原流程要召回候选、计算编辑距离、排序，缓存收益明显。

第二优先级：网页搜索最终结果

键：

```text
search:{normalized_query}:{topK}:{abstract_length}:{index_version}
```

值：

```text
WebSearcher::search_json() 返回的 JSON 字符串
```

原因：

- 可直接绕过分词、查询向量构造、posting list 交集、余弦打分、排序、动态摘要生成。
- 当前动态摘要是查询时生成，命中缓存可以省掉这部分 CPU。
- 对热门搜索词，收益最大。

第三优先级：文档展示信息或动态摘要片段

键：

```text
doc:{docId}:{index_version}
```

或：

```text
abstract:{docId}:{normalized_keywords}:{abstract_length}:{index_version}
```

值：

```text
title/link/content摘要/abstract
```

注意：当前 `PageLibrary` 已经把文档加载到 `documents_`，`find()` 只是内存哈希表查询，所以单独缓存 `docId -> Document` 的收益有限。若未来把网页库改为按需从文件读取，或正文太大不再全量加载，文档级缓存才会成为重点。

### 2.4 速度提升预计

不能在没有压测数据的情况下承诺固定倍数，但可以从代码路径判断收益来源。

关键词推荐未命中时需要：

- 字符拆分。
- 索引召回。
- 候选行号去重。
- 对大量候选词计算编辑距离。
- 排序。
- JSON 构造。

本地缓存命中时只需要：

- 构造缓存 key。
- 哈希查找。
- 返回已序列化 JSON 字符串。

网页搜索未命中时需要：

- cppjieba 分词。
- 停用词过滤。
- 查询向量计算。
- 多个 posting list 求交集。
- 对候选文档打分。
- 排序。
- 查文档。
- 生成动态摘要。
- JSON 构造。

本地缓存命中时也只需要：

- 构造缓存 key。
- 哈希查找。
- 返回 JSON 字符串。

因此：

- 本地缓存命中通常可以把热点请求从“完整检索计算”降为“一次内存哈希查找 + 字符串拷贝”，热点 query 可能获得数倍到数十倍延迟改善。
- Redis 命中会有网络开销，但仍可绕过完整检索计算；如果 Redis 部署在本机或同机房，热点复杂查询仍可能明显更快。
- 总体吞吐提升取决于命中率。若命中率为 `H`，未命中耗时为 `Tmiss`，缓存命中耗时为 `Thit`，平均耗时近似为：

```text
Tavg = H * Thit + (1 - H) * Tmiss
```

由于当前第二期已经把索引和网页库放在内存中，缓存不会带来“磁盘 IO 级别”的巨大提升；它主要优化 CPU 计算、排序、摘要生成和 JSON 构造。对重复查询越多、查询越复杂、候选文档越多的场景，收益越明显。

## 3. 缓存架构设计选择

### 3.1 方案 A：一级缓存

一级缓存可以有两种理解：仅本地缓存，或仅 Redis。

#### 3.1.1 仅本地缓存

架构：

```text
请求 -> 本进程 L1 Cache -> 未命中 -> 原搜索流程 -> 写入 L1 -> 返回
```

优点：

- 延迟最低，命中后不走网络。
- 实现相对简单，可以直接在 C++ 进程内使用 `unordered_map + list` 或分片结构。
- Redis 不可用时不影响服务。
- 非常适合当前单机课程项目。

缺点：

- 每个进程一份缓存，无法跨进程共享。
- 服务重启后缓存全部丢失。
- 多线程访问同一缓存需要加锁。
- 多实例部署时，同一个热门 query 可能在每个进程都重复计算一次。
- 容量受搜索服务进程内存限制。

适用场景：

- 单机服务。
- 当前课程项目体量。
- 追求实现清晰，先证明缓存效果。

#### 3.1.2 仅 Redis 缓存

架构：

```text
请求 -> Redis Cache -> 未命中 -> 原搜索流程 -> 写入 Redis -> 返回
```

优点：

- 多个搜索服务实例可以共享缓存。
- 服务进程重启后缓存仍可保留。
- Redis 自带 TTL、淘汰策略、内存管理、监控能力。
- 可以为未来分布式部署打基础。

缺点：

- 每次命中也要访问 Redis，有网络延迟。
- Redis 故障会影响缓存层，需要超时、降级和连接池。
- 当前项目 CMake 和代码未引入 Redis 客户端，需要新增依赖。
- 对非常轻量的关键词推荐请求，Redis 网络开销可能抵消部分收益。

适用场景：

- 多进程或多机器部署。
- 缓存容量需要独立于搜索进程。
- 需要跨实例共享热点结果。

### 3.2 方案 B：二级缓存，本地缓存 + Redis 分布式缓存

架构：

```text
请求
  -> L1 本地缓存
      命中：直接返回
      未命中：
        -> L2 Redis
            命中：写回 L1，返回
            未命中：执行原搜索流程，写 Redis，写 L1，返回
```

推荐的缓存对象：

- L1：保存最热的一小批 `query -> JSON`。
- L2：保存更大范围的热点 `query -> JSON`，供多个进程共享。

优点：

- L1 命中延迟最低。
- L2 支持跨进程、跨机器共享。
- Redis 重启或网络异常时，可以降级为仅 L1 + 原搜索流程。
- 本地 L1 可以吸收最高频请求，减少 Redis 压力。
- 更接近真实生产系统的缓存层级。

缺点：

- 实现复杂度最高。
- 需要处理 L1/L2 一致性、TTL、版本号、连接池、降级策略。
- 调试路径变长：L1 命中、L2 命中、全部未命中三种路径都要测试。
- 若没有多进程或多实例，Redis 的实际收益没有 L1 明显。

### 3.3 推荐方案

我推荐采用“二级缓存设计，一期实现可先落地 L1，预留 L2 Redis 接口”的方式。

理由：

1. 你的倾向是二级缓存，这个方向合理，符合未来扩展。
2. 当前代码是单进程多线程，L1 本地缓存最能直接降低热点请求延迟。
3. Redis 引入会带来依赖和部署复杂度，不建议第一步就让所有请求强依赖 Redis。
4. 通过抽象缓存接口，可以先实现本地缓存，再接入 Redis，不影响 `KeywordRecommender` 和 `WebSearcher` 的核心算法。
5. 离线索引是批量生成、在线只读的模式，非常适合使用 `index_version` 或 `data_version` 做缓存 key 前缀，降低一致性复杂度。

推荐落地结构：

```text
include/cache/Cache.h
include/cache/ShardedLruCache.h
include/cache/RedisCache.h
include/cache/TwoLevelCache.h
src/cache/...
```

核心接口：

```cpp
class Cache {
public:
    virtual ~Cache() = default;
    virtual bool get(const std::string& key, std::string& value) = 0;
    virtual void put(const std::string& key, const std::string& value, int ttlSeconds) = 0;
    virtual void erase(const std::string& key) = 0;
};
```

在线服务接入点：

- 在 `SearchServer::handle_request()` 调用业务模块前后接入缓存。
- 在 `WebHttpServer::handle_api()` 调用业务模块前后接入缓存。
- 或者更集中地封装一个 `CachedSearchService`，让 TLV 和 HTTP 都调用同一层，避免两处重复写缓存逻辑。

更推荐：

```text
SearchServer/WebHttpServer
  -> SearchService
      -> TwoLevelCache
      -> KeywordRecommender/WebSearcher
```

这样网络层继续只负责协议，缓存逻辑不会散落到两个 server 里。

## 4. 缓存淘汰算法选型

### 4.1 LRU

LRU 淘汰最近最少使用的数据。

常见实现：

```text
unordered_map<Key, list iterator> + list<Key, Value>
```

命中时把节点移动到链表头部；超容量时淘汰链表尾部。

优点：

- 实现简单。
- 时间复杂度可以做到 O(1)。
- 对“最近访问的数据很可能再次访问”的场景效果好。
- 很适合作为课程项目的第一版。

缺点：

- 抗扫描能力弱。如果突然出现大量一次性冷查询，会把真正热点数据挤出去。
- 只看最近性，不看长期频率。
- 每次 get 都要修改链表顺序，因此并发读也会变成写操作，需要加锁。

适合本项目的部分：

- 搜索框联想中，用户连续输入相近前缀，例如 `中`、`中国`、`中国人`，最近性很强。
- 热点新闻词、课程测试词短时间内反复出现，LRU 能捕捉。

### 4.2 LFU

LFU 淘汰访问次数最少的数据。

优点：

- 能保留长期高频 query。
- 对稳定热点更友好。
- 不容易被短时间冷数据完全冲掉。

缺点：

- 实现比 LRU 复杂。
- 需要维护频次，频次老化不好处理。
- 历史热点可能长期占据缓存，即使已经过时。
- 搜索引擎的热点具有时效性，纯 LFU 容易保留过期热点。

适合本项目的部分：

- 常年高频关键词，例如固定课程测试词或常见关键词。

不适合的部分：

- 新闻、热点事件、用户输入联想都更偏时间敏感，纯 LFU 容易滞后。

### 4.3 FIFO、Random、TTL-only

FIFO：

- 实现很简单。
- 不关心访问行为，命中率通常不如 LRU/LFU。
- 不推荐作为主要策略。

Random：

- 实现简单，锁竞争也可较低。
- 命中率不可控。
- 可以作为极简兜底，不适合作为本项目主要设计。

TTL-only：

- 只设置过期时间，不做容量淘汰。
- 实现简单，但可能撑爆内存。
- 可以和 LRU/LFU/W-TinyLFU 配合，但不能单独承担缓存管理。

### 4.4 ARC

ARC 是自适应替换缓存，会在 recency 和 frequency 之间动态调整。

优点：

- 能同时适应最近热点和高频热点。
- 理论命中率比单纯 LRU 更稳。

缺点：

- 实现复杂度高。
- 对课程项目来说理解和调试成本偏高。
- 若只需要展示第三期缓存设计，收益和复杂度不一定匹配。

### 4.5 W-TinyLFU / Caffeine 的设计思想

Caffeine 是 Java 生态中非常成熟的本地缓存库，其核心思路可以概括为 W-TinyLFU：

- Window LRU：新数据先进入一个小窗口，照顾突发访问和新热点。
- TinyLFU Admission：用近似频率统计判断新数据是否值得进入主缓存。
- Segmented LRU：主缓存区分 probation/protected，保护真正多次命中的热点。
- Count-Min Sketch：用较小内存估算访问频率。
- Aging：周期性衰减历史频率，避免旧热点永远占据缓存。

它比 LRU 更能抵抗扫描污染，也比 LFU 更能适应热点变化。

搜索引擎 query 的典型特征是：

- 访问分布近似 Zipf，少数 query 很热。
- 热点会随时间变化。
- 存在大量长尾 query，只访问一次。
- 可能出现扫描式或测试式随机 query。
- 输入联想有短时间强局部性。

这些特征非常适合 W-TinyLFU：既接纳新近热点，又保护长期高频热点，还能拒绝大量一次性长尾 query。

### 4.6 推荐选择

从“最契合搜索引擎场景”的角度看，W-TinyLFU / Caffeine 思想最契合本项目。

从“课程项目可实现性”的角度看，建议分阶段落地：

第一阶段：分片 LRU + TTL

- 实现简单。
- 容易测试。
- 能快速验证缓存收益。
- 已能回答 PDF 中并发访问和淘汰算法的问题。

第二阶段：升级为 SLRU 或简化 W-TinyLFU

- 增加一个小的 Window LRU。
- 主缓存分 probation/protected 两段。
- 增加轻量频率统计，用于 admission 判断。
- 对频率做周期性衰减。

第三阶段：完整 W-TinyLFU

- 使用 Count-Min Sketch。
- 使用 ring buffer 或批量记录降低访问路径锁竞争。
- 更细致地调参 window/main/protected 比例。

如果第三期目标偏工程落地，建议先实现“分片 LRU + TTL”。如果第三期目标偏深入缓存算法，建议文档设计为 W-TinyLFU，代码先实现简化版本。

## 5. 并发访问与高可用设计

### 5.1 当前并发模型带来的问题

第二期没有缓存时，业务对象查询阶段几乎只读：

- `KeywordRecommender::recommend_json()` 是 `const`。
- `WebSearcher::search_json()` 是 `const`。
- `PageLibrary::find()` 是 `const`。
- `DynamicAbstract::generate()` 是静态无状态函数。

因此多个 muduo 工作线程同时读共享对象风险较低。

引入缓存后情况不同：

- `get()` 命中可能要更新 LRU 链表位置。
- `put()` 要插入新节点。
- 超容量要淘汰旧节点。
- TTL 过期要删除节点。
- 命中率、访问次数等指标也可能被更新。

这些都是写操作。如果所有线程争夺一把全局锁，高并发下缓存会从优化点变成瓶颈。

### 5.2 分片缓存

PDF 第 16 页给出的方向是分片缓存：

```cpp
template<typename Key, typename Value>
class HashxxxCaches
{
public:
    void put(const Key& key, const Value& value);
    bool get(const Key& key, Value& value);
private:
    int capacity_;
    int slices_;
    std::vector<std::unique_ptr<xxxCache<Key, Value>>> _caches;
    std::hash<Key> hash_func_;
};
```

本项目应采用这个方向。

设计：

```text
shardIndex = hash(key) % shardCount
```

每个 shard 内部维护独立的：

- `unordered_map`
- LRU/SLRU 链表
- mutex
- 容量
- 命中/未命中统计

优点：

- 不同 key 落到不同 shard 时互不阻塞。
- 每把锁保护的数据更少，临界区更短。
- 可以按 muduo 工作线程数设置 shard 数，例如 `io_threads + http_threads` 的 2-4 倍。

建议：

- `shardCount` 使用 16、32、64 这类固定值起步。
- `capacity` 平均分配到每个 shard。
- 每个 shard 使用 `std::mutex` 即可。因为 LRU 的 `get()` 也要移动节点，本质是写操作，`shared_mutex` 的收益有限。

### 5.3 缓存值使用不可变字符串

当前业务接口已经返回 JSON 字符串：

- `KeywordRecommender::recommend_json() -> std::string`
- `WebSearcher::search_json() -> std::string`

这对缓存非常友好。缓存可以直接存最终 JSON 字符串。

推荐：

```cpp
using CacheValue = std::shared_ptr<const std::string>;
```

或简单一点：

```cpp
std::string value;
```

如果响应较大，使用 `shared_ptr<const std::string>` 可以减少拷贝。对课程项目，直接存 `std::string` 更容易实现。

### 5.4 避免缓存击穿：singleflight

问题：

如果某个热门 key 过期，100 个线程同时未命中，它们可能同时执行完整搜索流程，再同时写缓存。这叫缓存击穿或请求合并缺失。

解决：

- 为正在计算的 key 建一个 `inflight` 表。
- 第一个线程负责计算。
- 后续线程等待该 key 的计算结果。
- 计算完成后统一唤醒等待线程。

简化设计：

```text
get L1 miss
get L2 miss
enter singleflight(key)
  winner computes
  followers wait
winner writes cache
followers read result
```

课程项目第一版可以暂不实现 singleflight，但设计文档应保留该能力。若压测发现热点过期瞬间 CPU 抖动，再实现。

### 5.5 防止缓存穿透：空结果缓存

问题：

如果大量请求都是不存在的 query，每次都未命中缓存并走完整搜索，会浪费 CPU。

解决：

- 对空结果也缓存，但 TTL 更短。
- 例如正常结果 TTL 10 分钟，空结果 TTL 30-60 秒。

当前接口返回空 results 的 JSON 结构稳定，很适合缓存。

### 5.6 防止缓存雪崩：TTL 加随机抖动

问题：

如果大量 key 同时过期，短时间内会有大量请求回源计算。

解决：

- TTL 不使用完全相同的固定值。
- 加随机抖动，例如：

```text
realTTL = baseTTL + random(0, jitter)
```

建议：

- 关键词推荐：TTL 5-30 分钟。
- 网页搜索结果：TTL 5-15 分钟。
- 空结果：TTL 30-60 秒。

由于当前索引数据在线期间基本不变，也可以设置较长 TTL，但仍建议保留版本号，避免离线重建后读到旧结果。

### 5.7 缓存一致性：使用数据版本号

当前项目离线重建会覆盖：

- `dict_cn.dat`
- `dict_en.dat`
- `index_cn.dat`
- `index_en.dat`
- `pages.dat`
- `offsets.dat`
- `invert_index.dat`

在线服务启动后加载的是某一版本的数据。如果 Redis 中还保存旧版本 query 结果，就可能返回旧数据。

建议给缓存 key 加版本前缀：

```text
v:{data_version}:suggest:...
v:{data_version}:search:...
```

`data_version` 可以来自：

- 配置文件显式配置，例如 `data_version=20260626_01`。
- 离线建库生成一个 `data/index/version.txt`。
- 根据核心数据文件的 mtime 或 hash 生成。

课程项目中最简单可控的方式是新增配置：

```text
cache_version=search_engine_v3_001
```

离线重建后手动或脚本更新该值。这样旧 Redis key 会自然失效，不需要批量删除。

### 5.8 Redis 高可用与降级

如果引入 Redis，不应让 Redis 成为搜索服务的单点故障。

推荐策略：

- Redis get 设置短超时，例如 5-20ms，超时直接当未命中。
- Redis put 可以异步或失败忽略。
- Redis 异常时降级为 L1 本地缓存 + 原搜索流程。
- 使用连接池，避免每次请求创建连接。
- 每个线程或每个 shard 复用连接，减少锁竞争。
- 连续失败后熔断一段时间，避免每个请求都卡在 Redis 超时上。

生产级 Redis 高可用可以使用：

- Redis Sentinel。
- Redis Cluster。
- 主从复制。

课程项目中可以先只支持单 Redis 地址，并在代码上保证 Redis 不可用时服务仍然可用。

### 5.9 推荐的请求流程

关键词推荐：

```text
handle suggest request
  normalize query/lang/topK
  build key
  if L1 hit: return
  if L2 enabled and L2 hit:
      put L1
      return
  result = KeywordRecommender::recommend_json(...)
  put L2 with TTL
  put L1 with TTL
  return result
```

网页搜索：

```text
handle search request
  normalize query/topK/abstractLength
  build key
  if L1 hit: return
  if L2 enabled and L2 hit:
      put L1
      return
  result = WebSearcher::search_json(...)
  put L2 with TTL
  put L1 with TTL
  return result
```

### 5.10 推荐新增配置

可以在 `conf/config.conf` 中增加：

```text
# Cache.
cache_enabled=1
cache_version=search_engine_v3_001

# L1 local cache.
l1_cache_enabled=1
l1_cache_shards=32
l1_cache_capacity=4096
l1_cache_ttl_seconds=600
l1_empty_ttl_seconds=60

# L2 Redis cache.
redis_cache_enabled=0
redis_host=127.0.0.1
redis_port=6379
redis_db=0
redis_connect_timeout_ms=20
redis_command_timeout_ms=20
redis_ttl_seconds=1800
```

建议默认 `redis_cache_enabled=0`，这样第三期第一步不依赖 Redis 部署；需要二级缓存时再打开。

### 5.11 推荐代码改造顺序

1. 新增缓存接口和分片 LRU。
2. 新增 `CachedSearchService`，封装：
   - `suggest(query, lang, topK)`
   - `search(query, topK)`
3. 让 `SearchServer` 和 `WebHttpServer` 依赖 `CachedSearchService`，不直接依赖 `KeywordRecommender` / `WebSearcher`。
4. 配置化启用 L1 缓存。
5. 增加缓存命中率统计日志。
6. 再接入 Redis，实现 L2。
7. 增加 singleflight、空结果缓存、TTL 抖动。
8. 如需更高命中率，将 LRU 升级为 SLRU 或简化 W-TinyLFU。

## 总结建议

当前第二期的在线数据确实是进程内内存共享，但它是完整索引和网页库，不是缓存。第三期缓存应缓存“重复查询的最终响应”或“热点展示数据”，用更小、更热、可淘汰的数据层减少重复计算。

推荐架构是二级缓存：

- L1：进程内分片 LRU/SLRU，优先落地。
- L2：Redis，作为跨进程共享缓存，默认可配置关闭。

推荐淘汰策略：

- 工程第一版：分片 LRU + TTL。
- 进阶版：SLRU 或简化 W-TinyLFU。
- 最契合搜索引擎热点分布的算法：W-TinyLFU / Caffeine 思想。

推荐并发策略：

- 分片缓存降低锁竞争。
- 每个 shard 独立 mutex。
- 缓存最终 JSON 字符串，减少对象共享复杂度。
- 加 TTL、版本号、空结果缓存、TTL 抖动。
- Redis 只做加速层，不可用时降级，不影响主搜索流程。
