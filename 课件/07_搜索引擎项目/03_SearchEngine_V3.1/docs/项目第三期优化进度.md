## 2026-06-27：修复严格 AND 召回与部分 OOV 全失败

### 1. 优化背景

原网页搜索采用严格 AND 召回。查询包含多个有效词时，只有同时包含全部查询词的文档才能进入排序；只要有一个查询词不在倒排索引中，整条查询直接返回空结果。

例如查询：

```text
中国 qwertyuiopstrictandoovtoken
```

即使“中国”能够召回大量文档，原实现也会因为第二个词属于 OOV（未登录词）而返回空结果。多词查询同样通过 posting list 交集提前排除只命中部分关键词的相关文档，后续 TF-IDF 无法再把这些文档找回来。

### 2. 修改前逻辑

`WebSearcher::build_query_vector()`：

```text
遍历查询词
  -> 任一词不在 invertedIndex_
  -> 立即返回空 queryVector
```

`WebSearcher::find_candidate_docs()`：

```text
第一个词 posting list 作为初始候选
  -> 与后续每个词的 posting list 反复求交集
  -> 只保留包含全部查询词的文档
```

### 3. 本次设计

本次采用“忽略 OOV + 有效词 OR 召回”：

```text
查询分词
  -> 过滤停用词和无意义 token
  -> 跳过不在倒排索引中的 OOV
  -> 只使用已登录词计算查询 TF-IDF
  -> 合并所有有效词的 posting list
  -> 对候选文档执行原 TF-IDF 点积排序
```

具体规则：

- 部分词为 OOV：忽略 OOV，其他有效词继续检索。
- 全部词为 OOV：返回空结果。
- 多个有效词：文档命中任意一个词即可进入排序。
- 查询 TF 的分母只统计已登录词，OOV 不改变其他有效词的相对权重。
- 多个 posting list 使用 `std::set` 合并，自动按 docId 去重。
- 当前不引入固定 `minimum_should_match`，避免在缺少相关性评测集时再次人为压低召回。后续根据候选规模、空结果率和 NDCG/Recall 决定是否增加。

### 4. 代码修改

#### `include/online/WebSearcher.h`

- 更新 `build_query_vector()` 契约：未登录词被忽略。
- 更新 `find_candidate_docs()` 契约：候选集合来自有效词 posting list 并集。

#### `src/online/WebSearcher.cc`

- 删除任一 OOV 直接 `return {}` 的逻辑，改为 `continue`。
- 查询 TF 分母从“全部过滤后 token 数”调整为“已登录 token 数”。

- 删除不再需要的 `<iterator>` 头文件。

### 7. 行为变化与收益

- 一个错别字、新词或未登录词不再导致整条查询无结果。
- 多词查询可以返回只命中部分关键词、但仍具有相关性的网页。

- 当前排序仍使用归一化 TF-IDF，尚未迁移 BM25/BM25F。
- 当前 IDF 公式仍可能对高 DF 词产生零值或负值，本次未修改离线索引格式。
- 搜索结果缓存 key 没有独立的召回算法版本字段；本次已通过提升全局 `cache_version` 隔离旧结果。后续每次改变召回或排序语义时仍必须同步提升版本。

## 2026-06-27：离线补充 BM25 统计并将 TF-IDF 排序迁移为 BM25

### 1. 为什么离线和在线必须同时修改

原项目的 TF-IDF 分布在两个阶段：

- 离线 `PageProcessor` 统计词频和文档频率，直接计算归一化 TF-IDF double 权重并写入倒排索引。
- 在线 `WebSearcher` 为查询计算 TF-IDF 向量，再与离线文档权重做余弦点积。

BM25 需要原始 `tf`、`df`、文档长度 `dl`、平均文档长度 `avgdl` 和文档总数 `N`。旧索引只保留归一化后的权重，无法可靠反推出这些统计量。因此本次必须同时修改：

```text
离线：保存 BM25 充分统计量，不再提前计算最终分数
在线：加载统计量，按查询实时计算 BM25 分数
```

### 2. 新离线数据格式

#### `data/index/invert_index.dat`

格式从：

```text
word docId normalized_tfidf_weight ...
```

改为：

```text
word df docId tf [docId tf]...
```

其中：

- `tf` 是词项在文档中的原始出现次数。
- `df` 是 posting list 长度，即包含该词项的文档数。

#### `data/index/bm25_doc_stats.dat`

新增 BM25 文档统计文件：

```text
BM25_STATS_V1 N avgdl
docId dl
docId dl
...
```

当前重建结果：

```text
N = 3827
avgdl = 613.6004703423
文档长度记录 = 3827
倒排词项 = 96379
```

### 3. 离线代码改造

涉及：

- `include/offline/PageProcessor.h`
- `src/offline/PageProcessor.cc`
- `src/offline/offline_main.cc`

修改内容：

1. `PageProcessor::process()` 新增 BM25 文档统计输出路径。
2. `build_inverted_index()` 不再计算 TF-IDF、L2 范数和归一化权重。
3. 分词过滤后直接统计 `docTermCount[docId][word]` 作为原始 tf。
4. 统计每篇文档有效 token 数作为 dl，包括过滤后长度为 0 的文档。
5. posting list 的长度直接作为 df。
6. 使用全部去重文档计算 N 和 avgdl。
7. 输出版本化 `BM25_STATS_V1` 头，供在线阶段校验格式。

### 4. 在线 BM25 改造

涉及：

- `include/online/WebSearcher.h`
- `src/online/WebSearcher.cc`
- `src/online/online_main.cc`

在线使用公式：

```text
IDF(q) = ln(1 + (N - df(q) + 0.5) / (df(q) + 0.5))

score(q,d) = IDF(q) * tf(q,d) * (k1 + 1)
             / (tf(q,d) + k1 * (1 - b + b * dl(d) / avgdl))
```

默认参数：

```text
k1 = 1.5
b = 0.75
```

修改内容：

1. posting 类型从 `docId -> double weight` 改为 `docId -> int tf`。
2. 新增加载并校验 `BM25_STATS_V1`、N、avgdl 和逐文档 dl。
3. 校验 BM25 文档数与 `PageLibrary` 文档数一致，避免混用不同批次数据。
4. 校验倒排索引声明的 df 与实际读取 posting 数一致。
5. 删除查询 TF-IDF 向量和 L2 归一化逻辑。
6. 保留上一阶段完成的 OOV 容错与 OR 召回。
7. 对每个候选文档累加所有命中查询词的 BM25 分数。
8. BM25 IDF 使用正值平滑，高 DF 词不再产生 TF-IDF 中的零分或负分问题。

### 5. 配置和缓存版本

`conf/config.conf` 新增：

```text
bm25_doc_stats=data/index/bm25_doc_stats.dat
bm25_k1=1.5
bm25_b=0.75
```

缓存版本更新为：

```text
cache_version=search_engine_v3_003_bm25
```

该更新用于隔离旧 TF-IDF 搜索结果缓存。改变 `k1`、`b`、召回方式或排序公式时仍需更新缓存版本。

- 所有实际返回结果的 BM25 score 必须为有限正数。


### 8. 当前边界

- 当前 BM25 只索引正文，没有把标题作为独立字段；后续可升级为 BM25F。
- `k1=1.5`、`b=0.75` 是初始值，尚未基于人工相关性评测集调参。
- 当前查询中的重复词不额外放大分数，按唯一有效查询词求和。
- 当前仍对候选结果完整排序，尚未使用 topK heap 或 WAND。
- 新旧倒排索引格式不兼容，升级代码后必须先运行离线建库。

## 2026-06-27：Redis 持久连接池与 HTTP 并发/连接优化

### 1. 优化背景

此前 HTTP 端到端压测显示，稳定热点场景的主要开销不在搜索算法本身，而在：

1. HTTP 仅配置 2 个 muduo 工作线程。
2. 服务固定返回 `Connection: close`，每次请求重新建立 TCP 连接。
3. 业务回调和 muduo `TcpServer` 为连接建立/断开输出 INFO 日志。
4. `RedisCache` 每条 GET/SET/DEL 命令都重新连接 Redis。

本次改造同时处理这四个问题，避免只优化其中一层后由另一层继续限制端到端性能。

### 2. Redis 持久连接池

涉及：

- `include/cache/RedisCache.h`
- `src/cache/RedisCache.cc`
- `src/online/online_main.cc`

实现规则：

```text
缓存操作
  -> 从池中独占借出 hiredis context
  -> 执行一条同步命令
  -> 健康：归还池中
  -> reply/context 异常：关闭并移出池
  -> 后续请求惰性补建连接
```

具体设计：

- 连接池惰性创建，`RedisCache` 构造时不强制 Redis 可用。
- 使用 `totalConnections_` 预留计数，多个线程在锁外并行建连但不会突破容量。
- 每条连接同一时刻只借给一个线程，避免并发使用非线程安全的 hiredis context。
- 空闲连接保存在池中，复用 TCP、命令超时设置和 `SELECT` 结果。
- 池耗尽时通过条件变量限时等待，不无限阻塞 muduo 工作线程。
- 建连失败、命令返回空 reply 或 context 错误时丢弃连接。
- Redis 不可用时仍保持原有降级语义：GET 视为 miss，PUT/DEL 静默失败。

新增配置：

```text
redis_pool_size=16
redis_pool_wait_timeout_ms=20
```

默认池大小 16，可覆盖当前 8 个 HTTP 线程和 4 个 TLV 线程的并发缓存访问，并保留余量。

### 3. HTTP keep-alive 与请求循环

涉及：

- `include/online/WebHttpServer.h`
- `src/online/WebHttpServer.cc`

修改内容：

1. 解析并校验 HTTP/1.0、HTTP/1.1 版本。
2. HTTP/1.1 默认 keep-alive，`Connection: close` 显式关闭。
3. HTTP/1.0 默认关闭，`Connection: keep-alive` 可显式复用。
4. 响应头根据请求输出 `Connection: keep-alive` 或 `close`。
5. `on_message()` 循环处理 Buffer 中已经到达的多条请求，支持同连接连续请求。
6. 非 keep-alive 请求发送响应后才 `shutdown()`。
7. 增加请求总大小限制，防止请求头无限增长或伪造超大 Content-Length。

新增配置：

```text
http_max_request_size=1048576
```

### 4. HTTP 工作线程

配置从：

```text
http_threads=2
```

调整为：

```text
http_threads=8
```

代码默认值也同步改为 8，并对小于等于 0 的非法配置回退为 8。当前搜索回源可能同步读取文档、生成摘要和访问 Redis，8 个线程能降低 2 线程下的排队，但线程数并非越大越好，仍应按 CPU、阻塞比例和 P99 实测调整。

### 5. 消除逐连接 INFO 日志

最初只把 `WebHttpServer` 和 `SearchServer` 回调中的 `LOG_INFO` 改成 `LOG_DEBUG`。端到端验证发现 muduo `TcpServer` 内部仍会在建立和删除连接时打印 INFO，因此进一步增加全局配置：

```text
muduo_log_level=WARN
```

服务启动时调用 `muduo::Logger::setLogLevel()`。默认 WARN 会同时抑制业务回调和框架内部的逐连接 INFO；排障时仍可改为 TRACE、DEBUG、INFO 或 ERROR。

### 6. 压测工具改造

`tests/http_load/http_load_test.py` 原来在每次请求中创建并关闭 `HTTPConnection`，无法验证服务端 keep-alive。

现在每个并发 worker 默认持有一条连接并循环复用：

```bash
--connection-mode keep-alive  # 默认
--connection-mode close       # 短连接对照
```

结果 JSON 增加 `connection_mode`，报告必须注明连接模式、HTTP 线程数和 Redis 池大小。

### 7. 本次端到端验证

环境：本机回环、Redis 开启、W-TinyLFU、8 个热点查询、100 次预热、1000 次正式请求、并发 32。两组使用同一服务进程，属于功能与方向性对照，不是严格统计报告。

### 10. 当前边界

- Redis 使用同步 hiredis，尚未实现 pipeline 或异步命令。
- 连接池没有熔断器；Redis 持续故障时仍会按请求尝试惰性重建。
- 当前未分别统计连接池等待/超时、创建/复用/丢弃次数。
- keep-alive 没有独立空闲超时和每连接最大请求数，依赖 muduo/TCP 生命周期。
- HTTP 仍是课程项目的最小解析器，不支持 chunked request、完整管线化错误隔离等通用能力。
- 工作线程从 2 调到 8 的收益需要用多轮、交叉顺序和真实查询分布继续验证。

## 2026-06-27：接入 spdlog 统一异步滚动日志

### 1. 优化目标

原代码混用 `std::cout/std::cerr` 和 muduo 日志，存在以下问题：

- 离线建库只有零散进度文本，没有统一时间、级别、线程和阶段耗时。
- 在线启动、缓存统计、协议异常分散在不同输出方式中。
- 缺少 HTTP/TLV 请求耗时、搜索内部阶段耗时和慢请求识别。
- 没有文件滚动和保留上限。
- Redis 故障静默降级，排障时缺少原因。
- 如果对每个请求都打印 INFO，会重新成为端到端性能瓶颈。

本次目标是建立足够实用但不过度复杂的日志体系，不引入 request tracing、远程日志平台或复杂结构化日志框架。

### 2. 日志模块

新增：

- `include/common/Logger.h`
- `src/common/Logger.cc`

`AppLogger` 统一创建：

```text
彩色控制台 sink
  + rotating_file_sink
  + 1 个异步后台线程
  + 有界队列
```

默认策略：

```text
单文件上限：20 MiB
滚动文件数：5
异步队列：8192
WARN 及以上立即 flush
每 3 秒周期 flush
队列满：阻塞生产者，不丢失错误日志
```

日志格式：

```text
时间 [级别] [线程] 消息与 key=value 上下文
```

例如：

```text
2026-06-27 22:57:23.867 [info] [thread 78021]
HTTP server listening address=0.0.0.0:18888 threads=8 keep_alive=true
```

### 3. 配置

`conf/config.conf` 新增：

```text

log_dir=logs
log_max_file_size_mb=20
log_max_files=5
log_async_queue_size=8192
slow_request_ms=200
```

生成文件：

```text
logs/offline_builder.log
logs/search_server.log
```

默认 INFO 不记录普通逐请求详情。需要分析单请求阶段时临时改为 DEBUG；超过
`slow_request_ms` 的请求即使在 INFO 配置下也会记录 WARN。

### 4. 离线日志设计

涉及：

- `src/offline/offline_main.cc`
- `src/offline/KeywordProcessor.cc`
- `src/offline/PageProcessor.cc`

INFO 记录：

- 整体建库开始、结束和总耗时。
- 英文词典、英文字符索引、中文词典、中文字符索引的阶段耗时。
- 网页提取、SimHash 去重、网页/偏移库、BM25 索引的阶段耗时。
- 输入文件数、原始 item 数、有效文档数、去重文档数、词项数、N 和 avgdl。

WARN 记录损坏 XML 的文件路径和 tinyxml2 错误码；不可恢复异常由入口记录 CRITICAL。

本次实际离线日志确认：

```text

chinese_dictionary             215 ms
chinese_character_index         33 ms
extract_documents              356 ms
deduplicate_documents         6326 ms
pages_and_offsets              319 ms

offline total               19676 ms
```

这些数据也再次表明当前离线主要耗时集中在 O(n²) SimHash 去重和 BM25 分词/建索引。

### 5. 在线日志设计

#### INFO

- 在线初始化。
- L1 策略、容量、分片和 TTL。
- Redis 地址、DB、连接池大小和等待超时。
- TLV/HTTP 监听地址与工作线程数。
- 周期缓存命中统计。

#### DEBUG

- 客户端连接/断开。
- 普通 HTTP/TLV 请求完成信息：协议、客户端、方法/消息类型、请求大小和耗时。
- 网页搜索阶段：`tokenize_us`、`recall_us`、`rank_us`、`render_us`、`total_us`。

DEBUG 日志只记录 query/body 字节数和有效词数量，不主动记录原始查询文本。

#### WARN

- HTTP/TLV 请求解析或业务处理异常，包含客户端、路径/类型、缓冲区大小和错误原因。
- 超过 `slow_request_ms` 的慢请求。
- Redis 获取连接或命令失败。

Redis 故障只记录第一次以及每累计 100 次故障，避免 Redis 宕机时每请求刷一条日志。

#### CRITICAL

- 离线建库或在线服务启动失败。

### 6. muduo 日志统一

muduo 仍保持默认 WARN 级别，避免逐连接 INFO。其 WARN 及以上输出通过
`Logger::setOutput()` 桥接到 spdlog，flush 也桥接到默认 logger，因此在线进程不再维护两套长期日志出口。

### 7. 构建依赖

CMake 新增：

```cmake
find_package(spdlog REQUIRED)
target_link_libraries(... spdlog::spdlog)
```

系统依赖为：

```text
libspdlog-dev
libfmt-dev
```

### 9. 当前边界

- 当前采用可读的 key=value 文本日志，没有引入 JSON 日志。
- 没有 request_id、分布式 tracing 或远程日志采集；当前单进程课程项目暂不需要。
- 缓存统计仍按固定请求间隔输出 INFO，后续可以迁移到 Prometheus metrics。
- 慢请求计时覆盖业务处理和响应入发送缓冲区，不代表客户端完整接收耗时。
- 错误日志尚未实现所有错误类型的独立限流，Redis 故障已做简单采样。
