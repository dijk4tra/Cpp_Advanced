# 搜索引擎第三期 HTTP 压测报告 - V3.1

## 1. 结论摘要

本轮直接启动 V3.1 `search_server`，使用项目自带 Python HTTP 客户端进行本机回环压测。
与旧版 V3 报告相比，结果如下：

- 稳定热点、并发 32 时，网页搜索 QPS 从 `665.80` 提升到 `1015.54`，提升 `52.53%`；
  P95 从 `87.028 ms` 降到 `67.421 ms`。
- 稳定热点、并发 32 时，关键词推荐 QPS 从 `692.06` 提升到 `1410.41`，提升
  `103.80%`；P95 从 `83.743 ms` 降到 `52.797 ms`。
- 在与旧报告相同的 `L1 capacity=100 / 32 分片 / Redis 开启 / 并发 32` 扫描条件下，
  QPS 从 `762.06` 提升到 `1516.50`，提升 `99.00%`；P50/P95/P99 分别下降
  `54.32% / 38.30% / 32.61%`。
- V3.1 内部对照显示，并发 32 时 keep-alive 相比短连接，搜索 QPS 提升
  `45.22%`，推荐 QPS 提升 `87.36%`。
- 18,600 个扫描 HTTP 请求期间，Redis 执行命令增加 `36,243`，但 TCP 连接仅增加
  `8`。Redis 持久连接池已消除“每命令建连”。
- `http_threads=8` 并非本机最优值。在 8 vCPU 虚拟机和当前 Python 压测端下，
  并发 32 的热点测试中 2 线程反而最快。线程数应按环境调优，不应认为越多越好。

综合看，本轮收益主要来自 HTTP keep-alive、关闭逐连接 INFO 日志和 Redis 连接池。
“旧 V3 只有两个 HTTP 线程”并不足以单独解释旧瓶颈，本轮线程数对照已对该判断进行了修正。

## 3. V3 与 V3.1 差异

| 项目 | 旧 V3 报告 | V3.1 本轮 |
| --- | --- | --- |
| HTTP 工作线程 | 2 | 正式配置 8，额外对照 2/4/8 |
| HTTP 连接 | 每请求 `Connection: close` | 默认 HTTP/1.1 keep-alive |
| 连接日志 | muduo 逐建连/断连 INFO | muduo WARN，业务逐连接日志为 DEBUG |
| 业务日志 | 分散在 cout/cerr/muduo | spdlog 异步控制台 + 滚动文件 |
| Redis | 每条命令新建连接 | 惰性持久连接池，上限 16 |
| 网页召回 | 严格 AND | 忽略 OOV + OR 召回 |
| 网页排序 | TF-IDF | BM25 |

## 4. 测试方法与公平性

### 4.1 统计方式

- 每个正式条件运行 3 次，报告 QPS、P50、P95、P99 和 Max 的三轮中位数。
- 稳定热点每轮预热 200 请求，正式计量 3000 请求。
- 旧 V3 报告每个条件只运行 1 次、计量 1500 请求；因此旧新百分比用于判断方向和数量级，
  不是严格统计置信区间。
- 正式计量共 163,500 个 HTTP 请求，额外预热 8400 个请求；全部完成，
  错误为 0，非 2xx 为 0。

### 4.2 测试配置

默认测试使用正式 V3.1 配置：

```text
HTTP threads：8
L1：W-TinyLFU，capacity=4096，shards=32
Redis L2：开启，pool_size=16
log_level：info
muduo_log_level：WARN
cache_stats_log_interval：100
```

扫描对照在 `/tmp/searchengine_v31_http_bench/` 中建立临时运行目录，复用同一二进制和数据，
仅将 `l1_cache_capacity` 调为旧报告的 100，不修改项目正式配置。

### 4.3 工作负载

1. 稳定热点：`sample_queries.txt` 的 8 行、6 个不同 query，分别请求 `/api/search`
   和 `/api/suggest`，并发度 1/8/32/64。
2. 连接模式对照：V3.1 服务保持不变，并发 32，客户端分别使用 keep-alive 和 close。
3. 扫描污染：与旧报告相同形状的 6200 请求，包含 20 个热点、4000 个单次 query，
   理论最高命中率 35.16%。每轮使用新 namespace，避免 Redis 复用旧结果。
4. singleflight：同一个全新 query，300 请求，并发 32，不预热。
5. 线程数：V3.1 keep-alive、并发 32，分别使用 2/4/8 个 HTTP 工作线程。

## 7. keep-alive 与短连接对照

配置和服务端完全相同，仅改变客户端 `Connection` 模式。并发度为 32。

| 接口 | 模式 | QPS | P50 ms | P95 ms | P99 ms |
| --- | --- | ---: | ---: | ---: | ---: |
| search | close | 699.32 | 43.297 | 88.262 | 114.484 |
| search | keep-alive | 1015.54 | 28.132 | 67.421 | 87.092 |
| suggest | close | 752.80 | 39.457 | 83.386 | 105.788 |
| suggest | keep-alive | 1410.41 | 19.598 | 52.797 | 73.107 |

keep-alive 相比 close：

```text
search： QPS +45.22%，P50 -35.03%，P95 -23.61%，P99 -23.93%
suggest：QPS +87.36%，P50 -50.33%，P95 -36.68%，P99 -30.89%
```

V3.1 切回短连接后，并发 32 的搜索 QPS `699.32` 与旧 V3 的 `665.80` 只相差约 5%；
这一对照证明 keep-alive 是热点路径吞吐提升的主要来源之一。

## 8. HTTP 工作线程数对照

条件：keep-alive、并发 32、稳定热点，每个条件三轮中位数。

| 接口 | HTTP 线程 | QPS | P50 ms | P95 ms | P99 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| search | 2 | 1057.40 | 26.509 | 64.219 | 82.393 |
| search | 4 | 1039.01 | 27.975 | 65.907 | 86.169 |
| search | 8 | 1015.54 | 28.132 | 67.421 | 87.092 |
| suggest | 2 | 1605.56 | 17.049 | 48.035 | 66.495 |
| suggest | 4 | 1448.15 | 18.734 | 50.580 | 70.015 |
| suggest | 8 | 1410.41 | 19.598 | 52.797 | 73.107 |

本机上 2 线程的中位数最好，4 线程次之，8 线程没有带来收益。这不表示所有部署都应改回 2，
原因包括：

1. 服务端和 32 个 Python 客户端线程共享同一台 8 vCPU 虚拟机。
2. 稳定热点基本全部命中 L1，单次业务很短，过多工作线程只增加调度和锁竞争。
3. 真实生产若存在慢 Redis、文件 I/O 或更多冷搜索，较多线程才可能通过隐藏等待提升吞吐。

因此，V3.1 的 `http_threads=8` 保证了 I/O 等待场景的容量，但不是本测试机热点负载的最优值。
建议将 4 作为当前 8 vCPU 环境的保守起点，再使用真实流量测试 2/4/8，而不是固定认为 8 最优。

V3.1 的 Max 中位数高于旧 V3，但 Max 是单个调度尖峰，不具有 P95/P99 的稳定性。

另一组正式容量 4096 的三轮扫描前后，Redis `INFO stats` 差值为：

```text

keyspace_misses：          +24,120
keyspace_hits：                +62

```

命令数主要来自首次 Redis GET、singleflight owner 的二次检查以及空结果 SETEX。
在 36,243 条命令下只新建 8 条连接，与 8 个 HTTP 工作线程相符，说明 Redis 连接池正常复用。

## 11. 原结论的验证与修正

| 旧 V3 判断 | V3.1 实测 | 结论 |
| --- | --- | --- |
| HTTP 短连接是瓶颈 | keep-alive 使 QPS 提升 45%~87% | 验证 |
| 逐连接 INFO 日志开销大 | V3.1 默认不输出逐连接日志，吞吐明显提升 | 方向验证，未单独量化 |
| Redis 每命令短连接是瓶颈 | 36,243 命令仅增加 8 连接 | 连接池改造已生效 |
| HTTP 只有 2 个工作线程是主要瓶颈 | keep-alive 下 2 线程不慢于 4/8 | 需修正：线程数不是该工作负载的首要因素 |
| W-TinyLFU 差异被 HTTP/Redis 开销掩盖 | 本轮未重复 LRU 对照，专注网络与 Redis 改造 | 本报告不改变旧结论 |

## 12. 限制与后续建议

1. Python `http.client` + 线程模式会受 GIL 和本机调度影响。下一轮若需确定服务端极限，
   应使用独立压测机上的 `wrk`/`h2load` 或 C++ 异步客户端。
2. 旧报告只有单轮数据，本轮是三轮中位数；百分比不是完全对称的 A/B 试验。
3. BM25、OR 召回和摘要长度会改变搜索计算和响应内容；稳定热点命中缓存时影响较小，
   冷搜索对比则不能只归因于 HTTP。
4. 建议为缓存统计增加 L1 hit、L2 hit、Redis latency 和 pool wait 分层指标。
5. 建议使用真实脱敏 query 重放调优 `http_threads`，并分别测试高命中、Redis 命中、
   文档回源和 CPU 密集型 BM25 路径。
6. 当前还没有 Redis 熔断器。Redis 长时间故障时，连接池会按请求重试建连，需要单独进行故障压测。

## 13. 复现命令

启动服务：

```bash
./bin/search_server
```

稳定热点：

```bash
python3 tests/http_load/http_load_test.py \
  --mode search \
  --query-file tests/http_load/sample_queries.txt \
  --requests 3000 \
  --concurrency 32 \
  --warmup 200 \
  --connection-mode keep-alive
```

短连接对照：

```bash
python3 tests/http_load/http_load_test.py \
  --mode search \
  --requests 3000 \
  --concurrency 32 \
  --warmup 200 \
  --connection-mode close
```

扫描流量：

```bash
python3 tests/http_load/http_load_test.py \
  --mode search \
  --workload scan \
  --scan-namespace v31_scan_round_1 \
  --requests 6200 \
  --concurrency 32 \
  --warmup 0 \
  --connection-mode keep-alive
```

singleflight：

```bash
python3 tests/http_load/http_load_test.py \
  --mode search \
  --query v31_singleflight_new_key \
  --requests 300 \
  --concurrency 32 \
  --warmup 0 \
  --connection-mode keep-alive
```

每轮扫描和 singleflight 必须使用全新 namespace/query，或修改 `cache_version`，否则 Redis 中的旧结果
会把冷路径变成热路径。
