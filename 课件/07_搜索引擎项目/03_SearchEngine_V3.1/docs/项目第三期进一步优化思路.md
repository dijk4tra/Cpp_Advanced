# 搜索引擎项目第三期进一步优化思路（V3.1）

## 1. 文档目标与结论

本文基于 `03_SearchEngine_V3.1` 当前代码、配置、离线数据和已有压测报告，评估下一阶段可以进行的优化。本文讨论的是搜索引擎项目，而不是通用网盘系统。

先给出结论：

| 方向 | 是否建议 | 优先级 | 核心结论 |
| --- | --- | --- | --- |
| SimHash 去重 | 建议优化实现，不建议立即替换算法 | P1 | 当前主要问题是 O(n²) 全量比较、正文未去模板和“保留第一篇”的质量策略，不是 64 位 SimHash 本身 |
| 词典/偏移/倒排索引存数据库 | 当前不建议作为性能优化 | P3 | 当前数据量小且索引已常驻内存；数据库查询会增加序列化、网络或 B-Tree/LSM 查找开销 |
| 二进制化、压缩、mmap/pread | 建议 | P1/P2 | 比“迁数据库”更符合只读搜索索引的访问模式，可降低启动时间、内存和文档随机读取成本 |
| TF-IDF 改 BM25 | 已完成 | P1（已完成） | V3.1 已保存 tf/df/dl/N/avgdl 并在线计算 BM25；后续可继续升级 BM25F |
| 严格 AND 召回 | 已完成第一阶段修复 | P0（已完成） | V3.1 已改为忽略 OOV 并对有效词执行 OR 召回；后续可按评测结果增加 `minimum_should_match` |
| 编辑距离推荐 | 建议分阶段优化 | P1/P2 | 先修归一化和复杂度，再按“前缀补全/拼写纠错”拆分场景；不应只替换一个距离公式 |
| 日志模块 | 已完成 | P0（已完成） | 已接入 spdlog 异步控制台/滚动文件，覆盖离线阶段、在线请求、慢请求和异常上下文 |
| Redis 连接方式 | 已完成 | P0（已完成） | V3.1 已改为有上限的惰性持久连接池，异常连接丢弃重建 |

推荐的实施顺序不是直接把所有算法替换掉，而是：

```text
建立相关性评测集和性能基线
  -> 修复召回并迁移 BM25（已完成）
  -> 接入统一日志和指标
  -> 改造离线索引格式并实现 BM25/BM25F
  -> 优化文档去重候选查找
  -> 优化推荐召回与排序
  -> 数据规模增长后再决定是否引入专用存储系统
```

## 2. 当前实现基线

### 2.1 离线链路

当前 `offline_builder` 顺序执行两条链路：

```text
中英文语料
  -> 词频词典 dict_cn.dat / dict_en.dat
  -> 字符到词典行号索引 index_cn.dat / index_en.dat

网页 XML
  -> 提取 item
  -> SimHash 去重
  -> pages.dat + offsets.dat
  -> BM25 原始词频倒排索引 invert_index.dat
  -> BM25 文档统计 bm25_doc_stats.dat
```

关键实现：

- `KeywordProcessor.cc` 用 `std::map` 统计词频并按字典序输出；字符索引记录词典物理行号。
- `PageProcessor.cc` 只使用正文 `content/description` 计算 SimHash 和搜索索引，标题没有进入索引。
- 每篇文档的 SimHash 与此前所有已保留文档逐一比较，汉明距离不超过 3 即删除。
- 倒排项保存 `df + docId/tf`，文档统计库保存 `N/avgdl/docId/dl`，在线可完整计算 BM25。

### 2.2 在线链路

当前在线进程启动时：

- 全量加载中英文词典和字符索引。
- 全量加载倒排索引到 `unordered_map<string, unordered_map<int, double>>`。
- 只加载网页偏移表；网页正文按 `docId` 打开 `pages.dat`、seek、读取并解析 XML。
- L1 使用分片 W-TinyLFU（可回退 LRU），L2 可使用 Redis。
- 搜索结果、推荐结果、文档和动态摘要均可缓存。

网页搜索执行过程为：

```text
查询分词
  -> 过滤 OOV 并执行 OR 召回
  -> 忽略 OOV，对有效查询词 posting list 求并集
  -> 余弦相似度排序
  -> 按偏移读取网页
  -> 生成动态摘要
```

关键词推荐执行过程为：

```text
查询按字符拆分
  -> 合并每个字符对应的词典行号
  -> 对全部候选计算 Levenshtein 编辑距离
  -> 距离升序、词频降序、字典序排序
```

### 2.3 当前数据规模

仓库中现有离线数据约为：

| 数据 | 当前规模 |
| --- | ---: |
| 去重后网页数 | 3,827 |
| `pages.dat` | 约 20 MiB |
| `invert_index.dat` | 约 8.1 MiB，96,379 个词项行（BM25 整数 tf） |
| `bm25_doc_stats.dat` | 约 36 KiB，3,827 条文档长度记录 |
| `offsets.dat` | 约 68 KiB |
| 中文词典 | 17,040 词，约 168 KiB |
| 英文词典 | 34,705 词，约 376 KiB |
| 中文字符索引 | 约 216 KiB |
| 英文字符索引 | 约 1.3 MiB |

这个规模下，词典、偏移和倒排索引全量加载内存是合理设计。当前应优先改善相关性、索引内存布局和 I/O，而不是引入数据库网络跳转。

## 3. 在更换算法前应先修复的问题

### 3.1 严格 AND 召回问题（V3.1 已完成第一阶段修复）

原实现中，`WebSearcher::build_query_vector()` 在任一查询词不在倒排索引时直接返回空向量，`find_candidate_docs()` 又对全部 posting list 求交集。其实际语义是：

> 文档必须包含每一个查询词，否则完全不参与排序。

问题包括：

1. 一个未登录词会让其他有效词全部失效。
2. 分词粒度与离线不一致时容易返回空结果。
3. 自然语言长查询包含的词越多，交集越容易为空。
4. BM25 即使计算得更准确，也无法给未被召回的文档排序。

V3.1 已完成以下改造：

- `build_query_vector()` 跳过 OOV，只使用已登录词计算查询 TF-IDF。
- 查询 TF 分母只统计已登录词，OOV 不会改变其他有效词的相对权重。
- `find_candidate_docs()` 改为合并所有有效词的 posting list。
- 只有全部查询词均为 OOV，或查询向量无法归一化时才返回空结果。
- 新增 `web_searcher_recall_test`，验证部分 OOV 容错和多词 OR 并集语义。

当前采用纯 OR 召回。后续数据规模增大、候选集过宽时，再评估 `minimum_should_match`：

- 短查询默认至少命中 1 个有效词。
- 3 个及以上查询词可要求命中 60%~80%，具体值通过评测确定。
- 未登录词忽略并记录 OOV 指标，不让整条查询失败。
- 排序分数自然奖励命中更多查询词的文档，必要时额外增加 coordination bonus。

如果候选过多，按 DF 从稀有词开始遍历，使用 topK 小根堆；规模继续增长后再实现 WAND/Block-Max WAND，而不是恢复严格 AND。

### 3.2 TF-IDF IDF 零权重/负权重问题（已随 BM25 迁移解决）

原 TF-IDF 离线和在线都使用：

```text
IDF = log2(N / (DF + 1))
```

当 `DF = N - 1` 时 IDF 为 0；当 `DF = N` 时 IDF 为负。负权重再做 L2 归一化和余弦点积，语义不直观，也可能让高频词对相似度产生反向影响。

当前已切换为 BM25 正值平滑 IDF：

```text
IDF = ln(1 + (N - df + 0.5) / (df + 0.5))
```

离线只保存 df，在线统一计算上述 IDF，因此不再存在离线/在线 TF-IDF 公式不一致问题。

### 3.3 标题没有参与检索

当前 `PageProcessor::build_inverted_index()` 只对 `doc.content` 分词。标题只用于结果展示。这意味着“查询词只出现在标题”时文档不会被召回，而标题通常是网页最重要的相关性信号。

建议：

- 最低成本方案：把标题词频乘固定 boost 后合并到正文词频。
- 更完整方案：实现 BM25F，分别保存标题和正文的 `tf/dl`，给标题更高权重。

BM25F 比简单拼接标题更可控，因为短标题不会被长正文长度归一化稀释。

### 3.4 建索引前缺少正文清洗

动态摘要会清理 HTML，但建倒排索引和计算 SimHash 时直接使用原始 `content`。如果语料正文包含标签、导航、版权信息或模板片段，会造成：

- 模板词进入倒排索引。
- 同站网页因共享导航而被误判为相似。
- 文档长度被 HTML 和模板噪声放大。

建议离线统一增加 `DocumentNormalizer`：HTML 实体解码、标签移除、空白归一化、站点模板/版权块清理。去重、索引和摘要应尽量共享同一套规范化规则，并通过版本号避免新旧产物混用。

## 4. 离线优化一：文档去重

### 4.1 是否有必要替换 SimHash

现阶段没有足够证据证明需要直接换掉 SimHash。SimHash 擅长发现长文本的近似重复，64 位指纹配合小汉明距离适合新闻转载和少量编辑场景。当前实现的主要瓶颈和质量问题是：

1. 候选查找为 O(n²)。
2. 正文没有先清除 HTML/模板噪声。
3. 阈值 3 是固定经验值，没有标注集验证。
4. 每组相似文档简单保留最先出现的一篇，没有考虑标题、正文长度、链接完整性和来源质量。
5. 没有先做廉价的精确去重。

当前只有 3,827 篇文档，O(n²) 尚可运行；但当文档达到 10 万或百万级后，该实现不可扩展。

### 4.2 推荐方案：精确去重 + 分桶 SimHash

第一阶段先做精确去重：

```text
规范化正文 -> 稳定内容哈希 -> 相同哈希只保留质量最好的一篇
```

这里应使用稳定哈希实现，不能把 `std::hash<string>` 当作跨版本持久化格式。可选 SHA-256（冲突风险最低）或 xxHash/BLAKE3（更快）。

第二阶段继续使用 SimHash，但不要和全部历史指纹比较。阈值为 3 时，可把 64 位指纹切成 4 个 16 位块。根据抽屉原理，两个指纹汉明距离不超过 3 时，至少有一个块完全相同。因此可以：

1. 为 4 个块分别建立 `blockValue -> docIds` 桶。
2. 新文档只召回至少一个块相同的候选。
3. 对候选计算真实 64 位汉明距离，避免分桶假阳性。
4. 对重复集合选择质量最高的代表文档，而不是固定保留第一篇。

该方案保持现有“汉明距离 <= 3”的判定语义，同时把典型候选量从全库缩小到少量桶内文档。最坏情况仍可能因热门块退化，因此需要记录桶大小并对超大桶做二次切分或长度过滤。

建议在比较 SimHash 前加入正文长度比过滤，例如长度差异过大的文档不比较；阈值必须由标注数据确定，不能直接把经验值改得更大。

### 4.3 何时考虑 MinHash/LSH

如果实际重复样本具有以下特征，可以评估基于词/字符 shingle 的 MinHash + LSH：

- 大段落重排。
- 文档只共享若干局部段落。
- 页面模板差异较大，但正文集合重合明显。

MinHash更接近 Jaccard 相似度，解释性更好，但需要保存多个哈希值，内存与实现复杂度高于单个 SimHash。推荐做法不是凭直觉替换，而是在同一标注集上比较：

- duplicate precision / recall / F1。
- 每万篇处理时间。
- 峰值内存。
- 被误删文档示例。

### 4.4 代表文档质量评分

对同一重复簇，建议按以下字段选择保留文档：

```text
title 非空 + link 合法 + 正文有效字符数 + 来源优先级 - 模板占比 - 异常字符占比
```

这不会直接提升去重速度，但能避免“先扫描到的低质量网页覆盖后续完整网页”。

### 4.5 预期提升

- 数据规模小时：搜索结果中的重复项更少，去重时间略有下降。
- 数据规模大时：分桶后平均候选比较量显著下降，避免 O(n²) 成为离线建库瓶颈。
- 正文清洗和质量选优会比盲目更换指纹算法更直接地改善去重准确率。

不应在没有真实重复标注集时承诺固定百分比提升。

## 5. 离线优化二：数据是否存入数据库

### 5.1 为什么当前不应迁移热索引

当前词典、字符索引、偏移表和倒排索引在启动后都是进程内只读结构。查询一个词只需要哈希查找和内存遍历。把它们迁移到 MySQL/PostgreSQL/Redis 后，热路径会增加：

- 客户端协议和序列化/反序列化。
- 网络或 Unix socket 往返。
- 数据库连接池与超时管理。
- B-Tree/LSM/哈希表的额外查找。
- posting list 多行返回与对象构造。

因此，“放数据库”可以改善数据管理能力，但通常不会提升当前单机搜索性能。

尤其不建议把一条 posting 拆成数据库中的多行 `(term, doc_id, weight)` 后在线查询。一个高频词可能返回大量行，数据库行格式和网络传输开销会远大于连续压缩 posting list。

### 5.2 不同数据的建议归宿

| 数据 | 当前建议 | 原因 |
| --- | --- | --- |
| 原始网页、抓取状态、来源、更新时间 | 可存关系数据库或对象存储 | 需要增删改查、审计和增量处理 |
| 词典与词频 | 小规模继续内存加载 | 体积很小，在线随机访问频繁 |
| 字符推荐索引 | 内存或紧凑二进制文件 | 只读，多次随机访问 |
| 网页偏移表 | 改为连续 `vector` 或 mmap 数组 | docId 连续，`unordered_map` 没有必要 |
| 倒排索引 | 压缩二进制文件 + mmap/内存 | 连续扫描 posting 性能最好 |
| 网页正文 | 顺序文档文件/对象存储；热点缓存 | 大对象不应全量复制到普通关系表热路径 |
| 查询日志和点击日志 | 数据库/日志平台 | 需要聚合分析和训练排序信号 |
| 搜索结果缓存 | 当前 L1 + Redis | 是 Redis 适合的场景 |

### 5.3 比数据库更值得做的存储优化

#### 5.3.1 偏移表改为连续数组

离线去重后 docId 从 1 连续编号。当前 `PageLibrary` 却使用 `unordered_map<int, PageOffset>`，会产生 bucket、节点和指针开销。可以直接保存：

```cpp
std::vector<PageOffset> offsets; // offsets[docId]
```

查找变为一次数组寻址，并减少内存碎片。

#### 5.3.2 倒排索引改为二进制 CSR/词典 + posting 区

当前文本格式易读但启动解析慢，`unordered_map<int,double>` 为每个 posting 产生较大对象开销。建议格式：

```text
索引头：magic、format_version、corpus_version、N、avgdl、tokenizer_version
词项表：term、df、posting_offset、posting_length
posting 区：delta_docId、tf、可选 field_tf
文档表：docId、dl、title_dl、page_offset、page_length
```

可使用：

- docId 差分编码 + VarInt。
- `tf` 使用无符号整数。
- 元数据定长对齐或 FlatBuffers/自定义二进制格式。
- mmap 词项表和 posting 区，按需触页。

BM25 在查询时计算分数，不需要离线保存 double 权重。这样通常比当前节点式哈希结构节省大量内存，并缩短启动解析时间。

#### 5.3.3 文档读取使用 mmap/pread 和紧凑格式

当前每个未缓存文档都要：打开文件、seek、读取 XML、解析 XML、关闭文件。建议至少使用 `pread` 复用文件描述符；进一步可 mmap `pages.dat`。文档记录也可从 XML 改为长度前缀二进制结构，避免每次 tinyxml2 解析。

如果继续保留 XML 作为可读产物，可以同时生成一个在线专用二进制文档库。

### 5.4 何时数据库才有必要

满足以下需求时再引入数据库：

- 文档持续在线更新，无法整库重建发布。
- 多个离线任务需要共享抓取状态和版本元数据。
- 需要按来源、时间、权限进行事务性管理。
- 单机文件无法承载数据量，需要分片和副本。

即便如此，也建议使用数据库管理原始数据和索引版本，在线检索仍使用专用倒排索引。若需求已经包括实时写入、分布式检索、副本、聚合和高亮，直接评估 Elasticsearch/OpenSearch，比在关系数据库上重新实现搜索引擎更合理。

## 6. 在线优化一：从 TF-IDF 迁移到 BM25（BM25 已完成，BM25F 待实现）

### 6.1 是否有必要

BM25 迁移已经完成。原 TF-IDF 存在三个明显限制：

1. 词频与相关性线性增长，没有饱和机制。
2. 文档长度只通过 `tf=count/totalWords` 处理，对长短文档的校正不够灵活。
3. 标题和正文无法分字段加权。

BM25通过词频饱和和长度归一化，通常更适合网页检索。但它不是召回算法的替代品，因此本项目已同时完成严格 AND 到 OR 召回的改造。

### 6.2 BM25 需要新增的离线信息

标准 BM25 单词项得分可写为：

```text
IDF(q) = ln(1 + (N - df(q) + 0.5) / (df(q) + 0.5))

score(q, d) = IDF(q) *
              tf(q,d) * (k1 + 1) /
              (tf(q,d) + k1 * (1 - b + b * dl(d) / avgdl))
```

离线必须提供：

- `N`：有效文档数。
- `df(term)`：包含词项的文档数，可保存在词项表。
- `tf(term, doc)`：词项在文档中的原始出现次数。
- `dl(doc)`：文档有效 token 数。
- `avgdl`：全库平均文档长度。
- 如果实现 BM25F，还要保存标题/正文各自的 `tf` 和长度。

当前索引已改为保存 `word df docId tf...`，并新增 `bm25_doc_stats.dat` 保存 `N/avgdl/docId/dl`。旧归一化 TF-IDF double 权重格式已经移除，离线数据已重建。

### 6.3 离线改造建议

将 `PageProcessor::build_inverted_index()` 拆成三个职责：

1. `DocumentAnalyzer`：清洗、分词、停用词过滤，输出标题/正文 token。
2. `IndexBuilder`：统计 `tf/df/dl/avgdl` 并构造 posting。
3. `IndexWriter`：按版本化二进制格式落盘。

不要继续在一个函数中同时完成分词、统计、打分、归一化和文本序列化。BM25 的分数依赖查询参数，离线只保存充分统计量，在线再计算得分。

索引元数据至少包含：

```text
format_version
corpus_version
document_count
average_document_length
tokenizer/dictionary version
stopword version
normalizer version
build timestamp
```

服务启动时校验 magic、版本、文件长度和 checksum，失败时拒绝启动，不要加载半套索引。

### 6.4 在线检索改造建议

推荐流程：

```text
查询规范化/分词
  -> 忽略停用词和 OOV 词
  -> OR 合并 posting list
  -> 累加 BM25/BM25F 分数
  -> topK 小根堆
  -> 可选短语/邻近度加分
  -> 读取 topK 文档并生成摘要
```

初始参数可从 `k1=1.2~2.0`、`b=0.6~0.8` 范围开始，但最终必须用评测集调参。查询词频对普通短查询影响有限，不要机械复用当前查询 TF-IDF 归一化逻辑。

BM25F 可按字段计算：

```text
weighted_tf = title_boost * normalized_title_tf
            + body_boost  * normalized_body_tf
```

标题 boost、字段 b 值都应配置化，并进入缓存版本或搜索算法版本。

### 6.5 不要只比较 QPS

BM25 的目标首先是相关性。建议人工构造至少 100~300 条覆盖不同场景的查询，每条标注相关文档等级，比较：

- NDCG@10。
- MRR@10。
- Recall@10/50。
- 空结果率。
- OOV query rate。
- 重复结果率。

性能指标同时记录：

- 冷/热缓存 P50、P95、P99。
- 每条查询扫描 posting 数。
- 候选文档数。
- 排序耗时和摘要耗时。
- 索引大小、进程 RSS、启动时间。

当前已直接切换到 BM25 格式，并通过 `BM25_STATS_V1` 头和文档数量校验防止新旧文件混用。后续优化 BM25F 时应增加新的格式版本。

### 6.6 预期提升

- 高频词在同一文档中重复出现时不会无限线性增益。
- 长文档与短文档的比较更合理。
- 当前正文排序获得词频饱和和长度归一化；标题加权需要后续 BM25F 才能实现。
- OR 召回会明显降低空结果率。

具体 NDCG、召回和延迟提升必须用本项目语料测量，不能直接套用其他系统的百分比。

## 7. 在线优化二：关键词推荐

### 7.1 当前编辑距离是否需要替换

编辑距离适合拼写纠错，算法本身可以保留；当前更需要优化的是候选召回、输入归一化和计算方式。

现有实现有以下问题：

1. 英文召回时会转小写，但计算距离时仍使用原始 query；输入 `Apple` 会与小写词典产生额外距离。
2. 候选集合是“共享任意一个字符”的并集，高频字符可能召回大量词。
3. 每个候选都分配完整 `(m+1)*(n+1)` DP 矩阵。
4. 对全部候选完整排序，而最终只需要 topK。
5. “用户正在输入前缀”和“用户已经输错单词”被当作同一个问题。
6. 中文只按汉字编辑距离，无法处理拼音、同音字和语义相关词。

### 7.2 第一阶段：低风险优化

建议先做：

- 英文 query 统一转小写后再召回和计算距离。
- Unicode 规范化、全半角归一化和首尾空白处理。
- 按词长差过滤：若 `abs(len(query)-len(candidate)) > maxDistance`，无需 DP。
- 使用两行 DP，把空间从 O(mn) 降为 O(min(m,n))。
- 使用 bounded Levenshtein/Ukkonen 带状 DP；当前行最小值超过阈值时提前结束。
- 维护 topK 大根堆，不对全部候选完整排序。
- 候选召回时统计共享字符数，优先计算字符重叠更多的词。
- 限制请求 topK 和 query 长度，防止异常输入造成 CPU 放大。

这批改造不改变推荐语义，适合先落地并建立 benchmark。

### 7.3 第二阶段：区分前缀补全和拼写纠错

如果产品交互是“边输入边提示”，前缀匹配应高于编辑距离：

```text
前缀完全匹配
  -> 前缀词按词频/近期热度排序
  -> 不足 topK 时用拼写纠错候选补齐
```

前缀索引可使用 trie/radix tree；词典规模约 5 万时，排序词表上的二分范围查找也足够简单高效。

如果目标是“输完后纠错”，可选择：

- BK-tree：复用编辑距离的度量性质，适合静态词典和较小最大距离。
- SymSpell 删除索引：离线为词生成删除变体，在线召回很快，但会增加索引体积。
- n-gram 倒排：对较长词和模糊匹配更稳健，可按 Jaccard/Dice 先召回再算编辑距离。

对当前静态、约 5 万词的词典，建议先实现“前缀二分 + bounded Levenshtein”；只有 benchmark 表明召回仍是瓶颈时再引入 SymSpell 或 BK-tree。

### 7.4 第三阶段：使用行为信号

当前 `frequency` 来自语料词频，不等于用户点击偏好。可以从脱敏查询日志和点击日志构造：

```text
final_score = edit/prefix score
            + corpus_frequency score
            + recent_query_popularity
            + click-through signal
            + freshness decay
```

应设置时间衰减和反作弊规则，避免永久固化旧热点。日志中不要直接长期保存敏感原始查询；至少做访问控制、保留周期和必要的脱敏/聚合。

中文推荐可以逐步增加拼音全拼/首字母索引和同音候选，但这是新能力，不应混进第一轮编辑距离性能重构。

### 7.5 评测指标

- Recall@K：正确候选是否被召回。
- MRR：正确推荐排在第几位。
- 前缀命中率、纠错命中率分开统计。
- 单请求候选数、DP 计算次数、P95/P99。
- 空推荐率。

## 8. 在线优化三：统一日志与可观测性（日志已完成，metrics 待实现）

### 8.1 原有问题

原代码混用：

- `std::cout/std::cerr`：离线进度、启动信息、缓存统计。
- muduo `LOG_INFO`：TLV/HTTP 连接建立和断开。
- Redis 失败大多静默降级。
- 请求异常只返回客户端，服务端缺少结构化错误上下文。

已有压测报告已经指出：每个 HTTP 请求使用短连接且连接/断开均打印 INFO，会影响并发性能。当前日志还无法回答：

- 某条请求慢在分词、召回、排序、读取文档、摘要还是 Redis？
- L1 命中还是 L2 命中？
- Redis 是 miss、timeout、connect failure 还是 command failure？
- 哪个索引版本处理了请求？
- 某个 XML 为什么被跳过、共跳过多少？

### 8.2 技术选择：spdlog

当前已经选择 `spdlog`，原因是：

- 现代 C++ 接口和格式化支持更好。
- 支持异步 logger、滚动文件、多 sink 和日志级别。
- 接入成本低，适合当前 CMake 项目。

`log4cpp` 可以使用，但接口和生态相对老，不建议为新代码优先选择。另一个可行方案是继续使用 muduo Logging 并接入 muduo AsyncLogging，这样依赖更少；但离线程序也需要统一日志时，spdlog 更容易跨离线/在线复用。

项目已通过 `AppLogger` 统一初始化，并把 muduo WARN 及以上输出桥接到 spdlog。

### 8.3 当前实现与后续建议

在线日志建议至少包含：

```text
timestamp level service request_id protocol client_ip
query_hash query_length topk
index_version cache_version
l1_hit l2_hit cache_status
tokenize_us recall_us rank_us page_read_us abstract_us total_us
candidate_count result_count oov_count
error_code error_message
```

实践原则：

- INFO：启动、配置摘要、索引版本、周期聚合统计，不记录每次连接。
- WARN：Redis 超时/降级、单篇文档解析失败、慢查询。
- ERROR：索引损坏、必需文件读取失败、不可恢复异常。
- DEBUG/TRACE：开发环境按请求记录详细阶段信息。
- 使用异步 bounded queue；队列满时明确采用丢弃低级别日志或同步回退策略。
- 使用按大小 + 按天滚动，配置保留天数和磁盘上限。
- 对错误日志做限流，防止 Redis 故障时每请求刷屏。
- query 默认记录 hash、长度和分词数量；是否记录原文由隐私策略决定。

离线日志建议记录每阶段耗时、输入文件数、原始文档数、无效 XML 数、精确重复数、近似重复数、超大分桶、词项数、posting 数、输出大小和 checksum。

### 8.4 日志不等于指标

缓存命中率、请求量、延迟直方图等应使用 metrics 采集，不能只依靠定期打印日志。可以增加 Prometheus `/metrics`，至少暴露：

- request_total / error_total。
- request_duration_seconds histogram。
- l1/l2 hit/miss/timeout。
- backend_compute_total / singleflight_wait_total。
- candidate/posting scanned histogram。
- index_build_duration 和 index_publish_status。

日志用于排查单次事件，指标用于判断系统趋势，两者职责不同。

## 9. 代码阅读中发现的其他高收益优化

### 9.1 Redis 每条命令都新建连接（已修复）

原 `RedisCache::get/put/erase()` 每次调用都会 `redisConnectWithTimeout()`，完成后立即释放连接。一次 L2 miss 后写缓存至少可能产生两次建连；文档和摘要细粒度缓存还会增加 Redis 操作。

当前已实现有上限的惰性持久连接池：连接独占借出、健康连接复用、异常连接丢弃、池耗尽限时等待。后续仍建议补充：

- 健康检查和断线重连。
- connect/command timeout 分类指标。
- 熔断和失败退避，Redis 故障期间暂时绕过 L2。
- L1/L2 分层命中统计。

这是比“把倒排索引放 Redis”更必要的 Redis 优化。

### 9.2 L1 容量按 key 数而不是字节数

同一个缓存同时保存搜索 JSON、推荐 JSON、完整 Document JSON 和摘要字符串。一个文档可能远大于一个推荐结果，但当前都只占一个 capacity 单位，无法约束真实内存。

建议：

- 至少统计 `key.size()+value.size()+entry overhead`。
- 按字节容量淘汰。
- 更稳妥地拆分 result/document/abstract 三类缓存，分别配置容量和 TTL。
- 超大 value 不进入 L1，避免单条文档挤占缓存。

### 9.3 同步文件和 Redis I/O占用 muduo 工作线程

缓存未命中时，当前工作线程可能同步访问 Redis、打开网页文件、解析 XML并生成摘要。这些操作都发生在 muduo I/O 线程回调中。高尾延迟时会拖住同一线程负责的其他连接。

短期先通过连接池、pread/mmap 和二进制文档格式降低阻塞；如果仍有明显慢请求，再把搜索计算放到独立业务线程池，网络线程只负责收发和任务投递。

### 9.4 HTTP 实现边界（keep-alive、线程和日志瓶颈已优化）

原 HTTP 服务固定短连接且逐连接打印 INFO。当前已经支持 HTTP/1.1 keep-alive、
同连接多请求、请求大小限制，逐连接日志已降为 DEBUG，默认工作线程从 2 提升到 8。
仍存在以下边界：

- 每请求复制整个可读 Buffer 到 string。
- 没有请求头/body 的独立上限。
- 手写最小 HTTP/1.1 解析。
- 每次静态资源请求重新读文件。

如果 HTTP 成为正式接口，仍建议使用成熟 HTTP 组件并增加静态文件缓存。压测工具已支持 `keep-alive/close` 对照模式，后续报告必须注明连接模式。

### 9.5 索引发布需要原子版本切换

当前离线程序直接覆盖多个数据文件，在线启动依赖这些文件恰好属于同一批次。建议：

```text
构建到 version_x.tmp 目录
  -> 完整性校验
  -> 写 manifest + checksum
  -> rename 为不可变 version_x
  -> 原子更新 current 符号链接/manifest
```

在线服务一次加载同一 manifest 下的全部文件。后续可用 `shared_ptr<const IndexSnapshot>` 实现新索引加载完成后原子切换，旧请求自然持有旧快照直到结束。

### 9.6 并发读取和线程安全验证

`KeywordRecommender` 与倒排索引加载后只读，适合并发共享。`cppjieba::Jieba` 也被多个 TLV/HTTP 工作线程共享调用，应针对当前依赖版本做 ThreadSanitizer 和并发压力测试；若内部组件存在可变缓存，则改成每线程 tokenizer 或对象池。

4. 只有在明确的管理、事务或分布式需求下，才把原始数据和元数据迁入数据库。

## 11. 验收标准

每个优化都应有独立回滚开关和验收指标。

| 改造 | 正确性验收 | 性能验收 |
| --- | --- | --- |
| 去重分桶 | 与全量汉明距离基准结果一致；标注集 F1 不下降 | 建库耗时、候选比较数、峰值内存 |
| BM25/BM25F | NDCG/MRR/Recall 优于现有 TF-IDF；空结果率下降 | P95/P99、posting 扫描数、RSS、启动时间 |
| 推荐优化 | 前缀/纠错 Recall@K 与 MRR 不下降 | 候选数、DP 次数、P95/P99 |
| 二进制索引 | 与文本索引返回 docId/统计量一致；checksum 校验 | 文件大小、加载时间、RSS |
| Redis 连接池 | Redis 故障时主搜索仍正确降级 | 建连次数、L2 P95/P99、超时率 |
| 日志与指标 | 错误包含 request/index 上下文且不泄露敏感 query | 日志丢弃数、队列深度、日志开启前后 QPS |

建议压测至少覆盖：

- 冷启动、冷缓存和热缓存。
- 单词、长查询、全部 OOV、部分 OOV、高 DF 词。
- 热点、扫描污染、突发同 key、Redis 故障。
- 大文档、超长 query、超大 topK 和非法 UTF-8。
- 索引切换期间的并发请求。

## 12. 最终建议

本项目当前最值得做的不是“全面换算法”或“把文件全部迁数据库”，而是按以下主线推进：

1. 严格 AND、OOV 全失败和 BM25 迁移已完成；下一步处理标题不入索引并评估 BM25F。
2. 使用版本化统计量索引实现 BM25/BM25F，同时把倒排索引改成紧凑二进制结构。
3. 保留 SimHash 判定，优先优化规范化、精确去重、候选分桶和代表文档选择。
4. 保留编辑距离作为纠错能力，增加前缀补全通路并优化候选与 DP，而不是简单换一个距离算法。
5. spdlog 统一异步日志已完成；后续补齐 metrics。
6. 优先修复 Redis 每命令建连、文档每次打开并解析 XML、缓存不按字节计费等可直接影响尾延迟的问题。

这样得到的提升不仅是某个公式的局部变化，而是相关性、吞吐、尾延迟、内存、可扩展性和可维护性的整体改善。
