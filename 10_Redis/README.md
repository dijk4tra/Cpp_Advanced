# 10_Redis 知识点整理

## Redis 字符串 String 常用命令

### 1. 设置字符串

- 设置一个字符串：`SET key value`
- 只有 key 不存在时才设置成功：`SET key value NX`
- 只有 key 已经存在时才设置成功：`SET key value XX`
- 设置值，并指定过期时间，单位是秒：`SET key value EX seconds`
- 设置值，并指定过期时间，单位是毫秒：`SET key value PX milliseconds`
- 一次设置多个字符串：`MSET key value [key value ...]`
- 设置字符串并指定过期时间，单位是秒：`SETEX key seconds value`
- 设置字符串并指定过期时间，单位是毫秒：`PSETEX key milliseconds value`

------

### 2. 获取字符串

- 获取一个字符串：`GET key`
- 一次获取多个字符串：`MGET key [key ...]`
- 获取旧值并设置新值：`GETSET key value`
- 设置新值并返回旧值：`SET key value GET`

------

### 3. 数字自增自减

- 将 key 中的数字加 1：`INCR key`
- 将 key 中的数字减 1：`DECR key`
- 将 key 中的数字加上指定整数：`INCRBY key increment`
- 将 key 中的数字减去指定整数：`DECRBY key decrement`
- 将 key 中的数字加上指定浮点数：`INCRBYFLOAT key increment`

------

### 4. 字符串追加和长度

- 在字符串末尾追加内容：`APPEND key value`
- 获取字符串长度：`STRLEN key`

------

### 5. 字符串截取和覆盖

- 截取字符串的一部分：`GETRANGE key start end`
- 从指定位置开始覆盖字符串：`SETRANGE key offset value`

------

### 6. 位操作

- 设置字符串指定偏移量上的二进制位：`SETBIT key offset value`
- 获取字符串指定偏移量上的二进制位：`GETBIT key offset`
- 统计字符串中值为 1 的二进制位数量：`BITCOUNT key [start end]`
- 对一个或多个字符串做位运算：`BITOP operation destkey key [key ...]`

------

### 7. 过期时间相关

- 设置 key 的过期时间，单位是秒：`EXPIRE key seconds`
- 设置 key 的过期时间，单位是毫秒：`PEXPIRE key milliseconds`
- 查看 key 剩余过期时间，单位是秒：`TTL key`
- 查看 key 剩余过期时间，单位是毫秒：`PTTL key`
- 移除 key 的过期时间：`PERSIST key`

------

### 8. 删除和判断

- 删除 key：`DEL key [key ...]`
- 判断 key 是否存在：`EXISTS key [key ...]`
- 查看 key 的类型：`TYPE key`

------

### 9. 常见应用场景

- 缓存对象：`SET user:1 "{...}" EX 3600`
- 验证码：`SET code:phone 123456 EX 300`
- 计数器：`INCR article:1:views`
- 分布式锁：`SET lock:order:1 uuid NX EX 30`
- 限流计数：`INCR ip:limit:192.168.1.1` + `EXPIRE`

------

### 10. 面试常问总结

String 类型常用命令可以分成几类：

| 分类       | 常用命令                                          | 作用                     |
| ---------- | ------------------------------------------------- | ------------------------ |
| 设置       | `SET`、`SETEX`、`MSET`                            | 设置一个或多个字符串     |
| 获取       | `GET`、`MGET`                                     | 获取一个或多个字符串     |
| 删除判断   | `DEL`、`EXISTS`、`TYPE`                           | 删除、判断存在、查看类型 |
| 数值操作   | `INCR`、`DECR`、`INCRBY`、`DECRBY`、`INCRBYFLOAT` | 计数器、自增自减         |
| 字符串操作 | `APPEND`、`STRLEN`、`GETRANGE`、`SETRANGE`        | 追加、长度、截取、覆盖   |
| 过期时间   | `EXPIRE`、`TTL`、`PERSIST`                        | 设置和查看过期时间       |

一句话总结：

> Redis 的 String 是最基础的数据类型，常用于缓存、验证码、Token、计数器、分布式锁等场景。常用命令主要包括 `SET/GET`、`MSET/MGET`、`INCR/DECR`、`APPEND/STRLEN`、`EXPIRE/TTL` 等。

## Redis 哈希 Hash 常用命令

### 1. 设置字段

- 设置哈希表中一个字段的值：`HSET key field value`
- 一次设置哈希表中多个字段的值：`HSET key field value [field value ...]`
- 只有字段不存在时才设置成功：`HSETNX key field value`

------

### 2. 获取字段

- 获取哈希表中指定字段的值：`HGET key field`
- 一次获取哈希表中多个字段的值：`HMGET key field [field ...]`
- 获取哈希表中所有字段和值：`HGETALL key`
- 获取哈希表中所有字段名：`HKEYS key`
- 获取哈希表中所有字段值：`HVALS key`
- 获取哈希表中字段的数量：`HLEN key`

------

### 3. 判断字段是否存在

- 判断哈希表中指定字段是否存在：`HEXISTS key field`

------

### 4. 删除字段

- 删除哈希表中的一个或多个字段：`HDEL key field [field ...]`

------

### 5. 数值自增

- 将哈希表中指定字段的整数值加上指定增量：`HINCRBY key field increment`
- 将哈希表中指定字段的浮点数值加上指定增量：`HINCRBYFLOAT key field increment`

------

### 6. 获取字段字符串长度

- 获取哈希表中指定字段值的字符串长度：`HSTRLEN key field`

------

### 7. 遍历哈希表

- 迭代遍历哈希表中的字段和值：`HSCAN key cursor [MATCH pattern] [COUNT count]`

------

### 8. 常见应用场景

- 存储用户对象：`HSET user:1 name zhangsan age 18 city Beijing`
- 获取用户某个字段：`HGET user:1 name`
- 修改用户某个字段：`HSET user:1 age 20`
- 统计用户访问次数：`HINCRBY user:1 visit_count 1`
- 判断字段是否存在：`HEXISTS user:1 email`

## Redis 集合 Set 常用命令

### 1. 添加元素

- 向集合中添加一个或多个元素：`SADD key member [member ...]`

------

### 2. 获取元素

- 获取集合中的所有元素：`SMEMBERS key`
- 随机获取集合中的一个或多个元素，不删除：`SRANDMEMBER key [count]`
- 获取集合中元素的数量：`SCARD key`

------

### 3. 删除元素

- 删除集合中的一个或多个元素：`SREM key member [member ...]`
- 随机删除并返回集合中的一个或多个元素：`SPOP key [count]`

------

### 4. 判断元素是否存在

- 判断元素是否在集合中：`SISMEMBER key member`
- 判断多个元素是否在集合中：`SMISMEMBER key member [member ...]`

------

### 5. 集合运算

- 求多个集合的交集：`SINTER key [key ...]`
- 求多个集合的并集：`SUNION key [key ...]`
- 求多个集合的差集：`SDIFF key [key ...]`

------

### 6. 集合运算并保存结果

- 求多个集合的交集，并保存到目标集合：`SINTERSTORE destination key [key ...]`
- 求多个集合的并集，并保存到目标集合：`SUNIONSTORE destination key [key ...]`
- 求多个集合的差集，并保存到目标集合：`SDIFFSTORE destination key [key ...]`

------

### 7. 移动元素

- 将元素从一个集合移动到另一个集合：`SMOVE source destination member`

------

### 8. 遍历集合

- 迭代遍历集合中的元素：`SSCAN key cursor [MATCH pattern] [COUNT count]`

------

### 9. 常见应用场景

- 用户标签：`SADD user:1:tags java redis mysql`
- 共同好友：`SINTER user:1:friends user:2:friends`
- 关注列表：`SADD user:1:follows user:2 user:3`
- 粉丝列表：`SADD user:2:followers user:1`
- 抽奖：`SPOP lottery 1`
- 去重统计：`SADD article:1:readers user:1 user:2 user:3`

## Redis 有序集合 ZSet / Sorted Set 常用命令

### 1. 添加元素

- 向有序集合中添加一个或多个元素：`ZADD key score member [score member ...]`
- 只有元素不存在时才添加：`ZADD key NX score member`
- 只有元素已经存在时才更新：`ZADD key XX score member`
- 添加元素时返回被修改的元素数量：`ZADD key CH score member`
- 添加元素时让分数自增：`ZADD key INCR score member`

------

### 2. 获取元素

- 按分数从小到大获取指定排名范围内的元素：`ZRANGE key start stop`
- 按分数从大到小获取指定排名范围内的元素：`ZREVRANGE key start stop`
- 获取元素时同时返回分数：`ZRANGE key start stop WITHSCORES`
- 按分数范围获取元素：`ZRANGEBYSCORE key min max`
- 按分数范围倒序获取元素：`ZREVRANGEBYSCORE key max min`
- 按字典序范围获取元素：`ZRANGEBYLEX key min max`

------

### 3. 获取排名

- 获取元素从小到大的排名：`ZRANK key member`
- 获取元素从大到小的排名：`ZREVRANK key member`

------

### 4. 获取分数

- 获取指定元素的分数：`ZSCORE key member`
- 获取多个元素的分数：`ZMSCORE key member [member ...]`

------

### 5. 修改分数

- 给指定元素的分数增加指定值：`ZINCRBY key increment member`

------

### 6. 删除元素

- 删除有序集合中的一个或多个元素：`ZREM key member [member ...]`
- 按排名范围删除元素：`ZREMRANGEBYRANK key start stop`
- 按分数范围删除元素：`ZREMRANGEBYSCORE key min max`
- 按字典序范围删除元素：`ZREMRANGEBYLEX key min max`

------

### 7. 统计元素数量

- 获取有序集合中元素的数量：`ZCARD key`
- 统计指定分数范围内的元素数量：`ZCOUNT key min max`
- 统计指定字典序范围内的元素数量：`ZLEXCOUNT key min max`

------

### 8. 集合运算

- 求多个有序集合的交集，并保存结果：`ZINTERSTORE destination numkeys key [key ...]`
- 求多个有序集合的并集，并保存结果：`ZUNIONSTORE destination numkeys key [key ...]`
- 求多个有序集合的差集，并保存结果：`ZDIFFSTORE destination numkeys key [key ...]`

------

### 9. 遍历有序集合

- 迭代遍历有序集合中的元素：`ZSCAN key cursor [MATCH pattern] [COUNT count]`

------

### 10. 常见应用场景

- 排行榜：`ZADD rank 100 user:1 90 user:2 80 user:3`
- 获取排行榜前 10 名：`ZREVRANGE rank 0 9 WITHSCORES`
- 获取用户排名：`ZREVRANK rank user:1`
- 获取用户分数：`ZSCORE rank user:1`

## Redis 的持久化机制

Redis 常见的持久化机制主要有三种：

### 1. RDB 持久化

- RDB，全称 Redis Database。
- 它会在某个时间点，把 Redis 内存中的数据生成一份快照文件。
- 生成的文件通常叫：`dump.rdb`
- Redis 重启时，可以通过加载 RDB 文件恢复数据。

一句话：

> RDB 保存的是某一时刻 Redis 内存数据的快照。

------

### 2. AOF 持久化

- AOF，全称 Append Only File。
- 它会把 Redis 执行过的写命令追加记录到 AOF 文件中。
- Redis 重启时，会重新执行 AOF 文件中的写命令，从而恢复数据。Redis 官方文档也说明，RDB 是时间点快照，而 AOF 会记录服务器收到的每一条写操作。([Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/?utm_source=chatgpt.com))

一句话：

> AOF 保存的是 Redis 执行过的写命令日志。

------

### 3. RDB + AOF 混合持久化

- Redis 可以同时开启 RDB 和 AOF。
- 重启恢复时，通常会优先使用 AOF，因为 AOF 一般数据更完整。
- Redis 4.0 之后支持 AOF 重写时使用 RDB 格式作为前半部分，再追加 AOF 命令，这就是混合持久化。

一句话：

> 混合持久化结合了 RDB 恢复快、AOF 数据更完整的优点。

------

## RDB 和 AOF 的原理

### 1. RDB 的原理

RDB 的核心思想是：

> 定期把 Redis 当前内存中的所有数据，保存成一个二进制快照文件。

RDB 可以通过两种方式触发：

### 手动触发

- `SAVE`
  - 阻塞 Redis 主线程。
  - 直到 RDB 文件生成完成，Redis 才能继续处理请求。
  - 生产环境一般不推荐使用。
- `BGSAVE`
  - Redis 会 `fork` 一个子进程。
  - 子进程负责生成 RDB 文件。
  - 主进程继续处理客户端请求。
  - 生产环境更常用。

### 自动触发

在配置文件中可以配置：

```bash
save 900 1
save 300 10
save 60 10000
```

含义是：

```text
900 秒内至少 1 个 key 被修改，触发 BGSAVE
300 秒内至少 10 个 key 被修改，触发 BGSAVE
60 秒内至少 10000 个 key 被修改，触发 BGSAVE
```

RDB 原理总结：

```text
Redis 内存数据
        |
        | 生成快照
        v
dump.rdb 文件
        |
        | Redis 重启时加载
        v
恢复数据
```

------

### 2. AOF 的原理

AOF 的核心思想是：

> Redis 每执行一条写命令，就把这条命令追加到 AOF 文件末尾。

例如执行：

```bash
SET name zhangsan
INCR count
HSET user:1 age 18
```

AOF 文件中会记录类似命令：

```bash
SET name zhangsan
INCR count
HSET user:1 age 18
```

Redis 重启时，会重新执行这些写命令：

```text
读取 AOF 文件
        |
        v
重新执行写命令
        |
        v
恢复数据
```

AOF 有三种常见刷盘策略：

| 策略           | 配置                   | 说明                              |
| -------------- | ---------------------- | --------------------------------- |
| 每次写都刷盘   | `appendfsync always`   | 最安全，但性能最差                |
| 每秒刷盘       | `appendfsync everysec` | 默认常用方案，最多丢失约 1 秒数据 |
| 由操作系统决定 | `appendfsync no`       | 性能最好，但数据安全性较差        |

AOF 文件会越来越大，所以 Redis 提供了 AOF 重写机制，也就是 `BGREWRITEAOF`，用更少的命令重新描述当前数据状态。

------

## RDB 和 AOF 的优缺点对比

| 对比项     | RDB                    | AOF                      |
| ---------- | ---------------------- | ------------------------ |
| 保存内容   | 某一时刻的数据快照     | 每条写命令日志           |
| 文件体积   | 较小                   | 通常较大                 |
| 恢复速度   | 快                     | 较慢                     |
| 数据安全性 | 可能丢失较多数据       | 数据更完整               |
| 性能影响   | 主要在生成快照时有影响 | 每次写命令都要追加日志   |
| 可读性     | 二进制文件，不易读     | 命令日志，相对可读       |
| 适合场景   | 备份、全量恢复、容灾   | 对数据安全要求更高的场景 |
| 典型命令   | `SAVE`、`BGSAVE`       | `BGREWRITEAOF`           |

------

### RDB 优点

- 文件紧凑，占用磁盘空间较小。
- 恢复速度快。
- 适合做全量备份。
- 对 Redis 写入性能影响较小，因为不是每条写命令都刷盘。

------

### RDB 缺点

- 数据安全性不如 AOF。
- 如果两次快照之间 Redis 宕机，这段时间的数据会丢失。
- `BGSAVE` 需要 `fork` 子进程，大数据量时可能带来 CPU 和内存压力。

------

### AOF 优点

- 数据安全性更高。
- 默认 `everysec` 策略下，通常最多丢失 1 秒左右的数据。
- AOF 文件是追加写，写入方式比较简单。
- AOF 文件记录的是 Redis 命令，相对更容易理解和修复。

------

### AOF 缺点

- 文件通常比 RDB 大。
- 恢复速度通常比 RDB 慢，因为要重新执行命令。
- 长期运行后需要 AOF 重写，否则文件会越来越大。
- 对写性能影响比 RDB 更明显。

Redis 官方也总结过类似区别：AOF 通常更耐久，但资源消耗更高、恢复可能更慢；RDB 资源消耗较低、恢复较快，但耐久性较弱。([Redis](https://redis.io/docs/latest/operate/rs/databases/configure/database-persistence/?utm_source=chatgpt.com))

------

## 生成 RDB 快照的流程

以 `BGSAVE` 为例，生成 RDB 快照的大致流程如下：

### 1. Redis 主进程接收到 `BGSAVE`

客户端执行：

```bash
BGSAVE
```

Redis 主进程收到生成 RDB 快照的请求。

------

### 2. Redis 判断当前是否已经有持久化子进程

Redis 会先检查：

```text
当前是否正在执行 BGSAVE？
当前是否正在执行 BGREWRITEAOF？
```

如果已经有子进程在执行持久化任务，一般不会重复创建新的持久化子进程。

------

### 3. Redis 主进程 fork 子进程

Redis 主进程调用 `fork()` 创建子进程。

```text
Redis 主进程
     |
     | fork
     v
Redis 子进程
```

fork 之后：

- 主进程继续处理客户端请求。
- 子进程负责生成 RDB 文件。

------

### 4. 子进程根据内存数据生成临时 RDB 文件

子进程会把当前 Redis 数据写入一个临时 RDB 文件。

注意：

```text
子进程看到的是 fork 那一刻的数据快照
```

因为操作系统使用了写时复制，Copy On Write，机制。

------

### 5. 写入完成后，用临时文件替换旧 RDB 文件

子进程写完后：

```text
临时 RDB 文件  --->  替换旧的 dump.rdb
```

这样可以避免生成过程中出现问题导致旧 RDB 文件损坏。

------

### 6. 子进程退出，主进程更新状态

RDB 文件生成完成后：

- 子进程退出。
- 主进程收到通知。
- Redis 更新持久化相关状态信息。

------

### RDB 快照流程图

```text
客户端执行 BGSAVE
        |
        v
Redis 主进程检查是否已有持久化任务
        |
        v
fork 子进程
        |
        |--------------------------|
        |                          |
        v                          v
主进程继续处理请求          子进程生成临时 RDB 文件
                                   |
                                   v
                         写完后替换旧 dump.rdb
                                   |
                                   v
                              子进程退出
                                   |
                                   v
                            主进程更新状态
```

## BGREWRITEAOF 命令的执行流程

`BGREWRITEAOF` 的作用是：

> 在后台重写 AOF 文件，生成一个更小、更紧凑的新 AOF 文件。

注意：AOF 重写不是简单压缩旧 AOF 文件，而是根据 Redis 当前内存数据，重新生成一份可以恢复当前数据状态的最小命令集合。Redis 官方文档也说明，`BGREWRITEAOF` 会创建当前 AOF 文件的更小优化版本；如果重写失败，旧 AOF 文件不会被破坏。([Redis](https://redis.io/docs/latest/commands/bgrewriteaof/?utm_source=chatgpt.com))

例如原来 AOF 里有：

```bash
SET count 1
INCR count
INCR count
INCR count
```

重写后可以变成：

```bash
SET count 4
```

效果一样，但命令更少，文件更小。

------

### BGREWRITEAOF 执行流程

### 1. Redis 主进程接收到 `BGREWRITEAOF`

客户端执行：

```bash
BGREWRITEAOF
```

Redis 开始准备进行 AOF 重写。

------

### 2. Redis 判断当前是否已有后台持久化任务

Redis 会检查：

```text
当前是否正在执行 BGSAVE？
当前是否正在执行 BGREWRITEAOF？
```

如果已经有后台任务，Redis 可能会拒绝或延迟执行。

------

### 3. Redis 主进程 fork 子进程

Redis 主进程执行 `fork()`：

```text
Redis 主进程
     |
     | fork
     v
Redis 子进程
```

fork 之后：

- 主进程继续处理客户端请求。
- 子进程负责根据当前内存数据重写 AOF 文件。

------

### 4. 子进程根据当前内存数据生成新的 AOF 临时文件

子进程不会逐行读取旧 AOF 文件进行压缩。

它会直接遍历当前 Redis 内存数据，然后生成新的写命令。

例如：

```text
当前内存中：
name = zhangsan
count = 4
```

子进程可能生成：

```bash
SET name zhangsan
SET count 4
```

------

### 5. 重写期间，主进程继续处理写请求

在子进程重写 AOF 的过程中，Redis 主进程仍然会接收新的写命令。

这些新写命令会做两件事：

```text
1. 继续追加到旧 AOF 文件
2. 同时写入 AOF 重写缓冲区
```

为什么要写入 AOF 重写缓冲区？

因为子进程生成的新 AOF 文件，只包含 fork 那一刻的数据。

fork 之后新产生的写命令，也必须追加到新 AOF 文件中，否则数据会丢失。

------

### 6. 子进程完成 AOF 临时文件

子进程完成重写后，会通知主进程：

```text
新的 AOF 临时文件已经生成完成
```

------

### 7. 主进程把 AOF 重写缓冲区追加到新 AOF 文件

主进程会把重写期间产生的新写命令，追加到子进程生成的新 AOF 文件末尾。

这样新 AOF 文件就包含了：

```text
fork 时刻的数据
+
fork 之后的新增写命令
```

------

### 8. 用新的 AOF 文件替换旧 AOF 文件

最后 Redis 用新的 AOF 文件替换旧的 AOF 文件。

```text
新的 AOF 文件  --->  替换旧 AOF 文件
```

替换完成后，后续写命令继续追加到新的 AOF 文件中。

------

### BGREWRITEAOF 流程图

```text
客户端执行 BGREWRITEAOF
        |
        v
主进程检查是否已有后台持久化任务
        |
        v
fork 子进程
        |
        |-----------------------------------|
        |                                   |
        v                                   v
主进程继续处理请求                  子进程遍历内存数据
        |                                   |
        v                                   v
新写命令追加到旧 AOF          生成新的 AOF 临时文件
        |
        v
新写命令写入 AOF 重写缓冲区
        |
        v
子进程完成重写并通知主进程
        |
        v
主进程把 AOF 重写缓冲区追加到新 AOF
        |
        v
新 AOF 文件替换旧 AOF 文件
        |
        v
后续写命令追加到新 AOF 文件
```

------

## 持久化机制总结

| 问题              | 核心答案                                                     |
| ----------------- | ------------------------------------------------------------ |
| Redis 持久化机制  | RDB、AOF、RDB+AOF 混合持久化                                 |
| RDB 原理          | 定期生成内存快照                                             |
| AOF 原理          | 追加记录每条写命令                                           |
| RDB 优点          | 文件小、恢复快、适合备份                                     |
| RDB 缺点          | 容易丢失最近一次快照后的数据                                 |
| AOF 优点          | 数据更安全、丢失更少                                         |
| AOF 缺点          | 文件大、恢复慢、需要重写                                     |
| RDB 快照流程      | 主进程 fork 子进程，子进程写临时 RDB，完成后替换旧文件       |
| BGREWRITEAOF 流程 | 主进程 fork 子进程，子进程重写 AOF，主进程记录重写期间的新命令，最后替换旧 AOF |

一句话总结：

> RDB 是“拍照片”，保存某一刻的数据快照；AOF 是“记流水账”，记录每一条写命令。RDB 恢复快但可能丢数据，AOF 数据更安全但文件更大、恢复更慢。

## 缓存穿透

**缓存穿透**指的是：

> 用户请求的数据，在缓存中不存在，在数据库中也不存在。

正常情况下，请求流程是：

```text
请求数据
   |
   v
查 Redis 缓存
   |
   | 命中
   v
直接返回数据
```

如果缓存没有命中，就会去查数据库：

```text
请求数据
   |
   v
查 Redis 缓存
   |
   | 未命中
   v
查数据库
```

但是缓存穿透的问题在于：

```text
Redis 没有这个数据
数据库也没有这个数据
```

所以每次请求都会变成：

```text
请求不存在的数据
        |
        v
Redis 查不到
        |
        v
MySQL 也查不到
        |
        v
返回空结果
```

由于数据库没有这个数据，所以也没法把正常数据写回缓存。下一次相同请求过来，还是会继续穿过 Redis，直接打到数据库。

------

### 举例说明

假设数据库中用户 id 最大只有 `1000`。

但是有人不断请求：

```text
user:999999
user:888888
user:-1
user:abc
```

这些数据在 Redis 中不存在，在 MySQL 中也不存在。

于是每个请求都会绕过缓存，直接访问数据库：

```text
GET user:999999
        |
        v
Redis 没有
        |
        v
MySQL 也没有
        |
        v
返回空
```

如果这种请求量很大，就会导致数据库压力暴增，甚至被打垮。

------

### 缓存穿透的本质

缓存穿透的本质是：

> 请求访问了一个缓存和数据库中都不存在的数据，导致缓存失去保护数据库的作用。

也可以这样理解：

```text
正常缓存：
请求 -> Redis -> 返回

缓存穿透：
请求 -> Redis 未命中 -> MySQL 查询 -> MySQL 也没有 -> 返回空
```

Redis 本来是数据库前面的一层保护，但是对于“不存在的数据”，Redis 没有缓存效果。

------

### 应对缓存穿透的方案

#### 1. 缓存空值

**思路**

当数据库查询结果为空时，不要直接返回，而是把这个“空结果”也缓存到 Redis 中。

例如请求：

```text
user:999999
```

Redis 没有，查询 MySQL 后也没有。

这时可以写入 Redis：

```bash
SET user:999999 "" EX 60
```

或者：

```bash
SET user:999999 null EX 60
```

之后再请求 `user:999999`，就可以直接从 Redis 返回空结果，不再访问数据库。

------

**流程**

```text
请求 user:999999
        |
        v
查询 Redis
        |
        | 未命中
        v
查询 MySQL
        |
        | 数据不存在
        v
把空值写入 Redis，设置较短过期时间
        |
        v
返回空结果
```

下一次请求：

```text
请求 user:999999
        |
        v
查询 Redis
        |
        | 命中空值
        v
直接返回空结果，不查数据库
```

------

**优点**

- 实现简单。
- 对重复请求同一个不存在 key 的场景非常有效。
- 可以明显减少数据库压力。

------

**缺点**

- 如果大量不同的无效 key 被请求，Redis 中会缓存很多空值，占用内存。
- 空值过期时间不好设置。
- 可能存在短时间数据不一致问题。

例如：

```text
第一次查询 user:10086，数据库中不存在，于是缓存空值。
过了一会儿，数据库新增了 user:10086。
但是 Redis 里还有空值缓存。
此时查询 user:10086，可能仍然返回空。
```

所以空值缓存一般要设置较短的过期时间，比如：

```text
30 秒、60 秒、5 分钟
```

------

#### 2. 使用布隆过滤器

**思路**

在 Redis 和数据库前面加一层布隆过滤器。

布隆过滤器可以快速判断：

```text
这个 key 是否可能存在？
```

请求进来后，先经过布隆过滤器：

```text
请求 key
   |
   v
布隆过滤器判断
   |
   | 一定不存在
   v
直接拒绝，不查 Redis，不查 MySQL
```

如果布隆过滤器判断这个 key 可能存在，才继续查 Redis 和数据库。

------

**流程**

```text
请求 user:999999
        |
        v
布隆过滤器判断
        |
        | 一定不存在
        v
直接返回空结果
```

如果请求的是可能存在的数据：

```text
请求 user:100
        |
        v
布隆过滤器判断
        |
        | 可能存在
        v
查询 Redis
        |
        | 未命中
        v
查询 MySQL
```

------

**布隆过滤器的特点**

布隆过滤器有两个重要特点：

| 判断结果   | 含义                           |
| ---------- | ------------------------------ |
| 一定不存在 | 这个数据肯定不存在             |
| 可能存在   | 这个数据可能存在，也可能不存在 |

也就是说：

> 布隆过滤器不会误判“存在的数据不存在”，但可能误判“不存在的数据存在”。

------

**优点**

- 能在请求进入 Redis 和数据库之前拦截大量非法 key。
- 非常适合防止恶意攻击和随机 key 查询。
- 内存占用较小。

------

**缺点**

- 有一定误判率。
- 删除数据不方便。
- 需要提前把合法 key 加入布隆过滤器。
- 系统复杂度比缓存空值更高。

------

#### 3. 参数校验

**思路**

在查询缓存之前，先对请求参数做合法性校验。

很多缓存穿透请求本身就是非法参数，例如：

```text
id = -1
id = abc
id = 999999999999
pageSize = 100000
```

这些请求没有必要进入 Redis，更没有必要进入数据库。

------

**示例**

如果用户 id 必须是正整数：

```text
id <= 0       直接拒绝
id 不是数字   直接拒绝
id 过大       直接拒绝
```

**流程**

```text
请求参数
   |
   v
参数校验
   |
   | 不合法
   v
直接返回错误
```

------

**优点**

- 实现简单。
- 能过滤明显非法请求。
- 可以减少 Redis 和数据库压力。

------

**缺点**

- 只能过滤格式非法的请求。
- 对格式合法但数据不存在的请求无效。

例如：

```text
user:999999
```

这个 id 是合法数字，但数据库中可能不存在，参数校验拦不住。

------

#### 4. 接口限流

**思路**

当短时间内出现大量异常请求时，可以通过限流保护系统。

常见限流维度：

- 按 IP 限流
- 按用户限流
- 按接口限流
- 按设备号限流
- 按 token 限流

------

**示例**

例如限制某个 IP：

```text
1 秒最多访问 10 次用户查询接口
```

超过限制后直接拒绝：

```text
请求
 |
 v
限流判断
 |
 | 超过阈值
 v
返回 429 Too Many Requests
```

------

**优点**

- 可以防止恶意攻击。
- 可以保护数据库不被瞬间打垮。
- 常和其他方案一起使用。

------

**缺点**

- 不能从根本上解决不存在 key 的问题。
- 阈值设置不好，可能误伤正常用户。

------

#### 5. 黑名单机制

**思路**

如果发现某些 IP、用户、设备持续请求大量不存在的数据，可以把它们加入黑名单。

```text
异常请求来源
      |
      v
加入黑名单
      |
      v
后续请求直接拒绝
```

------

**优点**

- 对恶意攻击有效。
- 可以减少无效请求进入系统。

------

**缺点**

- 需要监控和识别异常行为。
- 可能误封正常用户。
- 一般作为辅助方案，不是核心方案。

------

#### 常见方案对比

| 方案       | 作用                      | 优点               | 缺点                         |
| ---------- | ------------------------- | ------------------ | ---------------------------- |
| 缓存空值   | 缓存数据库不存在的结果    | 简单有效           | 可能占用内存，存在短暂不一致 |
| 布隆过滤器 | 提前判断 key 是否可能存在 | 拦截能力强，内存小 | 有误判率，维护复杂           |
| 参数校验   | 拦截非法参数              | 简单直接           | 只能拦截明显非法请求         |
| 接口限流   | 控制异常请求量            | 防止系统被打爆     | 不能彻底解决穿透             |
| 黑名单     | 拦截恶意来源              | 对攻击有效         | 需要识别异常来源             |

------

### 面试回答

缓存穿透是指请求查询的数据在缓存中不存在，在数据库中也不存在，导致每次请求都会绕过缓存直接访问数据库。如果大量请求访问不存在的数据，就会给数据库带来很大压力。

常见解决方案有：

1. **缓存空值**：数据库查询为空时，也把空结果写入 Redis，并设置较短过期时间。
2. **布隆过滤器**：把合法 key 提前放入布隆过滤器，请求先经过布隆过滤器，不存在的 key 直接拦截。
3. **参数校验**：对非法 id、非法参数直接拒绝，避免无效请求进入缓存和数据库。
4. **限流和黑名单**：对异常 IP、异常用户进行限流或封禁，防止恶意攻击。

一句话总结：

> 缓存穿透就是“查一个根本不存在的数据”，导致请求穿过 Redis 打到数据库。常见解决方案是缓存空值、布隆过滤器、参数校验、限流和黑名单，其中缓存空值和布隆过滤器是最常见的核心方案。

------

## 缓存击穿

**缓存击穿**指的是：

> 某个热点 key 在缓存中过期了，而这个 key 又被大量并发请求访问，导致这些请求瞬间全部打到数据库。

注意关键词：

```text
热点 key
+
突然过期
+
大量并发请求
```

正常情况下：

```text
请求热点数据
     |
     v
查询 Redis
     |
     | 命中
     v
直接返回
```

但是当热点 key 过期时：

```text
大量请求同时访问热点 key
          |
          v
      Redis 未命中
          |
          v
    大量请求同时查 MySQL
          |
          v
      数据库压力暴增
```

------

### 举例说明

比如首页有一个热门商品：

```text
product:1001
```

这个商品信息被缓存在 Redis 中：

```bash
SET product:1001 "{商品信息}" EX 3600
```

平时大量用户访问这个商品时，Redis 可以直接返回数据。

但是 1 小时后，`product:1001` 过期了。

此时如果刚好有大量请求同时访问这个商品：

```text
请求 1 -> Redis 未命中 -> 查 MySQL
请求 2 -> Redis 未命中 -> 查 MySQL
请求 3 -> Redis 未命中 -> 查 MySQL
请求 4 -> Redis 未命中 -> 查 MySQL
...
```

这些请求会在同一时间打到数据库，可能导致数据库压力瞬间升高。

这就是缓存击穿。

------

### 缓存击穿的本质

缓存击穿的本质是：

> 热点数据失效瞬间，大量并发请求绕过缓存，直接访问数据库。

可以简单理解为：

```text
缓存穿透：查不存在的数据
缓存击穿：热点 key 过期了
缓存雪崩：大量 key 同时过期或 Redis 故障
```

------

### 应对缓存击穿的方案

#### 1. 互斥锁

**思路**

当热点 key 过期后，不允许所有请求都去查数据库。

只让一个请求去查数据库并重建缓存，其他请求等待或者稍后重试。

**流程：**

```text
请求热点 key
      |
      v
查询 Redis
      |
      | 未命中
      v
尝试获取互斥锁
      |
      | 获取成功
      v
查询数据库，重建缓存，释放锁
```

其他没有拿到锁的请求：

```text
请求热点 key
      |
      v
查询 Redis
      |
      | 未命中
      v
尝试获取互斥锁
      |
      | 获取失败
      v
等待一会儿后重试 Redis
```

------

**示例**

使用 Redis 的 `SET NX EX` 实现互斥锁：

```bash
SET lock:product:1001 uuid NX EX 10
```

含义：

```text
如果 lock:product:1001 不存在：
    加锁成功，当前请求去查数据库

如果 lock:product:1001 已存在：
    加锁失败，说明已有请求正在重建缓存
```

伪代码：

```cpp
data = getRedis("product:1001");

if (data != null) {
    return data;
}

lock = setRedis("lock:product:1001", uuid, NX, EX, 10);

if (lock success) {
    data = queryDB("product:1001");
    setRedis("product:1001", data, EX, 3600);
    delRedis("lock:product:1001");
    return data;
} else {
    sleep(50ms);
    retry getRedis("product:1001");
}
```

------

**优点**

- 可以有效防止大量请求同时打到数据库。
- 实现思路比较清晰。
- 是解决缓存击穿最常用的方案之一。

------

**缺点**

- 实现复杂度比普通缓存高。
- 需要考虑锁超时、死锁、误删锁等问题。
- 如果请求等待时间过长，可能影响响应速度。

------

#### 2. 热点 key 永不过期

**思路**

对于非常热点的数据，不设置物理过期时间。

也就是说，不让 Redis 自动删除这个 key。

```bash
SET product:1001 "{商品信息}"
```

这样热点 key 不会因为过期而突然失效，也就不会出现大量请求同时打到数据库的问题。

------

**但是数据怎么更新？**

可以使用**逻辑过期时间**。

也就是 value 中自己保存一个过期时间字段：

```json
{
  "data": {
    "id": 1001,
    "name": "热门商品"
  },
  "expireTime": "2026-06-21 12:00:00"
}
```

Redis key 本身不设置过期时间。

每次查询时，先判断 value 里的逻辑过期时间。

------

**逻辑过期流程**

```text
请求热点 key
      |
      v
查询 Redis
      |
      | 命中
      v
判断逻辑过期时间
      |
      | 没过期
      v
直接返回数据
```

如果逻辑上已经过期：

```text
请求热点 key
      |
      v
查询 Redis
      |
      | 命中旧数据
      v
发现逻辑过期
      |
      v
尝试获取互斥锁
      |
      | 获取成功
      v
后台线程重建缓存
      |
      v
当前请求先返回旧数据
```

也就是说：

> 缓存逻辑过期后，不是让所有请求都去查数据库，而是先返回旧数据，然后让一个线程异步更新缓存。

------

**优点**

- 热点 key 不会突然消失。
- 请求基本都能快速返回。
- 对数据库保护效果很好。
- 非常适合热点数据场景。

------

**缺点**

- 可能短时间返回旧数据。
- 实现比普通过期时间复杂。
- 需要业务能接受短暂数据不一致。

------

#### 3. 提前预热热点数据

**思路**

系统启动时，或者活动开始前，提前把热点数据加载到 Redis。

例如：

```bash
SET product:1001 "{商品信息}" EX 3600
SET product:1002 "{商品信息}" EX 3600
SET product:1003 "{商品信息}" EX 3600
```

适合以下场景：

```text
秒杀商品
热门商品
首页配置
排行榜
热点文章
热门评论
```

------

**优点**

- 可以避免热点数据第一次访问时直接打到数据库。
- 对活动类场景很有用。

------

**缺点**

- 需要提前知道哪些数据是热点。
- 热点变化时，需要动态更新缓存。

------

#### 4. 后台定时刷新热点 key

**思路**

对热点 key 不完全依赖用户请求触发缓存重建，而是由后台任务定时刷新。

例如每隔一段时间执行：

```text
查询数据库最新商品信息
        |
        v
更新 Redis 中的热点 key
```

这样可以避免热点 key 真正过期。

------

**示例**

```text
每 5 分钟刷新一次：
product:1001
product:1002
home:banner
rank:hot
```

------

**优点**

- 用户请求不承担缓存重建压力。
- 可以减少热点 key 过期导致的击穿问题。

------

**缺点**

- 会增加后台任务复杂度。
- 如果热点 key 很多，刷新成本较高。
- 需要控制刷新频率，避免反过来给数据库造成压力。

------

#### 5. 设置合理的过期时间

**思路**

对于热点 key，可以设置较长的过期时间，减少过期频率。

例如普通数据：

```bash
SET product:2001 "{商品信息}" EX 300
```

热点数据：

```bash
SET product:1001 "{商品信息}" EX 7200
```

这样热点数据不会频繁失效。

------

**优点**

- 实现简单。
- 可以降低击穿概率。

------

**缺点**

- 不能彻底解决问题。
- 仍然可能在过期瞬间出现并发访问数据库。
- 数据更新不及时的问题更明显。

------

### 常见方案对比

| 方案              | 作用                     | 优点             | 缺点                     |
| ----------------- | ------------------------ | ---------------- | ------------------------ |
| 互斥锁            | 只允许一个请求重建缓存   | 防止并发打 DB    | 有锁复杂度，可能影响响应 |
| 热点 key 永不过期 | 避免热点 key 突然失效    | 对热点数据保护强 | 可能返回旧数据           |
| 逻辑过期          | key 不物理删除，异步刷新 | 响应快，抗击穿强 | 短暂数据不一致           |
| 缓存预热          | 提前加载热点数据         | 适合秒杀、首页   | 需要提前识别热点         |
| 定时刷新          | 后台主动更新缓存         | 用户请求压力小   | 任务复杂，刷新成本高     |
| 延长过期时间      | 减少过期频率             | 简单             | 不能根治                 |

------

### 面试回答

缓存击穿是指某个**热点 key** 在 Redis 中过期了，同时有大量并发请求访问这个 key，导致这些请求在缓存未命中的情况下全部打到数据库，造成数据库瞬间压力过大。

常见解决方案有：

1. **互斥锁**：缓存未命中时，只允许一个线程查询数据库并重建缓存，其他线程等待或重试。
2. **热点 key 永不过期**：对热点数据不设置物理过期时间，避免 key 突然失效。
3. **逻辑过期**：value 中保存过期时间，逻辑过期后先返回旧数据，再由后台线程异步刷新缓存。
4. **缓存预热**：系统启动或活动开始前，提前把热点数据加载到 Redis。
5. **后台定时刷新**：定时更新热点 key，避免它们自然过期。
6. **设置较长过期时间**：减少热点 key 频繁失效的概率。

一句话总结：

> 缓存击穿就是“热点 key 过期后，大量请求同时打到数据库”。核心解决思路是：不要让所有请求都去查数据库，要么加互斥锁，只让一个请求重建缓存；要么让热点 key 永不过期，配合逻辑过期和后台刷新。

------

## 缓存雪崩

**缓存雪崩**指的是：

> 大量缓存 key 在同一时间失效，或者 Redis 服务整体不可用，导致大量请求瞬间打到数据库。

关键词是：

```text
大量 key
+
同时失效
+
请求直接打到数据库
```

正常情况下：

```text
用户请求
   |
   v
Redis 缓存
   |
   | 命中
   v
直接返回数据
```

但是发生缓存雪崩时：

```text
大量请求
   |
   v
Redis 大量未命中 / Redis 不可用
   |
   v
大量请求打到 MySQL
   |
   v
数据库压力暴增，甚至宕机
```

------

### 举例说明

假设系统中很多缓存都设置了相同的过期时间：

```bash
SET product:1  "商品1" EX 3600
SET product:2  "商品2" EX 3600
SET product:3  "商品3" EX 3600
SET product:4  "商品4" EX 3600
SET product:5  "商品5" EX 3600
```

这些 key 都是 1 小时后过期。

如果刚好 1 小时后流量很大，那么这些 key 会集中失效：

```text
product:1  过期
product:2  过期
product:3  过期
product:4  过期
product:5  过期
...
```

于是大量请求都会缓存未命中，直接访问数据库：

```text
请求 product:1 -> Redis 未命中 -> MySQL
请求 product:2 -> Redis 未命中 -> MySQL
请求 product:3 -> Redis 未命中 -> MySQL
请求 product:4 -> Redis 未命中 -> MySQL
...
```

这就是缓存雪崩。

------

### 缓存雪崩的两种常见情况

#### 1. 大量 key 同时过期

例如：

```text
大量商品缓存
大量首页缓存
大量用户缓存
大量排行榜缓存
```

如果它们设置了相同的过期时间，就可能在某一刻集中失效。

------

#### 2. Redis 服务不可用

比如：

```text
Redis 宕机
Redis 网络故障
Redis 主从切换异常
Redis 集群大面积不可用
```

此时所有请求都无法从缓存中获取数据，会直接打到数据库。

这种情况比大量 key 过期更严重。

------

### 应对缓存雪崩的方案

#### 1. 给过期时间增加随机值

**思路**

不要让大量 key 在同一时间过期。

原来这样设置：

```bash
SET product:1 data EX 3600
SET product:2 data EX 3600
SET product:3 data EX 3600
```

可以改成：

```bash
SET product:1 data EX 3600 + 随机秒数
SET product:2 data EX 3600 + 随机秒数
SET product:3 data EX 3600 + 随机秒数
```

例如：

```text
product:1  3600 秒后过期
product:2  3650 秒后过期
product:3  3710 秒后过期
product:4  3540 秒后过期
```

这样 key 的过期时间被打散，就不会集中失效。

------

**示例**

```cpp
expireTime = baseTime + random(0, 300);
```

例如基础过期时间是 1 小时，再加上 0 到 5 分钟随机值：

```text
3600 秒 ~ 3900 秒之间随机过期
```

------

**优点**

- 实现简单。
- 对“大量 key 同时过期”非常有效。
- 是最常用的防雪崩方案之一。

------

**缺点**

- 只能解决 key 集中过期问题。
- 如果 Redis 整体宕机，这个方案无效。

------

#### 2. 热点数据永不过期

**思路**

对于特别重要、访问量特别高的数据，不设置物理过期时间。

例如：

```bash
SET home:banner data
SET hot:rank data
SET product:1001 data
```

这些 key 不会自动过期。

然后通过后台任务定时刷新数据。

------

**流程**

```text
用户请求
   |
   v
查询 Redis
   |
   | 命中
   v
直接返回数据
```

后台任务：

```text
定时查询数据库
      |
      v
更新 Redis 热点数据
```

------

**优点**

- 可以避免热点 key 突然过期。
- 对核心数据保护效果好。
- 适合首页、排行榜、热门商品等场景。

------

**缺点**

- 可能短时间返回旧数据。
- 需要后台刷新机制。
- 不适合所有数据都永不过期。

------

#### 3. 缓存预热

**思路**

系统启动后，不要等用户请求来了才加载缓存，而是提前把核心数据加载到 Redis。

适合这些场景：

```text
系统重启后
活动开始前
秒杀开始前
大促开始前
缓存被清空后
```

------

**示例**

系统启动时提前加载：

```text
查询数据库中的热门商品
        |
        v
写入 Redis
```

例如：

```bash
SET product:1001 data EX 7200
SET product:1002 data EX 7200
SET product:1003 data EX 7200
```

------

**优点**

- 避免系统刚启动时大量请求直接打数据库。
- 适合热点数据明确的业务场景。

------

**缺点**

- 需要提前知道热点数据。
- 数据量太大时，预热成本较高。

------

#### 4. 多级缓存

**思路**

不要只依赖 Redis 一层缓存，可以增加本地缓存。

例如：

```text
本地缓存 Caffeine / Guava Cache
+
Redis 缓存
+
MySQL 数据库
```

**请求流程：**

```text
请求
 |
 v
本地缓存
 |
 | 未命中
 v
Redis
 |
 | 未命中
 v
MySQL
```

如果 Redis 短暂不可用，本地缓存还能挡住一部分请求。

------

**优点**

- 可以降低 Redis 故障带来的影响。
- 能减少 Redis 压力。
- 对热点数据效果很好。

------

**缺点**

- 系统复杂度更高。
- 本地缓存可能存在数据不一致。
- 多台机器上的本地缓存需要考虑更新问题。

------

#### 5. Redis 高可用

**思路**

如果缓存雪崩是 Redis 故障导致的，就需要提高 Redis 自身可用性。

常见方案：

```text
Redis 主从复制
Redis Sentinel 哨兵
Redis Cluster 集群
```

作用：

| 方案          | 作用                       |
| ------------- | -------------------------- |
| 主从复制      | 提供数据副本               |
| Sentinel 哨兵 | 主节点宕机后自动故障转移   |
| Cluster 集群  | 数据分片，提高容量和可用性 |

------

**优点**

- 可以降低 Redis 整体不可用的概率。
- 是生产环境必备方案。
- 对 Redis 宕机导致的雪崩非常重要。

------

**缺点**

- 部署和运维复杂度更高。
- 主从切换期间仍可能有短暂不可用。
- 集群也需要考虑网络分区、数据一致性等问题。

------

#### 6. 限流和降级

**思路**

当缓存大量失效或者 Redis 故障时，不能让所有请求都打到数据库。

可以在服务层做限流：

```text
超过系统承受能力的请求，直接拒绝或返回默认结果
```

例如：

```text
每秒只允许 1000 个请求访问数据库
超过的请求返回“系统繁忙”
```

------

**降级示例**

如果 Redis 不可用，可以返回：

```text
默认首页数据
默认排行榜
静态页面
稍后再试
```

------

**优点**

- 可以保护数据库。
- 防止系统被完全打垮。
- 是高并发系统中的兜底方案。

------

**缺点**

- 部分请求会失败。
- 用户体验可能下降。
- 需要提前设计降级策略。

------

#### 7. 互斥锁重建缓存

**思路**

当某个 key 失效后，不让所有请求都查数据库。

只允许一个请求查数据库并重建缓存，其他请求等待或快速失败。

```text
缓存未命中
   |
   v
尝试获取锁
   |
   | 成功
   v
查询数据库并写入缓存
```

其他请求：

```text
获取锁失败
   |
   v
等待后重试 / 返回旧数据 / 返回默认值
```

------

**优点**

- 可以减少数据库并发压力。
- 对热点 key 失效有明显效果。

------

**缺点**

- 更常用于解决缓存击穿。
- 如果是大量不同 key 同时失效，只靠互斥锁还不够。
- 需要处理锁超时、误删锁等问题。

------

#### 常见方案对比

| 方案             | 作用                  | 优点                | 缺点                |
| ---------------- | --------------------- | ------------------- | ------------------- |
| 过期时间加随机值 | 打散 key 的过期时间   | 简单有效            | 不能解决 Redis 宕机 |
| 热点数据永不过期 | 防止热点 key 失效     | 保护核心数据        | 可能返回旧数据      |
| 缓存预热         | 提前加载缓存          | 避免冷启动冲击      | 需要知道热点数据    |
| 多级缓存         | 本地缓存 + Redis      | 降低 Redis 故障影响 | 数据一致性复杂      |
| Redis 高可用     | 防止 Redis 整体不可用 | 生产环境必备        | 部署运维复杂        |
| 限流降级         | 保护数据库            | 兜底能力强          | 用户体验下降        |
| 互斥锁           | 控制缓存重建并发      | 减少 DB 压力        | 更适合热点 key 击穿 |

------

### 面试回答

缓存雪崩是指大量缓存 key 在同一时间失效，或者 Redis 服务整体不可用，导致大量请求同时打到数据库，从而使数据库压力瞬间暴增，甚至引发系统崩溃。

常见解决方案有：

1. **过期时间加随机值**：给 key 的 TTL 加随机偏移，避免大量 key 同时过期。
2. **热点数据永不过期**：核心热点数据不设置物理过期时间，通过后台任务定时刷新。
3. **缓存预热**：系统启动或活动开始前，提前把热点数据加载到 Redis。
4. **多级缓存**：使用本地缓存 + Redis，降低 Redis 故障对系统的影响。
5. **Redis 高可用**：使用主从复制、哨兵、Cluster，降低 Redis 整体不可用概率。
6. **限流和降级**：当缓存异常时，限制进入数据库的请求量，必要时返回默认数据或错误提示。
7. **互斥锁重建缓存**：缓存失效后只允许少量请求重建缓存，避免并发打爆数据库。

一句话总结：

> 缓存雪崩就是“大量缓存同时失效或 Redis 故障，导致请求集体打到数据库”。核心解决思路是：打散过期时间、提前预热热点数据、保证 Redis 高可用，并通过限流降级保护数据库。
